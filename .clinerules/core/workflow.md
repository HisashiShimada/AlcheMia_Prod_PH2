# タスク実行ワークフロー規約

## 概要

Clineがタスクを実行する際は、必ず事前にタスク計画書を`docs/tasks/`に作成し、ユーザーの承認を得てから作業を開始する必要があります。

## ワークフロー

### 1. タスク受領

ユーザーからタスクを受け取ったら、以下の手順で進めます。

### 2. タスク専用フォルダの作成

**必須ステップ:**

1. `docs/tasks/` ディレクトリ配下にタスク専用フォルダを作成
   - フォルダ名: `YYYYMMDD_HHMM_<タスク名>/`
   - 例: `docs/tasks/20251216_1830_ログイン機能改修/`

2. このフォルダ内にすべてのタスク関連ドキュメントを配置

### 3. タスク計画書の作成

**必須ステップ:**

1. タスク専用フォルダ内に `PLAN.md` を作成
2. タスク計画書には以下の内容を含める：
   - タスクの概要
   - 目的と期待される成果
   - 実装ステップの詳細チェックリスト
   - 影響範囲の分析
   - リスクと対策
   - 必要なファイルの変更リスト
   - テスト計画

3. タスク計画書をユーザーに提示して承認を求める

### 4. ユーザー承認

- ユーザーが計画書を確認し、承認または修正を指示
- 修正が必要な場合は計画書を更新して再提示
- 承認後、作業開始

#### ⚠️ 重要: 計画書修正後は必ず再承認を得てから実作業を開始する

**OK（問題なし）:**
- ユーザーの修正指摘を受けて計画書（PLAN.md）を更新する

**NG（禁止）:**
- 計画書を修正した後、承認を得ずにソースコード・ドキュメント等の実作業を開始する

**正しいフロー:**
```
1. ユーザーから修正指摘を受ける
   ↓
2. 計画書（PLAN.md）を修正する  ← OK
   ↓
3. 修正した計画書をユーザーに提示し、ask_followup_question で承認を求める
   ↓
4. ユーザーが明示的に承認する（「承認します」「OK」「進めてください」等）
   ↓
5. 実作業開始（PLAN.md 以外のファイルへの変更）
```

**❌ 間違ったフロー（禁止）:**
```
1. ユーザーから修正指摘を受ける
2. 計画書（PLAN.md）を修正する
3. 承認を得ずにソースコード・ドキュメント等の実作業を開始する  ← 禁止
```

### 4.5. 実装開始前の規約確認（必須）

**承認後、実装を開始する前に、以下の規約ファイルを必ず確認すること：**

#### 共通規約（必須）

- [ ] `.clinerules/core/workflow.md` - タスク実行の基本フロー
- [ ] `.clinerules/development/config.md` - コーディング規約
- [ ] **`.clinerules/development/typescript.md`** - TypeScript型定義規約（特に重要）
- [ ] `.clinerules/development/database.md` - DB操作規約（DB関連の場合）
- [ ] `.clinerules/development/security.md` - セキュリティ規約

#### 専門領域別規約（該当する場合は必須）

- [ ] `.cline/skills/backend-develop-skill/docs/backend.md` - バックエンド実装時
- [ ] `.cline/skills/frontend-develop-skill/docs/frontend.md` - フロントエンド実装時
- [ ] `.cline/skills/test-skill/docs/test.md` - テスト実装時

**重要**: `.cline/skills/`は専門領域別の詳細規約で、コンテキスト圧迫を防ぐために分離されています。該当する領域のskillのみを確認してください。

#### 設計ドキュメント

- [ ] 該当する画面・機能の設計ドキュメント

**特に注意すべきポイント:**
- ✅ TypeScript型定義は専用ファイルに集約（**インライン型定義禁止**）
- ✅ 引数にオブジェクトを渡す際は必ず変数に代入してから渡す（**インラインオブジェクト引数禁止**）
- ✅ バリデーションはミドルウェアで実施（**コントローラーに書かない** - backend）
- ✅ DB操作はRepository層に集約
- ✅ **Routes（Controller）はService層のみを呼び出す（Repository直接呼び出し禁止）**
- ✅ organization_idを必ず含める（マルチテナント分離）
- ✅ 既存コードのパターンを参照する
- ✅ **フロントエンドのコンポーネントから fetch/axios を直接呼び出さない（services/ 経由必須）**
- ✅ **フロントエンドのユーザー表示文字列はすべて翻訳キー（useLanguage の t()）を使用する**

#### DB操作を含むタスクの場合（必須確認項目）

**`.clinerules/development/database.md`を読んだ後、以下を明示的に確認すること：**

1. **Repository層の基本構造**
   - [ ] insertメソッドとupdateメソッドを1つずつ用意する
   - [ ] upsertメソッドは作成しない（Service層で実装）
   - [ ] テーブル型Objectを引数として受け取る

2. **動的SQL構築**
   - [ ] `Object.keys(data)`でカラム名を動的に抽出する
   - [ ] カラムを明示的に列挙しない（`organization_id, project_id, ...`のような記述は避ける）
   - [ ] プレースホルダー（$1, $2, ...）を動的に生成する

3. **upsertロジックの実装場所**
   - [ ] upsertロジックはService層で実装する
   - [ ] 既存レコードを取得 → 存在すればupdate、なければinsert

4. **規約準拠の確認方法**
   - [ ] 実装前に`database.md`の「実装パターン」セクションを熟読する
   - [ ] 規約準拠の実装例と比較する
   - [ ] 不明点があれば実装前にユーザーに質問する

**この確認を省略しないこと。規約違反は後から修正すると工数が倍増します。**

### 5. 実装作業

- 承認された計画書に従って実装
- 進捗をtask_progressパラメータで更新
- 計画からの逸脱が必要な場合は、その都度ユーザーに報告

#### 実装中の規約再確認タイミング

以下のタイミングで、関連規約を再確認すること：

1. **新しい型定義を作成する前**
   - → `.clinerules/development/typescript.md` を確認
   - → 型定義ファイル（`types/`）に作成しているか確認
   - → インライン型定義になっていないか確認

2. **API/関数の引数を定義する前**
   - → インライン型定義になっていないか確認
   - → 既存の型定義を再利用できないか確認

3. **DB操作を実装する前**
   - → `.clinerules/development/database.md` を確認
   - → Repository層を使用しているか確認

4. **長時間タスク（2時間以上）の途中**
   - → 関連規約ファイルを再読み込み
   - → 規約に準拠しているか自己チェック

### 6. 完了報告

- 作業完了後、タスク計画書を更新（実施結果、変更点などを記録）
- attempt_completionで完了を報告

## タスク専用フォルダの作成（重要）

### ルール: タスクごとに専用フォルダを作成

タスクを開始する際は、必ず `docs/tasks/` 配下にタスク専用のフォルダを作成します。

**フォルダ命名規則:**
```
docs/tasks/YYYYMMDD_HHMM_<タスク名>/
```

**例:**
```
docs/tasks/20251216_1830_ログイン機能改修/
docs/tasks/20251216_1900_API認証強化/
```

### タスク関連ドキュメントの配置

タスクで作成するすべてのドキュメント（計画書、調査レポート、設計書など）は、このフォルダ内に配置します。

**例:**
```
docs/tasks/20251216_1830_ログイン機能改修/
├── PLAN.md                    # タスク計画書
├── research.md                # 調査結果
├── design.md                  # 設計書
└── implementation_notes.md    # 実装メモ
```

### 重要な制約: docs/tasks/ 直下の .md ファイルは参照しない

**禁止事項:**
❌ `docs/tasks/` 直下の `.md` ファイルを参照しない
❌ 他のタスクフォルダ内のファイルを参照しない

**理由:**
- タスク間の干渉を防ぐ
- 関連性のない情報による混乱を避ける
- タスクの独立性を保つ

**例外:**
✅ `.clinerules/` 配下の規約ファイルは常に参照可能
✅ `docs/design/` など、プロジェクト全体の設計ドキュメントは参照可能

## タスク計画書のファイル命名規則

タスク専用フォルダ内に `PLAN.md` として作成します。

**ファイルパス:**
```
docs/tasks/YYYYMMDD_HHMM_<タスク名>/PLAN.md
```

**重要:** YYYYMMDDは**現在の日付**を使用してください（例: 2025年12月16日の場合は20251216）

**例:**
```
docs/tasks/20251216_1830_ログイン機能改修/PLAN.md
docs/tasks/20251216_1900_API認証強化/PLAN.md
```

## タスク計画書作成時の注意点

### write_fileツールの制約

**重要**: 完全なテンプレート（約250行）を一度に`write_file`で作成すると、XMLパースエラーが発生します。

**原因**:
- 大規模: 約250行、5,000文字以上
- 複雑な構造: 12セクション、ネストされた見出し、マークダウンテーブル
- 多数のチェックリスト（`- [ ]` が20個以上）

**推奨アプローチ**:

#### 方法1: 段階的作成（推奨）
1. **最初は最小限の構成で作成**（メタデータ+概要のみ）
2. **必要に応じて`replace_in_file`でセクションを追記**

#### 方法2: 簡易版テンプレート使用
小規模〜中規模タスクには以下の簡易版テンプレートを使用：

```markdown
# タスク計画書: [タスク名]

## メタデータ
- **作成日時**: YYYY-MM-DD HH:MM
- **タスクID**: [ID]
- **優先度**: [高/中/低]
- **推定工数**: [時間]

## タスク概要
[説明]

## 目的と期待される成果
- [ ] 成果1
- [ ] 成果2

## 実装ステップ
- [ ] ステップ1
- [ ] ステップ2
- [ ] ステップ3

## 変更ファイル
1. `path/to/file1.ts` - 変更内容
2. `path/to/file2.tsx` - 変更内容

## リスク
| リスク | 対策 |
|--------|------|
| リスク1 | 対策1 |

## テスト計画
- [ ] テスト1
- [ ] テスト2

## 承認記録
- **承認日時**: YYYY-MM-DD HH:MM
```

詳細は [file-writing.md](../development/file-writing.md#workflow実行時の特有の問題) を参照してください。

## 例外ケース

以下の場合は、簡易的な計画書でも可とします：

### 1. 緊急バグ修正（ホットフィックス）
- 本番環境で重大なバグが発生し、即座の対応が必要な場合
- 最小限の情報（概要、修正内容、影響範囲）のみで承認を求める

### 2. ドキュメント修正
- タイポ修正や軽微なドキュメント更新
- 変更内容が明確で影響範囲が限定的な場合

### 3. 設定ファイルの軽微な変更
- 環境変数の追加や設定値の調整
- リスクが低く、変更内容が明確な場合

**ただし、これらの場合でも、最低限以下の情報を記録します：**
```markdown
# 簡易タスク記録: [タスク名]

- **日時**: YYYY-MM-DD HH:MM （現在の日時を記入）
- **種類**: [ホットフィックス/ドキュメント修正/設定変更]
- **変更内容**: [簡潔な説明]
- **変更ファイル**: [ファイルリスト]
- **承認**: [承認済み/承認不要]
```

## ベストプラクティス

### DO（推奨）
✅ タスクを受け取ったらすぐに専用フォルダを作成する
✅ すべてのタスク関連ドキュメントを専用フォルダ内に配置する
✅ 実装ステップは具体的かつ測定可能にする
✅ リスクは楽観的に見積もらない
✅ 計画書は実施後も更新して記録を残す
✅ 複雑なタスクは小さく分割する
✅ ユーザーの承認を得てから作業を開始する
✅ 計画からの逸脱があれば報告する

### DON'T（非推奨）
❌ タスク専用フォルダを作成せずに docs/tasks/ 直下にファイルを作成しない
❌ docs/tasks/ 直下の .md ファイルを参照しない
❌ 他のタスクフォルダ内のファイルを参照しない
❌ 計画書なしで実装を開始しない
❌ 承認前に勝手に作業を進めない
❌ 抽象的な計画書を作成しない
❌ リスクを過小評価しない
❌ 計画書を放置して更新しない
❌ 影響範囲を軽視しない

## まとめ

このワークフローは、以下を実現するために設計されています：

1. **透明性**: ユーザーは常に何が行われるかを事前に把握できる
2. **品質保証**: 計画段階で問題を発見・解決できる
3. **記録管理**: 実施した作業の記録が残る
4. **リスク管理**: 事前にリスクを特定し対策を講じる
5. **効率化**: 承認後はスムーズに実装できる

すべてのタスク実行は、このワークフローに従って進めてください。

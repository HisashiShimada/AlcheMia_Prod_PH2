# タスク実行ワークフロー規約

## 概要

Clineがタスクを実行する際は、必ず事前にタスク計画書を`docs/cline_archives/`に作成し、ユーザーの承認を得てから作業を開始する必要があります。

## ワークフロー

### 1. タスク受領

ユーザーからタスクを受け取ったら、以下の手順で進めます。

### 2. タスク計画書の作成

**必須ステップ:**

1. `docs/cline_archives/` ディレクトリにタスク計画書（.mdファイル）を作成
2. タスク計画書には以下の内容を含める：
   - タスクの概要
   - 目的と期待される成果
   - 実装ステップの詳細チェックリスト
   - 影響範囲の分析
   - リスクと対策
   - 必要なファイルの変更リスト
   - テスト計画

3. タスク計画書をユーザーに提示して承認を求める

### 3. ユーザー承認

- ユーザーが計画書を確認し、承認または修正を指示
- 修正が必要な場合は計画書を更新して再提示
- 承認後、作業開始

### 4. 実装作業

- 承認された計画書に従って実装
- 進捗をtask_progressパラメータで更新
- 計画からの逸脱が必要な場合は、その都度ユーザーに報告

### 5. 完了報告

- 作業完了後、タスク計画書を更新（実施結果、変更点などを記録）
- attempt_completionで完了を報告

## タスク計画書のファイル命名規則

```
docs/cline_archives/YYYYMMDD_HHMM_<タスク名>_PLAN.md
```

**重要:** YYYYMMDDは**現在の日付**を使用してください（例: 2025年12月16日の場合は20251216）

**例:**
```
docs/cline_archives/20251216_1830_ログイン機能改修_PLAN.md
docs/cline_archives/20251216_1900_API認証強化_PLAN.md
```

## 例外ケース

以下の場合は、簡易的な計画書でも可とします：

### 1. 緊急バグ修正（ホットフィックス）
- 本番環境で重大なバグが発生し、即座の対応が必要な場合
- 最小限の情報（概要、修正内容、影響範囲）のみで承認を求める

### 2. ドキュメント修正
- タイポ修正や軽微なドキュメント更新
- 変更内容が明確で影響範囲が限定的な場合

### 3. 設定ファイルの軽微な変更
- 環境変数の追加や設定値の調整
- リスクが低く、変更内容が明確な場合

**ただし、これらの場合でも、最低限以下の情報を記録します：**
```markdown
# 簡易タスク記録: [タスク名]

- **日時**: YYYY-MM-DD HH:MM （現在の日時を記入）
- **種類**: [ホットフィックス/ドキュメント修正/設定変更]
- **変更内容**: [簡潔な説明]
- **変更ファイル**: [ファイルリスト]
- **承認**: [承認済み/承認不要]
```

## ベストプラクティス

### DO（推奨）
✅ タスクを受け取ったらすぐに計画書を作成する
✅ 実装ステップは具体的かつ測定可能にする
✅ リスクは楽観的に見積もらない
✅ 計画書は実施後も更新して記録を残す
✅ 複雑なタスクは小さく分割する
✅ ユーザーの承認を得てから作業を開始する
✅ 計画からの逸脱があれば報告する

### DON'T（非推奨）
❌ 計画書なしで実装を開始しない
❌ 承認前に勝手に作業を進めない
❌ 抽象的な計画書を作成しない
❌ リスクを過小評価しない
❌ 計画書を放置して更新しない
❌ 影響範囲を軽視しない

## まとめ

このワークフローは、以下を実現するために設計されています：

1. **透明性**: ユーザーは常に何が行われるかを事前に把握できる
2. **品質保証**: 計画段階で問題を発見・解決できる
3. **記録管理**: 実施した作業の記録が残る
4. **リスク管理**: 事前にリスクを特定し対策を講じる
5. **効率化**: 承認後はスムーズに実装できる

すべてのタスク実行は、このワークフローに従って進めてください。

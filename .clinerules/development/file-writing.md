# ファイル書き込み規約

## 概要

このドキュメントは、Clineのwrite_fileツールとreplace_in_fileツールの使い分け、および大規模ファイル書き込み時のベストプラクティスを定義します。

## write_fileツールの制約

### 発生するエラー

大規模な内容をwrite_fileツールで書き込むと、以下のエラーが発生することがあります：

```
[ERROR] You did not use a tool in your previous response!
```

### エラー原因の分析

**実例からの調査結果**:
- **requirements.md** (約11,000文字): ✅ 書き込み成功
- **design.md** (約4,500文字): ❌ エラー発生
- **research.md** (約3,000文字): ❌ エラー発生

この結果から、単純なファイルサイズだけでなく、**内容の複雑さ**がエラーの原因であることが判明しました。

### エラー発生の要因

1. **コードブロックの量**: SQLクエリ、TypeScriptコード等が大量に含まれる
2. **特殊文字の多さ**: XMLタグ(`<`, `>`)、バッククォート、特殊記号
3. **構造の複雑さ**: ネストされたコードブロック、マークダウンテーブル
4. **トークン制限**: 出力が長すぎてXMLパースに失敗

## ツールの使い分け基準

### write_fileツールを使用する場合

✅ **推奨ケース:**
- 新規ファイルの作成
- 小〜中規模のファイル（目安: 8,000文字以下または800行以下）
- シンプルなテキストコンテンツ
- コードブロックが少ない（全体の20%未満）
- 全体を一度に書き換える場合

### replace_in_fileツールを使用する場合

✅ **推奨ケース:**
- 既存ファイルの部分更新
- 大規模ファイルへの内容追加
- コードブロックが多いファイル
- 特殊文字が多いファイル
- 段階的にコンテンツを追加する場合

## 大規模ファイル書き込みワークフロー

### Step 1: 初期ファイルの作成

小規模な初期コンテンツ（ヘッダー、目次等）でファイルを作成します。

### Step 2: 段階的なコンテンツ追加

replace_in_fileツールで内容を段階的に追記します。

## 具体的な閾値と基準

### 文字数・行数の目安

| 内容の種類 | write_file推奨上限 | 推奨アプローチ |
|-----------|------------------|--------------|
| プレーンテキスト | 10,000文字 / 1,000行 | write_file |
| コードブロック少量 | 8,000文字 / 800行 | write_file |
| コードブロック多量 | 5,000文字 / 500行 | 段階的追記 |
| 複雑な構造 | 5,000文字 / 500行 | 段階的追記 |

### コンテンツの複雑さ評価

**低複雑度（write_file可）:**
- マークダウン本文のみ
- シンプルなリスト
- 基本的な見出し構造

**中複雑度（注意が必要）:**
- 少量のコードブロック（1-3個）
- シンプルなマークダウンテーブル
- 基本的な特殊文字

**高複雑度（段階的追記推奨）:**
- 大量のコードブロック（4個以上）
- ネストされた構造
- XMLタグや特殊文字が多い
- 長いSQLクエリやTypeScriptコード

## ツール実行の基本ルール（重要）

### 必須事項：ツール実行後は必ずユーザーの確認を待つ

**ルール**: 各write_file/replace_in_file実行後、**必ずユーザーの結果確認を待ってから**次のツールを呼び出すこと。

**理由**:
- ファイル作成/更新が成功したか確認が必要
- エラーが発生した場合、即座に対処できる
- 複数ファイルの同時作成は失敗リスクが高い
- ユーザーは各ステップの進行状況を把握できる

### 実例：2026-01-28の失敗ケース

**何が起きたか**:
```
1. write_file(research.md) 呼び出し
   ↓ ユーザー確認を待たずに
2. write_file(design.md) 呼び出し（大規模コンテンツ）
   ↓ エラー発生
3. research.mdは作成されず、design.mdも失敗
```

**べきだったこと**:
```
1. write_file(research.md) 呼び出し
   ↓ ✅ ユーザーの成功確認を待つ
2. write_file(design.md - 初期版のみ) 呼び出し
   ↓ ✅ ユーザーの成功確認を待つ
3. replace_in_file(design.md - セクション追加) 呼び出し
   ↓ ✅ ユーザーの成功確認を待つ
4. 以下、繰り返し
```

### 複数ファイル作成時の推奨フロー

**DO（推奨）**:
```typescript
// ❌ 間違った例
write_file("research.md");
write_file("design.md");      // 前のファイル完了を待っていない
write_file("spec.json");       // 複数ファイルを連続実行

// ✅ 正しい例
write_file("research.md");
// → ユーザー確認待ち → 成功確認
write_file("design.md");
// → ユーザー確認待ち → 成功確認
write_file("spec.json");
// → ユーザー確認待ち → 成功確認
```

### 大規模ファイル作成時の推奨フロー

**DO（推奨）**:
```typescript
// ✅ 段階的作成
// Step 1: 初期ファイル作成（ヘッダー+目次のみ）
write_file("design.md", "小規模な初期コンテンツ");
// → ユーザー確認待ち → 成功確認

// Step 2: セクション1追加
replace_in_file("design.md", "セクション1を追加");
// → ユーザー確認待ち → 成功確認

// Step 3: セクション2追加
replace_in_file("design.md", "セクション2を追加");
// → ユーザー確認待ち → 成功確認

// 以下、繰り返し
```

**DON'T（非推奨）**:
```typescript
// ❌ 一度に大規模コンテンツを書き込む
write_file("design.md", "5,000行の完全なコンテンツ"); // 失敗リスク高
```

## ベストプラクティス

### DO（推奨）

✅ **各ツール実行後、必ずユーザーの確認を待つ（最重要）**
✅ コンテンツの複雑さを事前に評価する
✅ 複雑な内容は段階的に追記する
✅ 各セクションごとにreplace_in_fileを使用
✅ 小さなチャンクに分割して追記
✅ ファイル作成は1つずつ完成させてから次に進む
✅ 大規模ファイル（1,000行超）は必ず段階的に作成
✅ 追記後にユーザーの確認を待つ

### DON'T（非推奨）

❌ **ツール実行結果を待たずに次のツールを呼び出す（最も危険）**
❌ **複数の大規模ファイルを同時に作成しようとする**
❌ 大量のコードブロックを一度に書き込まない
❌ 複雑な構造を一度に作成しない
❌ エラーが発生したら同じ方法を繰り返さない
❌ ファイルサイズだけで判断しない
❌ ユーザー確認なしで次のステップに進まない

## トラブルシューティング

### 問題: write_fileでエラーが発生する

**症状**: `[ERROR] You did not use a tool in your previous response!`

**原因**:
- コードブロックが多すぎる
- 特殊文字が多すぎる
- 構造が複雑すぎる

**解決策**:
1. ファイルをシンプルな初期バージョンで作成
2. replace_in_fileで段階的にセクションを追加
3. 各追加後にユーザーの確認を待つ

### 問題: replace_in_fileでマッチしない

**症状**: `The SEARCH block does not match anything in the file`

**原因**:
- SEARCHブロックの内容が正確にファイルと一致していない
- 自動フォーマットによる変更

**解決策**:
1. ファイルを再読み込みして最新状態を確認
2. final_file_contentを参照して正確なSEARCHブロックを作成
3. 小さなSEARCHブロックを使用

## workflow実行時の特有の問題

### spec-design / spec-tasksワークフロー実行時の注意

**問題**: spec-designワークフローでdesign.mdを生成する際、テンプレートが非常に大規模（約400行）でwrite_fileで一度に作成すると失敗する

**design.mdテンプレートの特徴**:
- 大規模: 約400行、10,000文字以上
- 複雑な構造: 10+セクション、多階層の見出し
- 大量のコードブロック: TypeScript interface定義、Mermaidダイアグラム、JSONスキーマ等
- 多数のマークダウンテーブル
- 特殊文字が多い: `|`, `:`, `-`, バッククォート、XMLタグ等

→ **「高複雑度」に該当し、write_fileの推奨上限を大幅に超える**

#### 推奨される実装パターン

**Step 1: 最小限の初期ファイル作成（Overview + Architecture概要のみ）**
```markdown
# Design Document: [Feature Name]

## Overview
[2-3 paragraphs]

### Goals
- Goal 1
- Goal 2

### Non-Goals
- Non-goal 1

## Architecture
[Brief summary]

## Components and Interfaces
（後で追記）

## Data Models
（後で追記）

## Error Handling
（後で追記）

## Testing Strategy
（後で追記）
```

**Step 2: セクションごとに段階的追記**
```
1. write_file(design.md) - 最小限の初期版作成
   ↓ ユーザー確認待ち
2. replace_in_file - Architecture詳細を追加
   ↓ ユーザー確認待ち
3. replace_in_file - Components and Interfaces を追加
   ↓ ユーザー確認待ち
4. replace_in_file - Data Models を追加
   ↓ ユーザー確認待ち
5. replace_in_file - Error Handling を追加
   ↓ ユーザー確認待ち
6. replace_in_file - Testing Strategy を追加
   ↓ ユーザー確認待ち
```

**Step 3: research.mdは別タイミングで作成**
- design.md完成後、**必ずユーザー確認を待ってから** research.mdを作成
- research.mdは中規模（約80行）なので、一度にwrite_fileで作成可能

#### spec-tasksワークフローの場合

**tasks.mdテンプレートの特徴**:
- 小規模: 約30行
- シンプルな構造: チェックリストとテンプレート例のみ
- コードブロックが少ない

→ **一度にwrite_fileで作成可能**

ただし、生成されるtasks.mdの内容（実際のタスクリスト）が大規模になる場合は、段階的作成を検討してください。

#### 重要なルール

1. **design.mdは必ず段階的作成**（テンプレートが400行と非常に大規模なため）
2. **各ファイル作成後、必ずユーザー確認を待つ**
3. **複数ファイルを同時に作成しない**（design.md + research.mdを連続実行しない）
4. **セクション単位でreplace_in_fileを使用**（一度に大量のコンテンツを追加しない）

### タスク計画書作成時の注意

**問題**: workflow.mdのタスク計画書テンプレート（約250行）をwrite_fileで一度に作成しようとすると失敗する

**原因**:
- 大規模: 約250行、5,000文字以上
- 複雑な構造: 12セクション、ネストされた見出し
- 多数のマークダウンテーブル（リスク管理表など）
- 多数のチェックリスト（`- [ ]` が20個以上）
- コードブロック（テンプレート例示用）

→ **「高複雑度」に該当し、write_fileの推奨上限を超える**

### 解決策1: 段階的作成（推奨）

**Step 1: 最小限の初期ファイル作成**
```markdown
# タスク計画書: [タスク名]

## メタデータ
- **作成日時**: YYYY-MM-DD HH:MM
- **タスクID**: [タスクを識別する短い名前]
- **優先度**: [高/中/低]

## 1. タスク概要
[タスクの簡潔な説明]

## 2. 実装ステップ
（後で追記）

## 3. 変更ファイル
（後で追記）
```

**Step 2: セクションごとに追記**
- `replace_in_file`で順次セクションを追加
- 各追加後にユーザー確認を待つ

### 解決策2: 簡易版テンプレート使用

小規模〜中規模タスク用（100行未満）：

```markdown
# タスク計画書: [タスク名]

## メタデータ
- **作成日時**: YYYY-MM-DD HH:MM
- **タスクID**: [ID]
- **優先度**: [高/中/低]
- **推定工数**: [時間]

## タスク概要
[説明]

## 目的と期待される成果
- [ ] 成果1
- [ ] 成果2

## 実装ステップ
- [ ] ステップ1
- [ ] ステップ2
- [ ] ステップ3

## 変更ファイル
1. `path/to/file1.ts` - 変更内容
2. `path/to/file2.tsx` - 変更内容

## リスク
| リスク | 対策 |
|--------|------|
| リスク1 | 対策1 |

## テスト計画
- [ ] テスト1
- [ ] テスト2

## 承認記録
- **承認日時**: YYYY-MM-DD HH:MM
```

### 解決策3: 外部ファイル参照

完全なテンプレートは`.clinerules/core/workflow.md`を参照：

```markdown
# タスク計画書: [タスク名]

※完全なテンプレートは .clinerules/core/workflow.md を参照

## （最小限の情報のみ記載）
...
```

### 推奨フロー

```
タスク受領
  ↓
【write_file】簡易計画書を作成
  - メタデータ
  - タスク概要
  - 主要ステップ（3-5個）
  - 変更ファイル
  ↓
ユーザー承認
  ↓
【replace_in_file】必要に応じて詳細追記
  - 技術詳細
  - リスク表
  - テスト計画
  ↓
実装開始
```

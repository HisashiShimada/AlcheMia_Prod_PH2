# ドキュメント構造ガイドライン

## 概要

このガイドラインは、MaiMLシステムの設計書・仕様書の構造と分割ルールを定義します。関心事の分離原則に基づき、保守性と再利用性を確保します。

## ディレクトリ構造

```
docs/
├── design/                      # 設計書（メインドキュメント）
│   ├── ui/                      # UI設計書（画面単位）
│   │   ├── ui_*.md              # 各画面のUI設計書
│   │   └── technical/           # UI技術仕様書（画面単位）
│   │        └── ui_technical_*.md # 各画面のUI技術仕様書
│   │
│   ├── api/                     # API仕様書（機能ドメイン単位）
│   │   └── api_*.md             # 機能ドメインごとのAPI仕様
│   │
│   ├── security/                # セキュリティ仕様書（横断的関心事）
│   │   └── security_*.md        # セキュリティ関連の仕様書
│   │
│   └── db/                      # データベース設計
│       └── db_*.md              # データベーススキーマ、ER図など
│
├── dev/                         # 開発関連ドキュメント
│   └── dev-guide/               # 開発ガイド（機能単位）
│       └── dev_*.md             # 開発・デバッグガイド
│
├── cline_archive/               # 開発過程のドキュメント（アーカイブ）
│   └── *.md                     # 実装完了報告、調査結果、修正記録など
│
├── images/                      # ドキュメント用画像ファイル
│   └── *.png, *.jpg, *.svg      # スクリーンショット、図表など
│
└── README.md                    # ドキュメント索引（未作成の場合は作成推奨）
```

## ファイル分割ルール

### 1. UI設計書（docs/design/ui/）

#### 命名規則
- `ui_<機能名>.md` - UI設計とUX仕様
- `ui_technical_<機能名>.md` - 技術実装仕様（オプション）

#### 内容
- **ui_<機能名>.md**（メインドキュメント）
  - 画面概要、利用権限
  - コントロール一覧、入出力項目
  - イベント、画面遷移
  - 表示仕様（レイアウト、スタイリング）
  - 使用コンポーネント一覧
  - エラーチェック
  
- **ui_technical_<機能名>.md**（オプション、複雑な画面のみ）
  - コンポーネント実装詳細
  - 状態管理の実装
  - カスタムフックの実装
  - エラーハンドリング実装

#### 分割判断基準
- 基本的に1画面1ファイル（ui_*.md）
- 実装が複雑（1000行超）な場合のみ技術仕様を分離
- API仕様はdocs/design/api/を参照リンクで対応

### 2. API仕様書（docs/design/api/）

#### 命名規則
- `api_<機能ドメイン>.md`

#### 機能ドメインの定義
API仕様書は**機能ドメイン（ビジネス機能）単位**で1ファイルにまとめます。

**標準的な機能ドメイン例:**
- `api_auth.md` - 認証・セッション管理
- `api_files.md` - ファイル管理
- `api_experiments.md` - 実験記録管理
- `api_maiml.md` - MAIML編集機能
- `api_organizations.md` - 組織管理
- `api_users.md` - ユーザー管理
- `api_workers.md` - ワーカー管理
- `api_admin.md` - システム管理

#### 内容
各API仕様書には以下を含めます：
- 概要（機能ドメインの説明）
- エンドポイント一覧
- 各エンドポイントの詳細仕様
  - HTTPメソッドとパス
  - リクエスト仕様（パラメータ、ボディ）
  - レスポンス仕様（成功時、エラー時）
  - 認証・権限要件
- エラーコード一覧
- 使用するデータベーステーブル
- 実装ファイルパス

#### 分割判断基準

✅ **1つのファイルにまとめる条件:**
- 同じビジネス機能に属するエンドポイント群
- データベーステーブルを共有するエンドポイント群
- ユーザーストーリーが関連するエンドポイント群
- 合計200〜400行程度に収まる規模

❌ **避けるべき分割:**
- エンドポイント単位での分割（細かすぎ）
- HTTPメソッド単位での分割（意味がない）
- ユーザーロール単位での分割（横断的関心事）

⚠️ **サブディレクトリ化を検討:**
- 1つの機能ドメインが1000行を超える場合
- ただし、基本はフラットな構造を維持

#### API仕様書の例

**api_auth.md に含まれるエンドポイント:**
```
POST   /api/auth/login           # ログイン
POST   /api/auth/logout          # ログアウト  
GET    /api/auth/verify-session  # セッション検証
POST   /api/auth/refresh-token   # トークン更新
GET    /api/auth/me              # 現在のユーザー情報
GET    /api/auth/admin-audit-log # 監査ログ（Admin用）
```

これらは全て「認証」という1つの機能ドメインなので、1ファイルにまとめます。

### 3. セキュリティ仕様書（docs/design/security/）

#### 命名規則
- `security_<関心事>.md`

#### 内容
横断的なセキュリティ関心事を記述：
- `security_authentication.md` - 認証方式、パスワードポリシー
- `security_authorization.md` - 認可、RBAC
- `security_data_isolation.md` - マルチテナント分離
- `security_encryption.md` - 暗号化仕様
- `security_audit.md` - 監査ログ仕様

#### 分割判断基準
- セキュリティドメインごとに1ファイル
- 複数の機能にまたがるセキュリティ要件を集約
- 特定のAPI仕様書から参照される

### 4. データベース設計（docs/design/db/）

#### 命名規則
- `db_<トピック>.md`

#### 内容
データベース設計に関する情報：
- テーブル定義（DDL）
- ER図
- インデックス設計
- マイグレーションスクリプト
- データベース正規化の説明

#### 分割判断基準
- 機能ドメインごとに1ファイル（大規模な場合）
- または全体を1ファイルにまとめる（中小規模な場合）
- 500〜1000行以内に収める

### 5. 開発ガイド（docs/dev/dev-guide/）

#### 命名規則
- `dev_<機能>.md`

#### 内容
開発・テスト・デバッグに関する実践的な情報：
- ローカル開発環境セットアップ
- テストアカウント情報
- デバッグ方法
- テスト実行方法
- トラブルシューティング

#### 分割判断基準
- 機能単位で1ファイル
- UI設計書やAPI仕様書から参照される
- 500行以内に収める

### 6. 開発過程ドキュメント（docs/cline_archive/）

#### 命名規則
- `<機能名>_<状態>.md`
- 例: `PETRI_NET_EDITOR_PHASE3_COMPLETE.md`
- 例: `MULTITENANT_S3_ACCESS_AUDIT_REPORT.md`

#### 内容
開発過程で作成されたドキュメント：
- 実装完了報告（*_COMPLETE.md）
- 調査結果（*_ANALYSIS.md, *_DIAGNOSIS.md）
- 実装計画（*_PLAN.md, *_IMPLEMENTATION_PLAN.md）
- テストガイド（*_TEST_GUIDE.md）
- デプロイメントガイド（*_DEPLOYMENT_GUIDE.md）

#### 管理方針
- **アーカイブ専用**: 完了した作業の記録を保管
- **参照用**: 過去の実装や意思決定を振り返るため
- **新規作成は非推奨**: 新しいドキュメントはdesign/やdev-guide/に作成
- **削除は不可**: 開発履歴として保存

### 7. 画像ファイル（docs/images/）

#### 内容
ドキュメントで使用する画像：
- UI設計書のスクリーンショット
- システムアーキテクチャ図
- ER図
- フローチャート、シーケンス図

#### 命名規則
- `<関連ドキュメント名>_<説明>.png`
- 例: `ui_login_screen.png`
- 例: `db_er_diagram.svg`

## ドキュメント間の相互参照

### 相互参照の原則
各ドキュメントの冒頭に「関連ドキュメント」セクションを設け、相互参照を明示します。

### 参照の例

**UI設計書から他のドキュメントへ:**
```markdown
# ログイン画面 UI設計書

## 関連ドキュメント
- [技術仕様](technical/ui_technical_login.md)
- [認証API仕様](../../design/api/api_auth.md)
- [認証セキュリティ仕様](../../design/security/security_authentication.md)
- [開発ガイド](../../dev/dev-guide/dev_authentication.md)
```

**API仕様書から他のドキュメントへ:**
```markdown
# 認証API仕様書

## 関連ドキュメント
- [UI設計: ログイン画面](../ui/ui_login.md)
- [UI設計: 組織選択画面](../ui/ui_organization_selector.md)
- [セキュリティ仕様](../security/security_authentication.md)
- [開発ガイド](../../dev/dev-guide/dev_authentication.md)
```

### API仕様の参照方法

UI設計書内でAPI仕様を記述する場合：

```markdown
## API仕様

詳細は [認証API仕様書](../../design/api/api_auth.md) を参照してください。

### このUI画面で使用するAPI
- POST /api/auth/login - ログイン処理
- GET /api/auth/verify-session - セッション検証

（必要に応じて簡単な概要のみ記載）
```

## ファイルサイズガイドライン

### 分割タイミング
- 複数の関心事が混在している場合は即座に分割
- 保守性が低下していると感じた場合は分割を検討

## メタデータ

各ドキュメントの先頭にメタデータを記載します：

```markdown
---
title: ログイン画面UI設計書
category: UI設計
version: 1.0.0
last_updated: 2024-12-08
author: Development Team
tags: [authentication, login, ui, phase3]
---
```

**メタデータフィールドの説明:**
- `title`: ドキュメントのタイトル
- `category`: ドキュメントの種類（UI設計、API仕様、セキュリティ仕様など）
- `version`: バージョン番号（Semantic Versioning）
- `last_updated`: 最終更新日（YYYY-MM-DD形式）
- `author`: 作成者/担当チーム
- `tags`: 検索用タグ（配列形式）

## バージョン管理

### バージョン番号規則
- メジャー変更（画面/API の大幅な変更）: 1.0.0 → 2.0.0
- マイナー変更（機能追加、仕様変更）: 1.0.0 → 1.1.0
- パッチ変更（誤記修正、補足追加）: 1.0.0 → 1.0.1

### 変更履歴
各ドキュメント末尾に変更履歴を記載：

```markdown
## 変更履歴

| バージョン | 日付 | 変更内容 | 担当者 |
|-----------|------|----------|--------|
| 1.0.0 | 2024-12-08 | 初版作成 | Development Team |
| 1.1.0 | 2024-12-15 | MFA機能追加 | Security Team |
```

## ベストプラクティス

### DO（推奨）
✅ 関心事ごとにドキュメントを分離する
✅ 機能ドメイン単位でAPI仕様をまとめる
✅ 相互参照を活用して重複を避ける
✅ メタデータとバージョン情報を記載する
✅ 具体的な例とサンプルコードを含める
✅ 画像やダイアグラムを活用する
✅ 新しいドキュメントはdesign/またはdev/配下に作成する
✅ 画像ファイルはdocs/images/に配置する
✅ 相対パスで画像を参照する（例: `![画面](../../images/ui_login_screen.png)`）

### DON'T（非推奨）
❌ 1つのファイルに全てを詰め込む
❌ エンドポイント単位でAPI仕様を分割する
❌ 同じ内容を複数ファイルにコピー&ペーストする
❌ 関連ドキュメントへのリンクを省略する
❌ 技術用語の説明なしに専門用語を使う
❌ 古い情報を放置する
❌ cline_archive/に新しいドキュメントを作成する
❌ ドキュメント内に画像をBase64エンコードで埋め込む

## まとめ

このガイドラインに従うことで：
- **保守性**: 変更対象を素早く特定できる
- **再利用性**: API仕様やセキュリティ仕様を複数画面で参照できる
- **協業性**: UI設計者、バックエンド開発者、セキュリティチームがそれぞれのドキュメントに集中できる
- **スケーラビリティ**: 新機能追加時も同じ構造を適用できる
- **検索性**: 機能名や関心事でドキュメントを特定しやすい

これらの原則を守り、長期的に保守可能なドキュメントを作成しましょう。

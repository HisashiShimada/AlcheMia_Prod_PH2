## 5. 技術的詳細

### 修正前のミドルウェアチェーン
```typescript
authMiddleware → [バリデーションルール] → controller (❌ handleValidationErrorsなし)
```

### 修正後のミドルウェアチェーン（規約準拠）
```typescript
authMiddleware → [バリデーションルール] → handleValidationErrors → controller
```

### バリデーション処理の責務分離

**DO（推奨）:**
- ✅ ルート層: express-validatorでバリデーションルールを定義
- ✅ ミドルウェア層: handleValidationErrorsで統一的なエラーレスポンスを返却
- ✅ コントローラー層: バリデーション済みパラメータを使用してビジネスロジックに集中

**DON'T（非推奨）:**
- ❌ コントローラー内で `validationResult()` を使用しない
- ❌ コントローラー内でリクエストパラメータの形式チェックをしない

### API仕様書（11番API）の要件

**エンドポイント**: `GET /api/v1/projects/:projectName/worker-instructions`

**パラメータバリデーション:**
- `projectName` (path): 必須、1-255文字
- `projectId` (query): オプショナル、UUID形式

### 参考: 他のエンドポイントの実装パターン

承認依頼API（`POST /api/v1/projects/:projectId/approval-request`）の実装が参考になります：

```typescript
router.post(
  '/:projectId/approval-request',
  authMiddleware,
  tenantIsolation,
  [
    param('projectId')
      .isUUID()
      .withMessage('projectIdはUUID形式である必要があります'),
    body('comment')
      .optional()
      .isLength({ max: 1000 })
      .withMessage('commentは1000文字以内である必要があります'),
  ],
  handleValidationErrors,  // ✅ ミドルウェアで処理
  projectController.requestApproval
);
```

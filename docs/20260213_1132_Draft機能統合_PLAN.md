### アーキテクチャ上の考慮事項

#### 1. レイヤードアーキテクチャの採用
- **Repository層**: データベースアクセス専門（新規作成）
  - **命名規則**: テーブル単位（maiml_draftsテーブル → maimlDraftsRepository.ts）
  - maiml_draftsテーブルへのCRUD操作
  - getPool()を使用したDB接続
  - Parameterized Queries使用
  - organization_id + user_idによる二重フィルタ
  
- **Controller層**: ビジネスロジック + HTTPハンドリング
  - Repositoryの呼び出し
  - リクエスト/レスポンスの変換
  - エラーハンドリング
  - 孤立アークのクリーニング処理
  
- **Route層**: エンドポイント定義
  - バリデーション
  - 認証ミドルウェア
  - Controllerへのルーティング

#### 2. TypeScript移行
- CommonJS（require）→ ES Module（import）
- any型を避け、明示的な型定義を使用
- async/awaitを使用

#### 2. バリデーション
express-validatorを使用:
```typescript
[
  body('draftKey').notEmpty().isString(),
  body('draftName').notEmpty().isString(),
  body('organizationId').notEmpty().isString(),
  body('nodes').optional().isArray(),
  body('arcs').optional().isArray(),
  body('templates').optional().isObject(),
  body('documentData').optional().isObject(),
]
```

#### 3. レスポンス形式の統一
既存のmaimlControllerと同様の形式:
```typescript
return res.json({
  success: true,
  draft: savedDraft,
  message: 'Draft saved successfully'
});
```

### TypeScript型定義の方針

**既存の型定義を活用（frontend/backend共通）:**

```typescript
// backend/src/types/editor.ts と frontend/src/types/editor.ts
// 既に以下の型定義が存在します（両方同一内容）

// ✅ 既存の型定義（そのまま使用）
export interface Draft {
  draft_key: string;
  draft_name: string;
  original_file_key?: string;
  last_saved_at: string;
  nodes?: Node<NodeData>[];
  edges?: Edge<EdgeData>[];
  templates?: Template[];
  documentData?: DocumentData;
}

export interface EditState {
  fileName: string;
  nodes: Node<NodeData>[];
  edges: Edge<EdgeData>[];
  templates?: Template[];
  documentData?: DocumentData;
}

export interface DraftSaveData {
  draftKey: string;
  draftName: string;
  originalFileKey?: string;
  nodes: Node<NodeData>[];
  edges: Edge<EdgeData>[];
  templates?: Template[];
  documentData?: DocumentData;
}
```

**拡張が必要な型定義:**

```typescript
// backend/src/types/editor.ts に追加（DB返却値用）

/**
 * Draft情報の型定義（拡張版）
 * DB（maiml_drafts）から返却される完全な情報を含む
 */
export interface DraftWithMeta extends Draft {
  id?: number;
  user_id?: string;
  organization_id?: string;
  node_count?: number;
  arc_count?: number;
  template_count?: number;
  created_at?: string;
  arcs?: Arc[]; // 後方互換性のため（edges → arcs変換用）
}

/**
 * Draft一覧取得のレスポンス型
 */
export interface DraftListResponse {
  success: boolean;
  drafts: DraftWithMeta[];
  count: number;
}

/**
 * Draft保存のレスポンス型
 */
export interface DraftSaveResponse {
  success: boolean;
  draft: DraftWithMeta;
  message?: string;
}
```

**方針:**
1. フロントエンドとバックエンドで同じeditor.ts型定義を共有
2. 既存のDraft, EditState, DraftSaveDataをそのまま使用
3. DB返却値用にDraftWithMetaを追加（オプショナルプロパティで拡張）
4. 新規の型定義は最小限に抑える

### フロントエンド側の現状（変更対象）

**useDraftManager.ts の現在のAPIエンドポイント:**
```typescript
// Draft一覧取得
GET /api/s3/drafts?userId=${userId}&organizationId=${orgId}

// Draft保存
POST /api/s3/drafts/save

// Draft削除
DELETE /api/s3/drafts/${draftKey}?userId=${userId}&organizationId=${orgId}
```

**変更後:**
```typescript
// Draft一覧取得（userIdはバックエンドでJWTから取得）
GET /api/v1/maiml/draft?organizationId=${orgId}

// Draft保存
POST /api/v1/maiml/draft/save

// Draft削除
DELETE /api/v1/maiml/draft/${draftKey}?organizationId=${orgId}
```

**注意事項:**
- フロントエンドではJWT認証があるため、userIdはクエリパラメータから削除可能
- organizationIdはマルチテナント分離のため引き続き必要

### 型定義の共有方針（確定版）

**採用方針: 現状維持（手動同期）**

1. **backend/src/types/editor.ts** はfrontendからコピーされたものなので、既に同期されている
2. 既存のDraft関連型定義（Draft, EditState, DraftSaveData）をそのまま使用
3. バックエンド実装時に不足する型定義があれば、backend/src/types/editor.tsに適宜追加
4. 追加した型定義が将来フロントエンドでも必要になった場合、手動でfrontend側にもコピー

**実装時の注意事項:**
- まず既存の型定義（Draft, EditState, DraftSaveData）で実装を試みる
- DB返却値用の拡張が必要な場合のみ、DraftWithMeta等を追加
- 型の不足や不整合が発生した場合は、その都度調整
- フロントエンドとバックエンドのAPIインターフェース部分は型を手動で合わせる

**利点:**
- シンプルで理解しやすい
- プロジェクト構造を変更する必要がない
- 既存コード（useDraftManager.ts, SaveDialog.tsx等）の変更が不要
- 必要な型定義のみを追加できる（オーバーエンジニアリングを避ける）

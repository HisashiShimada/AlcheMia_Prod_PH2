## 5. 考察

### 問題点の整理

| # | 内容 | 重要度 |
|---|------|--------|
| 1 | **ロール選択肢のロード失敗時の問題** | 🔴 高 |
| 2 | **バックエンド側に roleCd の有効性チェックがない** | 🟡 中 |
| 3 | **ブラウザキャッシュによる古い JS の動作** | 🟡 中 |

#### 問題1: ロール選択肢ロード失敗（最有力な原因）

`loadRoles()` はページ初期表示時に非同期で実行されます。  
APIリクエストが失敗した場合 `roles` は `[]`（空）になります。

- 編集モーダルを開くと `form.setFieldsValue({ roleCd: user.roleCd })` が実行される
- `roles` が空の状態だと、Ant Design の `Select` コンポーネントは現在の値を表示できるが「選択肢にない値」として扱われる可能性がある
- **`{ required: true }` のバリデーションが空選択として誤判定し、バリデーションエラーが発生する可能性がある**

#### 問題2: バックエンドの roleCd 有効性チェックなし

`userService.updateUser()` では `roleCd` の値が実際に存在するロールIDかどうかの検証を行っていません。  
フロントエンドで不正な値が送信された場合に DB エラーが発生する可能性があります。

## 9. 「入力内容に誤りがあります」の発生源特定

### 9.1 このメッセージはフロントバリデーションとは別物

「入力内容に誤りがあります」は `ja.json` のエラーコード **E1003** に対応したメッセージです。

```
E1003 → "入力内容に誤りがあります"（ja.json 2018行目）
```

エラーの伝達経路は以下のとおりです：

```
バックエンド validationMiddleware.ts（handleValidationErrors）
  └─ HTTP 400 + { code: 'E1003' } を返す
        ↓
フロントエンド UserManagement.tsx の catch ブロック
  └─ extractErrorMessage(error, t('userManagement.messages.saveError'))
        ↓ extractErrorCode(error) → 'E1003'
        ↓ mapErrorToMessage('E1003')
        └─ 「入力内容に誤りがあります」をトーストで表示
```

**フォームのインラインバリデーション失敗（ロール未選択等）の場合**は、`handleModalOk` 内の `'errorFields' in error` 判定で早期リターンするため、`message.error()` は呼ばれずトーストは出ません。つまりトーストが出た時点でバックエンド起因のエラーです。

### 9.2 PUT ルートのバリデーション定義（userRoutes.ts 175-203行）

```typescript
// PUT /systemManagement/user/:userId
param('userId').notEmpty().isString().isEmail(),   // パスパラメータ: メール形式必須
body('userName').optional().isString().isLength({ max: 30 }), // 最大30文字
body('departmentCd').optional().isString(),
body('roleCd').optional().isString(),
// body('isActive') ← 定義なし
```

### 9.3 フロントが送信するデータ（UpdateUserRequest）

```typescript
// frontend/src/types/user.ts
interface UpdateUserRequest {
  userName?: string;
  departmentCd?: string;
  roleCd?: string;
  isActive?: boolean;  // ← バックエンドのPUTルートに定義なし
}
```

## 10. E1003「入力内容に誤りがあります」が発生する具体的シナリオ

### 🔴 シナリオA: ユーザー名が30文字超（最有力・再現性高）

| 層 | チェック内容 | 結果 |
|----|-------------|------|
| フロントエンド | `{ required: true }` のみ（文字数制限なし） | **通過してしまう** |
| バックエンド PUT ルート | `body('userName').isLength({ max: 30 })` | **31文字以上で E1003** |

フロントのフォームバリデーションに **文字数制限が存在しない** ため、31文字以上のユーザー名を入力・保存しようとするとバックエンドのバリデーションで弾かれ「入力内容に誤りがあります」が表示されます。これは権限（ロール）の書き換えと直接関係はありませんが、他のフィールドを同時に編集した場合に発生します。

```typescript
// UserManagement.tsx 617-621行目
// ← 現在の状態（max: 30 のチェックなし）
rules={[{ required: true, message: t('userManagement.form.userNameRequired') }]}

// バックエンド userRoutes.ts 186-191行目
body('userName')
  .optional()
  .isString()
  .isLength({ max: 30 })  // ← フロントに対応するチェックなし
```

### 🟡 シナリオB: PUT ルートに isActive のバリデーション定義がない（設計の不整合）

フロントは `isActive: boolean` を PUT リクエストのボディで送信しますが、バックエンドの PUT ルートに `body('isActive')` の定義がありません。

| エンドポイント | isActive の扱い |
|--------------|----------------|
| POST `/user`（新規作成） | `body('isActive').optional().isBoolean()` が定義されている |
| PUT `/user/:userId`（更新） | **`body('isActive')` の定義なし** |
| PATCH `/user/:userId/status`（ステータス変更） | `body('isActive').notEmpty().isBoolean()` が定義されている |

現在は `req.body` がそのままサービス層に渡されるため実際の動作に影響はありませんが、型チェックなしで `isActive` が処理される状態です。

### 🟡 シナリオC: userId の URL エンコード問題（環境依存）

フロントが `encodeURIComponent(userId)` でURLエンコードした値をパスに使用しています。express は通常 `req.params` を自動デコードするため問題ないですが、プロキシやリバースプロキシの設定によってはデコードが二重になり `param('userId').isEmail()` が失敗する可能性があります。

```typescript
// frontend/src/services/userApiService.ts 111行目
const endpoint = `${API_ENDPOINT}/${encodeURIComponent(userId)}`;
// user@example.com → /systemManagement/user/user%40example.com
```

## 12. 本件の最有力原因（追加調査結果）

### 12.1 ロール選択肢の value と form の初期値が「別のフィールド」を参照している

これが今回のエラーの本命です。

**ロール選択肢のロード時（loadRoles / UserManagement.tsx 108行目）**

```typescript
.map((r) => ({
  value: String(r.roleId),   // ← roleId を value として設定
  label: String(r.roleName),
}))
```

**編集時のフォーム初期値セット（handleEdit / 298行目）**

```typescript
form.setFieldsValue({
  roleCd: user.roleCd,    // ← roleCd を value として設定
});
```

`roleId` と `roleCd` は **同じものを指している場合とそうでない場合があります。**

バックエンドの roleRepository.ts（94〜102行目）を見ると：

```typescript
// roleRepository.ts
roleId: row.role_cd,   // ← roleId の実体は DB の role_cd カラム
```

つまり `roleId === role_cd` です。一方 `RoleRecord` 型には `roleId`・`roleCd`・`role` という3つのフィールドが定義されています：

```typescript
// frontend/src/types/roleTypes.ts
export interface RoleRecord {
  roleCd: string;   // ← どこから来るのか？
  roleId: string;   // ← DB の role_cd と一致
  role: string;     // ← DB の role カラム（別物？）
  // ...
}
```

APIレスポンスの内容によっては `r.roleId` と `user.roleCd` が**一致しない**ことになり、フォームに設定された値が Select の選択肢のどれにも一致せず、バリデーションで「未選択」と判定される可能性があります。

**データを調べる際に確認してほしい点：**
- ロール一覧API（`GET /api/v1/systemManagement/role`）のレスポンスで `roleId` と `roleCd` の値を確認
- ユーザー一覧API（`GET /api/v1/systemManagement/user`）のレスポンスで `roleCd` の値を確認
- 両者が一致しているかどうか

### 12.2 departmentCd が null の場合に E1003 が発生する（確実な再現ケース）

今回の報告ユーザー（naoji.danno@aist-solutions.co.jp）が **所属部署未選択のまま**（`departmentCd = null`）保存しようとした場合、確実に E1003 が返ります。

**バックエンド PUT ルートのバリデーション（userRoutes.ts 192-195行目）:**

```typescript
body('departmentCd')
  .optional()      // ← null は通さない（nullable: true がない）
  .isString()
```

express-validator の `.optional()` はデフォルトで `undefined` のみをスキップします。`null` は **`isString()` に渡られて失敗**し E1003 になります。

**フロントが送るリクエストボディの実態：**

```typescript
// UserManagement.tsx 440-444行目
const updateData: UpdateUserRequest = {
  userName: values.userName,
  departmentCd: values.departmentCd,  // ← Select 未選択時は undefined
  roleCd: values.roleCd,
  isActive: values.isActive,
};
```

Ant Design の `Select` で未選択の場合 `undefined` が返るため、現在はエラーにならない可能性が高いです。しかし **`user.departmentCd` が `null`（DBにNULLが入っている）のユーザーを編集**した際、`form.setFieldsValue({ departmentCd: null })` がセットされ、そのまま保存されると `null` が送信されバリデーションエラーになる可能性があります。

```typescript
// handleEdit 298行目
departmentCd: user.departmentCd,  // ← null の場合は null がセットされる
```

今回のユーザーの部署設定がどうなっているかを確認してください。

## 13. 修正対応（2026-08-10 実施）

### 修正した箇所

#### ① バックエンド：`backend/src/routes/userRoutes.ts`

PUT（更新）・POST（新規作成）両ルートの `departmentCd` バリデーションに `{ nullable: true }` を追加。

```typescript
// 修正前
body('departmentCd').optional().isString()

// 修正後
body('departmentCd').optional({ nullable: true }).isString()
```

- POST ルート（148行目）
- PUT ルート（193行目）

#### ② フロントエンド：`frontend/src/components/SystemManagement/UserManagement.tsx`

`handleEdit`・`handleModalOk`（updateData・createData）の3箇所で `departmentCd` の `null → undefined` 変換を追加。

```typescript
// 修正前
departmentCd: user.departmentCd          // null がそのまま渡る

// 修正後
departmentCd: user.departmentCd ?? undefined   // null を undefined に変換
```

- `handleEdit`（297行目）
- `handleModalOk` updateData（442行目）
- `handleModalOk` createData（455行目）

### 修正の考え方

2層で対応することで再発を防ぐ。

| 層 | 修正内容 | 効果 |
|----|---------|------|
| バックエンド（根本対応） | `nullable: true` で `null` を許容 | 万が一 `null` が送信されても弾かない |
| フロントエンド（防御的対応） | `null → undefined` に変換してから送信 | そもそも `null` を送らない |

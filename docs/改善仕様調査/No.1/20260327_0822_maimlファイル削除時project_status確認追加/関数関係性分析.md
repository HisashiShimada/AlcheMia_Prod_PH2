# deleteFolderRecursive 関数の関係性分析

## 📋 概要

プロジェクト削除時に使用される3つの`deleteFolderRecursive`関数の関係性と、`fileAccessService.deleteFolderRecursive`の必要性について説明します。

---

## 🔗 3つの関数の関係性

### 呼び出しフロー

```
projectService.deleteProject
    ↓
    FileAccessService.deleteFolderRecursive
        ↓
        storageService.deleteFolderRecursive
```

---

## 📦 各層の責務

### 1. projectService.deleteProject
**責務**: プロジェクト削除のビジネスロジック

```typescript
// backend/src/services/projectService.ts

async deleteProject(organizationId: string, projectName: string) {
  // 1. DBからプロジェクトと関連データを削除
  await client.query('DELETE FROM project_task_detail WHERE ...');
  await client.query('DELETE FROM project_task WHERE ...');
  await client.query('DELETE FROM project WHERE ...');
  
  // 2. トランザクションコミット
  await client.query('COMMIT');
  
  // 3. ストレージからプロジェクトフォルダを削除
  const fileAccessService = new FileAccessService();
  const deletedFileCount = await fileAccessService.deleteFolderRecursive(
    organizationId,
    `projects/${projectName}`
  );
}
```

**役割**:
- ✅ プロジェクトの存在確認
- ✅ project_maiml_flgのチェック（true の場合は削除不可）
- ✅ DBトランザクション管理
- ✅ 関連テーブルのカスケード削除
- ✅ ストレージ削除の呼び出し（トランザクション外）

---

### 2. fileAccessService.deleteFolderRecursive
**責務**: ストレージとDBメタデータの統合管理

```typescript
// backend/src/services/fileAccessService.ts

async deleteFolderRecursive(organizationId: string, folderPath: string) {
  // 1. フォルダパスのバリデーション
  if (folderPath.includes('..') || folderPath.includes('//')) {
    throw new ValidationError('不正なフォルダパスが検出されました');
  }
  
  // 2. 削除対象のファイル一覧を取得
  const files = await this.storageService.listFiles(organizationId, folderPath);
  const fileKeys = files
    .filter(file => !file.key.endsWith('/'))
    .map(file => file.key);
  
  // 3. storageServiceでストレージから削除
  const deletedCount = await this.storageService.deleteFolderRecursive(
    organizationId,
    folderPath
  );
  
  // 4. DBからfile_metadataを一括論理削除
  if (fileKeys.length > 0) {
    await this.repository.softDeleteBatch(organizationId, fileKeys);
  }
  
  return deletedCount;
}
```

**役割**:
- ✅ パストラバーサル攻撃対策（セキュリティ）
- ✅ ストレージからファイル一覧取得
- ✅ **file_metadataテーブルの論理削除**
- ✅ 統一的なエラーハンドリング（ValidationError, NotFoundError, StorageError）

---

### 3. storageService.deleteFolderRecursive
**責務**: 純粋なストレージ操作（S3/Swift）

```typescript
// backend/src/services/storageService.ts

async deleteFolderRecursive(organizationId: string, folderPath: string) {
  // 1. フォルダ配下のファイル一覧を取得
  const files = await this.listFiles(organizationId, folderPath);
  
  if (!files || files.length === 0) {
    return 0;
  }
  
  // 2. 各ファイルを物理削除
  let deletedCount = 0;
  for (const file of files) {
    if (file.key.endsWith('/')) {
      continue; // フォルダはスキップ
    }
    
    await this.deleteFile(organizationId, relativePath);
    deletedCount++;
  }
  
  return deletedCount;
}
```

**役割**:
- ✅ S3/Swiftからファイル一覧取得
- ✅ 各ファイルの物理削除
- ✅ 削除進捗のログ出力
- ✅ **DBを一切意識しない**（純粋なストレージ操作）

---

## 🎯 fileAccessService.deleteFolderRecursive が必要な理由

### 理由1: **責務の分離（Separation of Concerns）**

各層が独立した責務を持つことで、保守性が向上します。

| 層 | 責務 | DB操作 | ストレージ操作 |
|---|---|---|---|
| projectService | ビジネスロジック | ✅ | ❌ |
| fileAccessService | ストレージ + DBメタデータ統合 | ✅ | ✅ |
| storageService | 純粋なストレージ操作 | ❌ | ✅ |

**メリット**:
- storageServiceはS3/Swift操作のみに集中できる
- fileAccessServiceがDBとストレージの整合性を保証
- projectServiceはビジネスロジックに専念できる

---

### 理由2: **DBメタデータの管理**

fileAccessServiceが`file_metadata`テーブルの論理削除を担当します。

```typescript
// fileAccessService.deleteFolderRecursive の重要な処理

// ストレージ削除
await this.storageService.deleteFolderRecursive(organizationId, folderPath);

// ✨ DBメタデータの論理削除（fileAccessServiceのみが実行）
if (fileKeys.length > 0) {
  await this.repository.softDeleteBatch(organizationId, fileKeys);
  console.log(`✅ DBメタデータ一括論理削除成功: ${dbDeletedCount}/${fileKeys.length}件`);
}
```

**もしfileAccessServiceが無ければ**:
- projectServiceがDBメタデータ削除を直接実行する必要がある
- または、storageServiceがDB操作を持つ必要がある（責務違反）
- 他の画面（フォーマット削除など）で同じ処理を重複実装する必要がある

---

### 理由3: **再利用性**

fileAccessServiceは他の画面・機能でも利用可能です。

**利用例**:
```typescript
// プロジェクトフォルダ削除
await fileAccessService.deleteFolderRecursive(
  organizationId,
  'projects/sample_project'
);

// フォーマットフォルダ削除
await fileAccessService.deleteFolderRecursive(
  organizationId,
  'formats/dept_001/chemistry'
);

// その他任意のフォルダ削除
await fileAccessService.deleteFolderRecursive(
  organizationId,
  'temp_uploads/batch_123'
);
```

**もしfileAccessServiceが無ければ**:
- 各画面ごとに「ストレージ削除 + DBメタデータ削除」のロジックを重複実装
- DRY原則違反
- バグ修正時に複数箇所の修正が必要

---

### 理由4: **セキュリティとバリデーション**

fileAccessServiceが統一的なバリデーションを提供します。

```typescript
// パストラバーサル攻撃対策
if (folderPath.includes('..') || folderPath.includes('//')) {
  throw new ValidationError('不正なフォルダパスが検出されました');
}

// 統一的なエラーハンドリング
throw new NotFoundError(`フォルダにファイルが見つかりません: ${folderPath}`);
throw new StorageError(`フォルダの削除に失敗しました: ${folderPath}`);
```

**もしfileAccessServiceが無ければ**:
- projectServiceが直接セキュリティチェックを実装
- またはstorageServiceがセキュリティチェックを実装（責務違反）
- 他の画面でセキュリティチェックを忘れるリスク

---

## 🔄 処理フローの詳細

### 実際の削除フロー

```
1. projectService.deleteProject
   ↓
   [DB操作]
   - project_task_detail削除
   - project_task削除
   - project_instruction削除
   - project削除
   ↓
   [DBコミット]
   ↓
2. fileAccessService.deleteFolderRecursive
   ↓
   [バリデーション]
   - パストラバーサル攻撃対策
   - フォルダパス正規化
   ↓
   [ファイル一覧取得]
   - storageService.listFiles()
   ↓
3. storageService.deleteFolderRecursive
   ↓
   [ストレージ操作]
   - 各ファイルをS3/Swiftから削除
   ↓
   [戻る]
   ↓
2. fileAccessService（続き）
   ↓
   [DB操作]
   - file_metadataテーブルの一括論理削除
   ↓
   [戻る]
   ↓
1. projectService（完了）
```

## 📊 比較: 現在の設計 vs 代替案

### 現在の設計（3層構造）

```
projectService
  ↓（ビジネスロジック）
fileAccessService
  ↓（ストレージ + DBメタデータ）
storageService
  ↓（純粋なストレージ操作）
```

**メリット**:
- ✅ 責務が明確に分離
- ✅ 再利用性が高い
- ✅ テストが容易
- ✅ 保守性が高い

**デメリット**:
- ⚠️ 層が増えて複雑に見える（しかし実際は整理されている）

---

### 代替案1: fileAccessServiceを削除（2層構造）

```
projectService
  ↓（ビジネスロジック + DBメタデータ削除）
storageService
  ↓（純粋なストレージ操作）
```

**デメリット**:
- ❌ projectServiceがDBメタデータ削除の責務を持つ（責務違反）
- ❌ 他の画面（フォーマット削除など）で処理を重複実装
- ❌ DRY原則違反
- ❌ セキュリティチェックを各画面で実装する必要がある

---

### 代替案2: storageServiceにDBメタデータ削除を追加

```
projectService
  ↓（ビジネスロジック）
storageService
  ↓（ストレージ操作 + DBメタデータ削除）
```

**デメリット**:
- ❌ storageServiceがDB操作を持つ（責務違反）
- ❌ 純粋なストレージ操作ではなくなる
- ❌ S3/Swift操作とDB操作が混在して複雑化
- ❌ テストが困難

---

## ✅ 結論

### fileAccessService.deleteFolderRecursive は必要

**理由まとめ**:

1. **責務の分離**: ストレージとDBメタデータの統合管理を担当
2. **DBメタデータ管理**: file_metadataテーブルの論理削除を一元管理
3. **再利用性**: プロジェクト、フォーマット、その他のフォルダ削除で共通利用
4. **セキュリティ**: 統一的なバリデーションとエラーハンドリング
5. **保守性**: 各層の責務が明確で、変更影響が限定的

### 現在の設計は適切

3層構造（projectService → fileAccessService → storageService）は、以下の設計原則に従っています：

- ✅ **Single Responsibility Principle（単一責任の原則）**
- ✅ **Separation of Concerns（関心の分離）**
- ✅ **DRY（Don't Repeat Yourself）**
- ✅ **SOLID原則**

## 🔧 改善提案（任意）

現在の設計は適切ですが、以下の改善を検討できます：

### 提案1: DBメタデータ削除の確実性向上

現在はストレージ削除後にDBメタデータ削除が失敗してもログのみで続行していますが、以下の改善を検討できます：

```typescript
// 現在の実装
try {
  await this.repository.softDeleteBatch(organizationId, fileKeys);
} catch (error) {
  // ログに記録するが、処理は続行
  console.error(`⚠️ DBメタデータ論理削除エラー（処理は続行）`, error);
}

// 改善案: リトライ機構を追加
try {
  await this.repository.softDeleteBatch(organizationId, fileKeys);
} catch (error) {
  // 3回までリトライ
  for (let i = 0; i < 3; i++) {
    try {
      await this.repository.softDeleteBatch(organizationId, fileKeys);
      break;
    } catch (retryError) {
      if (i === 2) {
        console.error(`❌ DBメタデータ削除が3回失敗しました`, retryError);
      }
    }
  }
}
```

### 提案2: トランザクション管理の見直し

現在はストレージ削除がトランザクション外ですが、整合性をより厳密にする場合は以下を検討：

```typescript
// 現在の実装
await client.query('COMMIT'); // DBコミット
await fileAccessService.deleteFolderRecursive(...); // トランザクション外

// 改善案: DB削除を遅延させる
await fileAccessService.deleteFolderRecursive(...); // 先にストレージ削除
await client.query('COMMIT'); // 成功後にDBコミット
```

ただし、この変更はストレージ削除が失敗した場合の挙動に影響するため、慎重に検討する必要があります。

## 3. 現状分析

### 3.1. バックエンドの現状
- **最小限の実装のみ**:
  - `backend/src/server.ts`: 基本的なExpress設定とヘルスチェックエンドポイントのみ
  - ディレクトリ構造: `src/`配下に`server.ts`のみ存在
  - 必要なディレクトリ未作成: `routes/`, `middleware/`, `services/`, `repository/`, `utils/`

### 3.2. フロントエンドの型定義
以下の型定義ファイルが存在し、API仕様の参考となります：

#### 認証関連 (`auth.ts`)
- **UserRole**: 6つのロール定義
  - `provider`, `system_admin`, `data_admin`, `experiment_admin`, `experiment_worker`
- **User**: ユーザー情報
- **LoginCredentials**: ログイン資格情報

#### プロジェクト関連 (`project.ts`)
- **Project**: プロジェクト情報（id, name, status, fileCount, tasks等）
- **ProjectStatus**: 6つのステータス（planning, pending, in_progress, review_waiting, completed, error）
- **Task**: タスク情報（taskId, workerId, transitionId, workStatus等）
- **TaskStatus**: 5つのステータス（pending, in_progress, error, review_waiting, completed）

#### 実験作業関連 (`experimentWorker.ts`)
- **Instruction**: 作業指示情報
- **Method**: 実験メソッド
- **Transition**: トランジション（プロセス）
- **Template**: データ記録テンプレート
- **ExperimentRecord**: 実験記録データ
- **Task**: タスクデータ（6つのステータス）

#### ファイル関連 (`file.ts`)
- **ProjectFile**: プロジェクトファイル情報
- **FileMetadata**: ファイルメタデータ
- **各種リクエスト型**: Upload, Download, Delete, Move, Copy, Rename

### 3.3. 必要なAPIエンドポイント（推定）

#### 認証API (`/api/v1/auth`)
1. POST `/login` - ログイン
2. POST `/logout` - ログアウト
3. GET `/verify-session` - セッション検証
4. POST `/refresh-token` - トークン更新
5. GET `/me` - 現在のユーザー情報

#### ユーザー管理API (`/api/v1/users`)
1. GET `/users` - ユーザー一覧取得
2. GET `/users/{id}` - ユーザー詳細取得
3. POST `/users` - ユーザー作成
4. PUT `/users/{id}` - ユーザー更新
5. DELETE `/users/{id}` - ユーザー削除

#### 組織管理API (`/api/v1/organizations`)
1. GET `/organizations` - 組織一覧取得
2. GET `/organizations/{id}` - 組織詳細取得
3. POST `/organizations` - 組織作成
4. PUT `/organizations/{id}` - 組織更新

#### プロジェクト管理API (`/api/v1/projects`)
1. GET `/projects` - プロジェクト一覧取得（フィルタ・ソート・ページング対応）
2. GET `/projects/{id}` - プロジェクト詳細取得

4. PUT `/projects/{id}` - プロジェクト更新
5. DELETE `/projects/{id}` - プロジェクト削除
6. POST `/projects/{id}/checkout` - プロジェクトチェックアウト
7. POST `/projects/{id}/checkin` - プロジェクトチェックイン
8. GET `/projects/{id}/tasks` - プロジェクトのタスク一覧取得

#### ファイル管理API (`/api/v1/files`)

2. GET `/files/{id}` - ファイル詳細取得
3. POST `/files/upload` - ファイルアップロード

#### 実験管理API (`/api/v1/experiments`)

### アーキテクチャ上の考慮事項
1. **レイヤードアーキテクチャ**:
   - ルート層 → ミドルウェア層 → サービス層 → リポジトリ層

2. **マルチテナント分離**:
   - すべてのDBクエリに`organization_id`フィルタ必須
   - すべてのS3パスに`org_{organization_id}`プレフィックス必須

3. **セキュリティ**:
   - JWT + Session Hybrid認証
   - Parameterized Queries（SQLインジェクション対策）
   - レート制限
   - CORS設定

## 7. リスクと対策

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|----------|------|
| データベース未構築 | 高 | 高 | モックデータで先行実装、後でDB接続 |
| S3未設定 | 高 | 高 | ローカルファイルシステムで代替実装 |
| 認証仕様の不明確さ | 中 | 中 | JWT + Sessionの標準パターンで実装 |
| APIエンドポイント数が多い | 中 | 高 | Phase分割で段階的に実装 |
| テスト工数の増大 | 中 | 高 | 重要APIから優先的にテスト実装 |
| フロントエンドとの型の不整合 | 中 | 中 | フロントエンドの型定義を参照して実装 |

# 不具合調査レポート4

## 調査日時
2026-05-22 10:10（再調査・更新）

## 調査対象
動作確認中に発見された以下の残存不具合

1. Template編集ダイアログでIDを書き換えた場合、変更が保存されない（または旧IDエントリが削除されず新IDで登録もされない）
2. 単一メソッドMAIMLに新しいメソッドを追加したとき、PNMLのIDとPROGRAMのIDが書き換わる（単一/複数でID命名規則が異なる）
3. 上記操作においてPNMLのUUIDは書き換わったがPROGRAMのUUIDは書き換わらなかった

## 不具合1: Template編集ダイアログでIDを変更しても保存されない

### 症状
- Template編集ダイアログでテンプレートのIDフィールドを変更して保存しても、変更が反映されない
- 旧IDのエントリが残り続ける

### 現在のコード（`PetriNetEditorInner.tsx` L2015〜2076）

```typescript
// L2018: 検索キーの決定
const searchId = templateEditNode?.data?.template?.id || templateId;
// ↑ templateEditNode が null または node.data.template が未設定の場合、
//   templateId（新ID）がsearchIdになる

// L2019〜2027: 元のテンプレートを全カテゴリから検索
(['material', 'condition', 'result'] as const).forEach((category) => {
  const found = templates.find((t: Template) => t.id === searchId);
  if (found) originalTemplate = found;
});

// L2043: 旧IDの決定
const oldTemplateId = originalTemplate.id || templateId;
// ↑ 検索がヒットしなかった場合、originalTemplate.id = ''（初期値）
//   → oldTemplateId = '' || templateId = templateId（新ID）

// L2044: ID変更判定
const idChanged = oldTemplateId !== templateId;
// ↑ oldTemplateId が新IDと同じになるため idChanged = false

// L2056: TemplateContext更新
window.clineUpdateTemplate(oldTemplateId, { id: templateId, ... });
// ↑ 第1引数が新ID（新IDで検索するが既存エントリは旧IDなのでヒットしない）
```

### 根本原因

**`templateEditNode?.data?.template` がダイアログ保存時点で更新済みの値（新ID）を持っている場合、`searchId = templateId`（新ID）になる。**
この場合 `originalTemplate` が見つからず `originalTemplate.id = ''` になるため、`oldTemplateId = templateId`（新ID）となり、`idChanged = false` と判定される。

結果として `window.clineUpdateTemplate(新ID, ...)` が呼ばれるが、TemplateContext内には旧IDのエントリしかないためヒットせず、更新が実行されない。

#### TemplateContext.updateTemplate の実装（`TemplateContext.tsx` L257〜279）

```typescript
const updateTemplate = useCallback((templateId: string, updatedTemplate: Template) => {
  setTemplates((prevTemplates) => {
    const updated = { ...prevTemplates };
    (['material', 'condition', 'result'] as const).forEach((category) => {
      const index = updated[category].findIndex((t) => t.id === templateId);
      // ↑ templateId = 新ID で検索しているが、既存エントリは旧ID → ヒットしない
      if (index !== -1) {
        updated[category][index] = updatedTemplate;
      }
    });
    return updated;
  });
}, []);
```

`findIndex` が `-1` を返す → 更新が実行されない。

#### 追加問題: 既存テンプレート更新パスでダイアログが閉じない

新規テンプレート作成パス（L1992〜1993）には `setTemplateEditorOpen(false)` / `setTemplateEditNode(null)` があるが、**既存テンプレート更新パス（L1997〜2183）にはこれらの呼び出しがない**。

```typescript
// 新規作成パス（L1992〜1993）
setTemplateEditorOpen(false);  // ← あり
setTemplateEditNode(null);     // ← あり

// 既存テンプレート更新パス（L1997〜2183）
onContentChange?.();
console.log('💾 Template保存完了...');
// ↑ setTemplateEditorOpen / setTemplateEditNode の呼び出しなし
```

### 修正方針

1. **`handleSaveTemplate` 内の `searchId` 取得を修正**：`templateEditNode.data.template.id` ではなく別の方法で旧IDを取得する。具体的には `templateEditNode` の初期状態（ダイアログ開いた時点の `node.data.template.id`）を別stateまたはrefで保持する。

2. **既存テンプレート更新パスにダイアログクローズ処理を追加**：
   ```typescript
   onContentChange?.();
   setTemplateEditorOpen(false);  // ← 追加
   setTemplateEditNode(null);     // ← 追加
   ```

## 不具合2: 単一→複数メソッド追加時にPNML/PROGRAMのIDが変わる

### 症状
- 単一メソッドMAIMLを編集中に新しいメソッドを追加（複数メソッドモードへ切り替わる）
- 保存すると、既存メソッドのPNML IDとPROGRAM IDが変わる
- 例: `pnmlID` → `pnml_method_xxx`、`programID` → `program_method_xxx`

### 現在のコード

#### 単一メソッドコンバーター（`reactFlowToMaiml.ts` L836〜845）

```typescript
const protocolId = documentData?.protocolId || originalStructure?.protocol?.id || 'protocolID';
const methodId   = documentData?.methodId   || originalStructure?.method?.id   || 'methodID';
// ✅ 修正コメントあり: 複数メソッド時（multiMethodConverter.ts）と命名規則を統一
// 単一メソッド時: 既存IDを優先し、なければ同じ命名規則を使用
const pnmlId    = documentData?.pnmlId    || originalStructure?.pnml?.id    || `pnml_${methodId}`;
const programId = documentData?.programId || originalStructure?.program?.id || `program_${methodId}`;
```

**`documentData?.protocolId` / `documentData?.pnmlId` / `documentData?.programId` はすでに `DocumentData` 型から削除されているため、常に `undefined`。**

したがって実際の評価は：
- `pnmlId = undefined || originalStructure?.pnml?.id || \`pnml_${methodId}\``
- `programId = undefined || originalStructure?.program?.id || \`program_${methodId}\``

元のMAIMLファイルの `<pnml id="pnmlID">` / `<program id="programID">` を読んだ場合：
- `originalStructure?.pnml?.id = 'pnmlID'` → `pnmlId = 'pnmlID'`（変わらない）
- `originalStructure?.program?.id = 'programID'` → `programId = 'programID'`（変わらない）

#### 複数メソッドコンバーター（`multiMethodConverter.ts` L368〜370）

```typescript
const pnmlId    = `pnml_${methodId}`;    // 常にこの形式
const programId = `program_${methodId}`; // 常にこの形式
```

#### 切り替えのタイミング（`PetriNetEditorInner.tsx`）

```typescript
if (multiMethodMode && methods.length > 0) {
  maimlXml = convertMultipleMethodsToMaiML(...);  // pnml_xxx / program_xxx 形式
} else {
  maimlXml = await convertReactFlowToMaiML(...);  // 既存ID（pnmlID / programID）を保持
}
```

`handleAddMethod` を呼ぶと `setMultiMethodMode(true)` になり、次の保存から `convertMultipleMethodsToMaiML` が使われる。これにより既存メソッドのPNML/PROGRAM IDが `pnml_${methodId}` / `program_${methodId}` 形式に変わる。

### ユーザー要件

**複数メソッドのID命名規則（`pnml_${methodId}` / `program_${methodId}`）に統一してほしい。**

### 修正方針

**`reactFlowToMaiml.ts` の `pnmlId` / `programId` 生成ロジックを `multiMethodConverter.ts` と同じ命名規則に変更する。**

```typescript
// 修正前（L836〜845）
const protocolId = documentData?.protocolId || originalStructure?.protocol?.id || 'protocolID';
const methodId   = documentData?.methodId   || originalStructure?.method?.id   || 'methodID';
const pnmlId     = documentData?.pnmlId    || originalStructure?.pnml?.id    || `pnml_${methodId}`;
const pnmlName   = originalStructure?.pnml?.name || `${fileName}PNML`;
const pnmlDescription = originalStructure?.pnml?.description || '';
const programId  = documentData?.programId || originalStructure?.program?.id || `program_${methodId}`;

// 修正後: DocumentDataからID系フィールドが削除されたため、originalStructureのみ参照。
// かつ単一メソッド時も multiMethodConverter.ts と同じ命名規則に統一する。
const protocolId = originalStructure?.protocol?.id || 'protocolID';
const methodId   = originalStructure?.method?.id   || 'methodID';
const pnmlId     = `pnml_${methodId}`;       // multiMethodConverter.ts と同じ命名規則
const pnmlName   = originalStructure?.pnml?.name || `${fileName}PNML`;
const pnmlDescription = originalStructure?.pnml?.description || '';
const programId  = `program_${methodId}`;    // multiMethodConverter.ts と同じ命名規則
```

#### 注意事項
- 既存の単一メソッドMAIMLを初回保存するとPNML/PROGRAM IDが `pnml_${methodId}` 形式に変わる（後方互換性への影響）
- `savedUuids.pnmls` / `savedUuids.programs` のキーは `methodId` であり、ID命名規則変更後も同じキーが使われるためUUIDの引き継ぎ自体は問題ない

## 不具合3: PNMLのUUIDは書き換わったがPROGRAMのUUIDは書き換わらなかった

### 症状
- 単一メソッドに新しいメソッドを追加して保存
- 既存メソッドのPNMLのUUIDは再生成された
- 既存メソッドのPROGRAMのUUIDは変わっていなかった（旧UUIDのまま）

### 現在のコード

#### multiMethodConverter.ts（L363〜371）

```typescript
function buildMethodXML(method, index, fileName, allTemplates, savedUuids) {
  const methodId   = method.methodId;
  const methodUuid = savedUuids?.methods.get(methodId)  || generateUUID();
  const pnmlId     = `pnml_${methodId}`;
  const pnmlUuid   = savedUuids?.pnmls.get(methodId)    || generateUUID();
  const programId  = `program_${methodId}`;
  const programUuid = savedUuids?.programs.get(methodId) || generateUUID();
  ...
}
```

#### filteredUuids生成ロジック（`PetriNetEditorInner.tsx`）

```typescript
const filteredUuids = {
  ...savedUuids,
  programs: new Map(
    [...savedUuids.programs.entries()].filter(([mid]) => !dirtyFlags.programs.has(mid))
  ),
  ...
};
```

`dirtyFlags.programs` が空の場合、全programエントリが `filteredUuids.programs` に残る。
→ `savedUuids.programs.get(methodId)` がヒットし、旧UUIDがそのまま使われる。

### なぜPNMLのUUIDは書き換わり、PROGRAMは書き換わらなかったのか

**PNMLとPROGRAMで挙動が異なる原因の調査：**

単一メソッドMAIML編集中、`savedUuids`（`ExtractedUuids`型）は `maimlUuidExtractor.extractUuidsFromMaiml()` によって読み込み時に構築される。

```typescript
// ExtractedUuids の構造
pnmls:    Map<methodId, uuid>   // キー: methodId
programs: Map<methodId, uuid>   // キー: methodId
```

`extractUuidsFromMaiml()` でキーとして使われる `methodId` は MAIMLの `<method id="...">` の値。

**元の単一メソッドMAIMLが `<method id="methodID">` の場合：**
- `savedUuids.pnmls.get('methodID')` = 元のpnml UUID
- `savedUuids.programs.get('methodID')` = 元のprogram UUID

新しいメソッドを追加して保存すると `convertMultipleMethodsToMaiML` が呼ばれ、各メソッドの `methodId`（`MethodData.methodId`）でlookupする。

**元のメソッドの `MethodData.methodId`**が何かによって挙動が分かれる：

- `MethodData.methodId = 'methodID'`（元MAIMLのmethod.idと同じ）の場合：
  → `savedUuids.pnmls.get('methodID')` がヒット → 旧UUID使用（PNMLは書き換わらないはず）
  → `savedUuids.programs.get('methodID')` がヒット → 旧UUID使用（PROGRAMも書き換わらないはず）

**ユーザーの観察では「PNMLは書き換わったがPROGRAMは書き換わらなかった」**。

この非対称な挙動の原因として考えられるのは：

1. `dirtyFlags.pnmls` には元のmethodIdが追加されていたが、`dirtyFlags.programs` は空だった
   → PNMLは `filteredUuids.pnmls` から除外（新UUID生成）、PROGRAMは除外されなかった（旧UUID使用）

2. または `savedUuids.pnmls` には `methodId` のエントリがなかった（キー不一致）が、
   `savedUuids.programs` にはエントリがあった

**最も可能性が高い原因：何らかの操作でpnmlがdirtyになっていたが、programはdirtyになっていなかった。**

現在の `markPnmlDirtyForCurrentMethod` 実装（`PetriNetEditorInner.tsx`）：

```typescript
const markPnmlDirtyForCurrentMethod = useCallback(() => {
  const currentMethodId = methods[activeMethodIndex]?.methodId;
  if (!currentMethodId) return;
  setDirtyFlags(prev => ({
    ...prev,
    protocol: true,
    methods: new Set([...prev.methods, currentMethodId]),
    pnmls: new Set([...prev.pnmls, currentMethodId]),
    // ← programs は追加されない
  }));
}, [methods, activeMethodIndex]);
```

`markPnmlDirtyForCurrentMethod` を呼ぶとpnmlはdirtyになるが **programはdirtyにならない**。
この結果、保存時に：
- PNML: `dirtyFlags.pnmls.has(methodId) = true` → `filteredUuids.pnmls` から除外 → 新UUID生成
- PROGRAM: `dirtyFlags.programs.has(methodId) = false` → `filteredUuids.programs` に残る → 旧UUID使用

### 修正方針

**`markPnmlDirtyForCurrentMethod` に `programs` も追加する。**

```typescript
const markPnmlDirtyForCurrentMethod = useCallback(() => {
  const currentMethodId = methods[activeMethodIndex]?.methodId;
  if (!currentMethodId) return;
  setDirtyFlags(prev => ({
    ...prev,
    protocol: true,
    methods: new Set([...prev.methods, currentMethodId]),
    pnmls: new Set([...prev.pnmls, currentMethodId]),
    programs: new Set([...prev.programs, currentMethodId]),  // ← 追加
  }));
}, [methods, activeMethodIndex]);
```

これにより「pnmlが変更された → methodのプログラムも同じmethodIdに属する → programも再採番」という一貫した動作になる。

## 不具合4: DocumentEditDialog の maimlIds セクションが型と不一致

### 症状
- `DocumentEditDialog.tsx` の「MAIML IDs」セクションに `Protocol ID` / `Method ID` / `PNML ID` / `Program ID` の入力欄がある（L415〜429）
- これらのフィールドは `DocumentData` 型（`editor.ts`）から既に削除されている
- 入力欄に値を入力しても `DocumentData` 型に存在しないため、`handleSave` 後に `onSave(documentToSave)` で渡された値がどこにも保存されない

### 現在のコード（`DocumentEditDialog.tsx` L260〜272）

```typescript
const handleSave = useCallback(async () => {
  const values = form.getFieldsValue(true);
  // ↑ フォームの全フィールドを取得（protocolId/methodId/pnmlId/programIdも含まれる）

  const documentToSave: DocumentData = {
    ...values,  // ← TypeScript型上は protocolId 等は DocumentData に存在しない
    date: values.date ? values.date : new Date(),
    signatureEnabled: values.signatureEnabled,
  };

  onSave(documentToSave);
  onClose();
}, [form, onSave, onClose]);
```

### 原因

`DocumentData` 型（`editor.ts` L112〜129）から `protocolId`/`methodId`/`pnmlId`/`programId` が削除された結果、`DocumentEditDialog` の入力欄が「表示はされるが保存先がない」状態になっている。

また `reactFlowToMaiml.ts` L836〜845 で `documentData?.protocolId` 等を参照しているが、型上は `undefined` になるため参照が無意味になっている（フォールバックの `originalStructure?.xxx.id` か `'methodID'` 等が使われる）。

### 影響

- ユーザーが `MAIML IDs` セクションで ID を変更しても、変更は MAIML 出力に反映されない
- `Protocol ID` 入力欄は特に、ユーザーが意図的に変更できる唯一の手段だったが機能不全になっている

### 修正方針

**案A: `DocumentEditDialog` の `maimlIds` セクションを削除する（推奨）**

ID は MAIMLパース時に `originalStructure` に取り込まれ、`reactFlowToMaiml.ts` / `multiMethodConverter.ts` で命名規則に従って生成されるため、ユーザーが手動編集する必要がない。

```
削除対象: DocumentEditDialog.tsx の
- Collapse item key="maimlIds" 全体（L404〜438）
```

**案B: `DocumentData` に ID 系フィールドを復活させる**（変更範囲が広いため非推奨）

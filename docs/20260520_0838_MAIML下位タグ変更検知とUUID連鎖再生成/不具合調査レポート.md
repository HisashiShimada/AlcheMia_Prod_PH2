## 2. 不具合① Creator/Vendor の annotation 消失

### 症状
- ito1_1.maiml の `<creator>` に存在した `<annotation>定期校正: 年1回 / ...</annotation>` が ito1_2.maiml では出力されていない
- 同様に `<vendor>` の `<annotation>` も消えている

### 根本原因
**`documentParser.ts` の正規表現パーサーと `maimlTypeConverter.ts` の型変換器が並存しており、annotation が取りこぼされるルートがある**

`documentParser.ts` の `parseDocumentElement()` では annotation を正しく取得している：
```typescript
annotation: extractTagContent(creatorContent, 'annotation', creatorContent) || '',
```

しかし `maimlTypeConverter.ts` の `convertCreator` / `convertVendor` 関数の実装を確認したところ、これらの関数の具体的な実装内容（特に annotation フィールドを含めているか）が不明であり、両パーサー間の不整合の可能性がある。

また、`PetriNetEditorInner.tsx` では `new MaimlParserTyped(maimlData)` を使い `getDocument()` でドキュメント情報を取得しているが、この経路で annotation が欠落している場合、保存時の `documentData.creators[].annotation` が空になる。

**確認が必要な箇所**: `maimlTypeConverter.ts` の `convertCreator` / `convertVendor` 関数の実装（annotation フィールドが含まれているか）

## 3. 不具合② protocol/method/pnml/program の id がデフォルト値になる

### 症状
ito1_1.maiml では `protocol_ito1_25262a67` 等のカスタムIDが付いていたが、ito1_2.maiml では `protocolID` / `methodID` / `pnmlID` / `programID` に書き換わっている。

### 根本原因
**`handleSaveConfirmAction` において `convertReactFlowToMaiML` への `originalStructure` 引数が `null` で渡されている**

```typescript
// PetriNetEditorInner.tsx の保存処理
maimlXml = await convertReactFlowToMaiML(
  nodes, edges, metadata, documentData ?? null,
  null,   // ← originalStructure が常に null！
  allTemplatesFromContext, null, filteredUuids
);
```

`convertReactFlowToMaiML` でのID解決ロジック:
```typescript
const protocolId = documentData?.protocolId || originalStructure?.protocol?.id || 'protocolID';
const methodId   = documentData?.methodId   || originalStructure?.method?.id   || 'methodID';
const pnmlId     = documentData?.pnmlId     || originalStructure?.pnml?.id     || 'pnmlID';
const programId  = documentData?.programId  || originalStructure?.program?.id  || 'programID';
```

`originalStructure` が `null` の場合、フォールバックは `documentData?.protocolId` のみ。
`documentData.protocolId` が `''`（空文字）または `undefined` の場合にデフォルト値 `'protocolID'` にフォールバックする。

**`documentData.protocolId` がなぜ空になるか**:  
`documentParser.ts` の `extractDocumentFromMaiML()` では `extractTagAttribute(maimlData, 'protocol', 'id')` でIDを取得しているが、この関数が `PetriNetEditorInner.tsx` のMAIML読み込み処理でどのように使われているかを確認すると、`documentData` の `protocolId` は `MAIMLParserTyped.getDocument()` 経由で設定されているが、**`getDocument()` の実装が `protocolId/methodId/pnmlId/programId` を返していない** 可能性が高い。

`maimlParserTyped.ts` の `getDocument()` は `MaimlDocument` 型（`maiml-unified.ts` の型定義）を返すが、この型は document タグ直下の情報しか含まない。`protocolId/methodId/pnmlId/programId` は document タグの外にあるため、**`getDocument()` では取得できない**。

つまり、`PetriNetEditorInner.tsx` のMAIML読み込み時に `documentData.protocolId` 等が設定されないまま `documentData` がstateに入ってしまっている。

## 4. 不具合③ method/pnml/program の UUID が変わる（連鎖影響）

### 症状
変更なし保存にも関わらず method/pnml/program の UUID が新規生成されている。  
（protocol の UUID は正しく引き継がれている）

### 根本原因
**不具合②の直接的な連鎖**: `savedUuids` の Map キーが実際のmethodId（`method_ito1_25262a67`）で格納されているのに、保存時の検索キーが `methodID`（デフォルト値）になってしまうため、Map から UUID が取得できずに `generateUUID()` が呼ばれる。

```typescript
// extractUuidsFromMaiml でMapに格納時
result.methods.set('method_ito1_25262a67', uuid);  // キー = 実際のmethodId
result.pnmls.set('method_ito1_25262a67', uuid);
result.programs.set('method_ito1_25262a67', uuid);

// 保存時の UUID 取得時（documentData.methodId が 'methodID' の場合）
const methodId = 'methodID';  // documentData から取得
const methodUuid = savedUuids?.methods.get('methodID') || generateUUID();
//                               ↑ 'method_ito1_25262a67' ではないのでundefined → 新UUID生成
```

protocol UUID だけ引き継がれる理由: `savedUuids.protocol` はキーなし（直接文字列）で格納されているため、methodId の問題に影響されない。

## 5. 不具合④ multiMethodConverter の instruction UUID も毎回新規生成

### 症状
`buildMethodXML` 内の instruction UUID が毎回 `generateUUID()` で生成されている。

### 根本原因
`multiMethodConverter.ts` の `buildMethodXML` では `savedUuids` を instruction UUID の解決に使っていない：

```typescript
// multiMethodConverter.ts buildMethodXML
transitions.forEach((transition: Node<NodeData>) => {
  const instructionId = transition.data.instructionId || `instruction_${transition.id}`;
  methodXml += `        <instruction id="${instructionId}">\n`;
  methodXml += `          <uuid>${generateUUID()}</uuid>\n`;  // ← savedUuids を参照していない！
```

`reactFlowToMaiml.ts` の単一メソッド版では savedUuids を参照しているが、`multiMethodConverter.ts` の複数メソッド版では対応していない。

## 6. 不具合⑤ data/eventLog UUID も引き継がれていない

### 症状
ito1_2.maiml で data/eventLog の UUID も変わっている。「以前に修正済みのはず」との指摘があったが、実際には変わっている。

### 根本原因
`convertReactFlowToMaiML`（単一メソッド版）側での data/eventLog UUID 出力は `savedUuids?.dataUuid` / `savedUuids?.eventLogUuid` を参照するよう実装済み。ただし今回 **`savedUuids` 自体が `null` になっている** ことが疑われる。

**経路の問題**: `savedUuids` は MAIML ロード時に `extractUuidsFromMaiml(maimlData)` で設定されるが、MAIMLロード処理のブランチ分岐（isMultiMethod 判定等）によってはこのコードが実行されないパスが存在する可能性がある。あるいは、バリデーション用途（`handleOpenValidationPanel`）の convertReactFlowToMaiML 呼び出しでは `savedUuids`（filteredUuidsではない）を渡しているが、保存処理（`handleSaveConfirmAction`）では `filteredUuids` を渡しており、`filteredUuids` 生成時に `savedUuids が null` だと `filteredUuids = null` になる（下記コード参照）：

```typescript
const filteredUuids: ExtractedUuids | null = savedUuids
  ? { ...savedUuids, ... }  // savedUuids が null の場合はここに来ない → null のまま
  : null;
```

`filteredUuids = null` のまま convertor に渡すと、dataUuid/eventLogUuid も `generateUUID()` になる。つまり **不具合②③の根本原因（documentData.methodId が空 → savedUuids の初期化が正しくできていない、またはロードパスが通っていない）と連動している**。

## 7. 不具合⑥ transition の `<name>` タグが勝手に生成される

### 症状
元の MAIML に `<name>` タグが存在しない transition に対して、再保存後に `<name>` タグが追加されている。

### 根本原因
**`reactFlowConverter.ts` で transition の `data.name` をフォールバック付きで設定しているため、元は名前なしだった transition でも name が埋まってしまう**。

```typescript
// reactFlowConverter.ts
const transitionNodes = transitions.map(transition => {
  ...
  data: {
    name: transition.name || transition.description || transition.id,  // ← フォールバックで description または id を代入
    ...
  }
});
```

- MAIML に `<name>` がない transition でも、`transition.description`（あれば）または `transition.id` が `data.name` にセットされる
- その後 `reactFlowToMaiml.ts` での保存時：

```typescript
const hasName = transition.data.name && transition.data.name.trim() !== '';
if (hasName) {
  maiml += `<name>${escapeXml(transition.data.name)}</name>\n`;  // ← id や description 値が name として書き出される
}
```

- `data.name` が `id` や `description` の値で埋まっているため `hasName = true` となり、元々なかった `<name>` タグが出力される

### 修正方針
`reactFlowConverter.ts` のフォールバック代入と、保存時の `<name>` 出力判定を分離する：

**方法A**: `reactFlowConverter.ts` で `name` と `label`（表示用）を分ける
```typescript
data: {
  name: transition.name ?? undefined,          // MAIMLの<name>タグ値のみ（なければ undefined）
  label: transition.name || transition.description || transition.id,  // 表示用ラベル
}
```

**方法B**: `reactFlowToMaiml.ts` で、name の値が id と等しい場合（フォールバック由来）は出力しない
```typescript
// name が id のフォールバックでない場合のみ出力
const hasName = transition.data.name
  && transition.data.name.trim() !== ''
  && transition.data.name !== transition.id;  // id フォールバックを除外
```

**推奨**: 方法Aが根本的解決。方法Bは description フォールバックを除外しきれないため不完全。

## 8. 修正方針

### 優先度 高: 不具合②③（ID/UUID引き継ぎ）の修正

**方針 A（推奨）**: MAIMLロード時に `extractDocumentFromMaiML`（documentParser.ts）を必ず呼んで `protocolId/methodId/pnmlId/programId` を `documentData` に設定する。

```typescript
// PetriNetEditorInner.tsx のMAIMLロード処理で
const docData = extractDocumentFromMaiML(maimlData);
// または MaimlParserTyped のgetDocumentで取得できない部分を補完
setDocumentData(prev => ({
  ...prev,
  protocolId: docData.protocolId,
  methodId: docData.methodId,
  pnmlId: docData.pnmlId,
  programId: docData.programId,
}));
```

**方針 B（暫定）**: `convertReactFlowToMaiML` に渡す `originalStructure` を正しく設定する（現在 `null` を渡している箇所を修正）。ただし、originalStructure の生成ロジックが別途必要。

**savedUuids のキーとdocumentDataのmethodIdの整合**:  
`savedUuids.methods.get(methodId)` でのキー検索が正しく機能するには、保存時の `methodId` と `extractUuidsFromMaiml` で使ったキー（`method.id`）が一致している必要がある。方針Aで `documentData.methodId` が正しく設定されれば解決する。

### 優先度 高: 不具合①（annotation消失）の修正

`maimlTypeConverter.ts` の `convertCreator` / `convertVendor` 関数に `annotation` フィールドの抽出を追加する（または確認して漏れがあれば追加）：

```typescript
function convertCreator(xmlCreator: XmlJsElement): DocumentTagData {
  return {
    // ...既存フィールド
    annotation: extractText(xmlCreator.annotation as XmlJsElement) || '',  // 追加確認
  };
}
```

### 優先度 中: 不具合④（multiMethodConverter の instruction UUID）の修正

`buildMethodXML` の instruction UUID 生成を `savedUuids?.instructions.get(instructionId)` にフォールバックさせる：

```typescript
methodXml += `          <uuid>${savedUuids?.instructions.get(instructionId) || generateUUID()}</uuid>\n`;
```

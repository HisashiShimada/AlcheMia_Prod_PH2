## 🔍 現在実装されている検索機能

### セマンティック検索（Transition Set検索）

**実装状況**: ✅ **実装済み・稼働中**

**検索対象データ**:
- `transition_set`テーブル
- MAIMLファイルから抽出されたトランジション情報
- 4軸ベクトル（input, transition, output, structure）

**検索方式**:
- ベクトル類似度検索（コサイン類似度）
- pgvector拡張機能を使用

## 📝 詳細な処理ステップ

### Step 1: ユーザー入力（フロントエンド）

**コンポーネント**: `TransitionSetSearchModal.tsx`

**入力項目**:
1. **4軸クエリ**
   - 入力（Input）: サンプルの種類・前処理条件など
   - 手法（Transition）: 使用する分析・処理手法など
   - 出力（Output）: 期待される測定結果・生成物など
   - 構造（Structure）: プレース数・テンプレート数など

2. **フィルター**
   - プロジェクト名
   - 手法コード（例: RAMAN, XRF）
   - 上位件数（1〜50件）

3. **重み調整（上級者向け）**
   - Input重み: 0.28（デフォルト）
   - Transition重み: 0.40（デフォルト）
   - Output重み: 0.22（デフォルト）
   - Structure重み: 0.10（デフォルト）

**実装コード**:

### Step 2: API呼び出し（フロントエンド）

**サービス**: `semanticSearchService.ts`

**エンドポイント**: `POST /api/v1/semantic-search/search`

**実装コード**:
```typescript
// frontend/src/services/semanticSearchService.ts
export async function search(request: SemanticSearchRequest): Promise<SearchResponse> {
  const response = await apiClient.post<ApiResponse<SearchResponse>>(
    `${BASE_PATH}/search`,
    request
  );
  
  if (!response.data.success || !response.data.data) {
    throw new Error(response.data.error?.message || '検索に失敗しました');
  }
  
  return response.data.data;
}
```

### Step 5: ベクトル検索実行（データベース）

**リポジトリ**: `semanticSearchRepository.ts`

**検索クエリ**:
```sql
-- backend/src/repositories/semanticSearchRepository.ts
SELECT 
  ts.*,
  (
    (emb_input <=> $2::vector) * $7 +
    (emb_transition <=> $3::vector) * $8 +
    (emb_output <=> $4::vector) * $9 +
    (emb_structure <=> $5::vector) * $10
  ) AS combined_score
FROM transition_set ts
WHERE ts.organization_id = $1
  AND ($11::text IS NULL OR ts.project_name = $11)
  AND ($12::text IS NULL OR ts.technique = $12)
ORDER BY combined_score ASC
LIMIT $6
```

**パラメータ**:
- `$1`: organization_id（マルチテナント分離）
- `$2`: 入力ベクトル
- `$3`: 手法ベクトル
- `$4`: 出力ベクトル
- `$5`: 構造ベクトル
- `$6`: 上位件数（top_k）
- `$7〜$10`: 重み（input, transition, output, structure）
- `$11`: プロジェクト名フィルター
- `$12`: 手法コードフィルター

**インデックス使用**:
- `idx_transition_set_org_id`: organization_idインデックス
- `idx_transition_set_emb_input_hnsw`: HNSWインデックス（入力ベクトル）
- `idx_transition_set_emb_transition_hnsw`: HNSWインデックス（手法ベクトル）
- `idx_transition_set_emb_output_hnsw`: HNSWインデックス（出力ベクトル）
- `idx_transition_set_emb_structure_hnsw`: HNSWインデックス（構造ベクトル）

## 📊 パフォーマンス

### 検索速度

**実測値**（開発環境）:
- クエリ1つ: 約200〜300ms
- クエリ4つ（全軸指定）: 約250〜400ms

**内訳**:
1. ベクトル化（Ollama）: 約50〜100ms（1クエリあたり）
2. DB検索: 約50〜150ms
3. 通信オーバーヘッド: 約20〜50ms

### スケーラビリティ

**現在の制限**:
- 上位件数: 最大50件
- 同時検索リクエスト: 制限なし（但しOllamaがボトルネック）

**推奨設定**:
- 通常検索: 10〜20件
- 詳細検索: 30〜50件

## 🔒 セキュリティ

### アクセス制御

1. **認証**: JWT Cookie認証（必須）
2. **認可**: データ管理機能（030000）の読取権限（0）が必要
3. **テナント分離**: organization_idによる完全分離

### データ保護

1. **クエリログ**: 検索クエリは記録されない（プライバシー保護）
2. **結果フィルタ**: 必ずorganization_idでフィルタリング
3. **SQL注入対策**: Parameterized Queriesを使用

## 🔧 トラブルシューティング

### 検索結果が0件

**原因1**: インデックスが未作成
```bash
# 確認方法
SELECT COUNT(*) FROM transition_set WHERE organization_id = 'your_org_id';

# 対処方法
POST /api/v1/semantic-search/batch
```

**原因2**: クエリが適切でない
- より一般的な用語で検索
- 手法コードフィルターを外す
- 重みを調整（transitionを高く）

**原因3**: 組織IDの不一致
- ログインユーザーの組織IDを確認
- 検索対象ファイルの組織IDを確認

### 検索が遅い

**原因1**: Ollamaが停止している
```bash
# 確認方法
GET /api/v1/semantic-search/health

# 対処方法
docker-compose up -d ollama
```

**原因2**: インデックスが未最適化
```sql
-- 再構築方法
REINDEX INDEX idx_transition_set_emb_input_hnsw;
REINDEX INDEX idx_transition_set_emb_transition_hnsw;
REINDEX INDEX idx_transition_set_emb_output_hnsw;
REINDEX INDEX idx_transition_set_emb_structure_hnsw;
```

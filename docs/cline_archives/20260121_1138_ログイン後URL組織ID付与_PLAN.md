## 1. タスク概要

ログイン画面で認証後、次の画面へ遷移する際のURLに組織ID（organizationId）を付与し、URLからも現在の組織を識別できるようにする。

## 2. 目的と期待される成果

### 目的
- URLだけで現在アクセスしている組織を識別可能にする
- ブックマークやURL共有時に組織情報を保持する
- マルチテナント環境でのUX向上

### 期待される成果
- [ ] ログイン後のURLに組織IDがクエリパラメータとして付与される
- [ ] 例: `/experiment-admin?orgId=org_lab_001`
- [ ] URLからの組織ID取得が可能になる
- [ ] 既存の認証フローに影響を与えない

## 3. 現状分析

### 3.1. 現在の実装

**バックエンド（authController.ts - verifyPin関数）**：
```typescript
// すでにredirectUrlは返されている
redirectUrl: REDIRECT_URLS[userInfo.role],

// REDIRECT_URLSマッピング
const REDIRECT_URLS: Record<UserRole, string> = {
  provider: '/provider',
  system_admin: '/system-admin',
  data_admin: '/data-admin',
  experiment_admin: '/experiment-admin',
  experiment_worker: '/experiment-worker',
  mi_engineer: '/mi-engineer',
};
```

**フロントエンド（page.tsx - handleVerifyPin）**：
```typescript
// レスポンスにredirectUrlが含まれているが使用していない
const response = await authService.verifyPin(pinCode, sessionToken);

// ユーザー情報を設定してメニュー表示
setCurrentUser(response.user);
setCurrentMenuType(response.user.role as UserRole);
setAuthStep('authenticated');
```

### 3.2. 問題点
- バックエンドから返される`redirectUrl`をフロントエンドで使用していない
- 現在はメニューコンポーネントを表示する方式（SPAモード）
- URLが変わらないため、組織情報がURLに反映されない

## 4. 実装ステップ

### Phase 1: バックエンド修正（redirectUrlに組織ID付与）

- [ ] 例: `/experiment-admin?orgId=${userInfo.organizationId}`

### Phase 2: フロントエンド修正（URL遷移の実装）

- [ ] または、現在のメニュー表示方式を維持しながら`router.replace()`でURLのみ更新

## 6. 技術的詳細

### 6.1. バックエンド実装案

```typescript
// authController.ts - verifyPin関数内
const baseUrl = REDIRECT_URLS[userInfo.role];
const redirectUrl = `${baseUrl}?orgId=${encodeURIComponent(userInfo.organizationId)}`;

res.status(200).json({
  success: true,
  data: {
    user: { /* ... */ },
    session: { /* ... */ },
    redirectUrl: redirectUrl, // 組織ID付きURL
  },
  // ...
});
```

### 6.2. フロントエンド実装案（選択肢）

**案1: 実際にページ遷移する（推奨）**
```typescript
// page.tsx - handleVerifyPin
const response = await authService.verifyPin(pinCode, sessionToken);

// ユーザー情報をSessionStorageに保存
if (typeof window !== 'undefined') {
  sessionStorage.setItem('user', JSON.stringify(response.user));
}

// redirectUrlを使用して遷移
router.push(response.redirectUrl);
```

**案2: URLのみ更新してメニュー表示（現在の方式維持）**
```typescript
// page.tsx - handleVerifyPin
const response = await authService.verifyPin(pinCode, sessionToken);

// ユーザー情報を設定（現在と同じ）
setCurrentUser(response.user);
setCurrentMenuType(response.user.role as UserRole);
setAuthStep('authenticated');

// URLのみ更新（履歴には残さない）
router.replace(response.redirectUrl);
```

### 6.3. 推奨案
**案2（URLのみ更新）を推奨**
- 理由1: 現在のメニュー表示方式を維持できる（影響範囲が小さい）
- 理由2: SPA的な動作を保ちつつ、URLに組織情報を反映できる
- 理由3: 各ロール専用ページ（/experiment-admin等）の実装が不要

## 7. セキュリティ考慮事項

- [ ] 組織IDはすでに認証済みユーザーの情報であり、漏洩リスクは低い
- [ ] URLパラメータからの組織ID取得時は、セッション情報と照合して検証
- [ ] クロステナントアクセス防止のため、URL操作による不正アクセスを防ぐ

## 8. リスクと対策

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|----------|------|
| URLパラメータの組織IDとセッションの組織IDが不一致 | 中 | 低 | URLパラメータは表示用のみとし、認証情報（Cookie）を優先 |
| ブラウザの戻るボタンでログイン画面に戻った際の挙動 | 低 | 中 | 認証状態を確認してリダイレクト処理を実装 |
| 既存のメニュー切り替え機能への影響 | 低 | 低 | メニュー切り替え時もURLを更新するように修正 |

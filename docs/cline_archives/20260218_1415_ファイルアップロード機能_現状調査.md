# プロジェクト管理画面 ファイルアップロード機能 現状調査

## 調査日時
2026-02-18 14:15

## 調査目的
プロジェクト管理画面のファイルアップロード機能の現状を把握し、見直しのための情報を整理する

---

## 1. 概要

プロジェクト管理画面では、`BulkUploadDialog`コンポーネントを使用してファイルのアップロード機能を提供しています。

### 1.1 アップロードモード

以下の3つのモードをサポートしています：

1. **単一ファイル (single)**: 1つのファイルをアップロード
2. **一括ファイル (bulk)**: 複数のファイルを一度にアップロード
3. **フォルダ (folder)**: フォルダ構造を保持してアップロード

### 1.2 主要機能

- ドラッグ&ドロップによるファイル選択
- アップロード先フォルダの選択（カスケード形式）
- フォルダ構造の保持オプション
- アップロード進捗表示
- ファイルサイズ制限: 500MB/ファイル
- ファイル数制限: 100ファイル/バッチ

### 1.3 最近の更新（2026-02-18）

- **Phase1-2**: ファイルサイズ上限を500MBに引き上げ
- **Phase1-3**: 空フォルダプレースホルダー機能の追加
- **Phase2-1**: バッチ管理機能の統合
- **Phase2-3**: MAIMLファイル簡易解析機能の統合

**アップロード実行フロー**:
1. ファイルリストのバリデーション
2. FormData構築（files, uploadMode, targetPath, metadata）
3. `fileService.uploadFiles()`を呼び出し
4. 進捗イベントで`uploadState`を更新
5. 成功時に`onUploadComplete`コールバック実行
6. 2秒後に状態をリセット

## 3. バックエンド構造

### 3.1 ルート定義

#### fileAccessRoutes.ts
- **場所**: `backend/src/routes/fileAccessRoutes.ts`
- **エンドポイント**: `POST /api/v1/files/upload`

**リクエストバリデーション**:
- `uploadMode`: 'single' | 'bulk' | 'folder' のいずれか（必須）
- `targetPath`: 文字列、1〜1024文字（必須）
- `metadata`: オブジェクト（任意）
- `emptyFolders`: 文字列配列（任意、Phase1-3で追加）

**Multer設定**:
```typescript
const upload = multer({
  storage: multer.memoryStorage(),
  limits: {
    fileSize: 500 * 1024 * 1024, // 500MB
    fieldSize: 50 * 1024 * 1024,  // 50MB
    files: 100, // 最大100ファイル
  },
});
```

**ミドルウェアチェーン**:
1. `authMiddleware`: JWT認証
2. `upload.array('files')`: Multerファイルアップロード
3. バリデーション
4. `handleValidationErrors`: バリデーションエラー処理
5. `fileAccessController.uploadFiles`: コントローラー実行

### 3.3 サービス層

#### FileAccessService.ts
- **場所**: `backend/src/services/fileAccessService.ts`
- **クラス**: `FileAccessService`
- **主要メソッド**: `uploadFiles()`

**処理フロー（Phase2統合版）**:

1. **バリデーション**
   - ファイルが選択されているか確認
   - 単一ファイルモードで複数ファイルがないか確認
   - パストラバーサル攻撃対策（`..`, `//`のチェック）

2. **Phase2-1: バッチ作成**
   ```typescript
   const batch = await uploadBatchRepository.create({
     batchName,
     uploadType,
     organizationId,
     uploadedBy: userId,
     totalFiles: files.length,
   });
   ```

3. **ターゲットパスの正規化**
   - 先頭・末尾のスラッシュを削除

4. **Phase2-2: 並列処理でファイルアップロード**
   - `processConcurrently()`を使用して並列処理
   - デフォルト並列数: 5（環境変数で調整可能）
   - 各ファイルごとに以下を実行:
     - ファイル名のサニタイゼーション
     - ファイルパスの構築
     - storageService経由でS3/Swiftにアップロード
     - file_metadataテーブルに保存
     - Phase2-3: MAIMLファイルの場合は簡易解析

5. **Phase1-3: 空フォルダプレースホルダー作成**
   - emptyFoldersパラメータがある場合
   - `.folder_placeholder`ファイルを作成
   - S3/Swiftでは空フォルダを保持できないための対策

6. **結果集計**
   - 成功・失敗ファイル数をカウント
   - 合計サイズを計算

7. **Phase2-1: バッチ完了**
   ```typescript
   await uploadBatchRepository.update(batch.batchId, {
     status: finalStatus, // completed, completed_with_errors, failed
     endTime: new Date(),
   });
   ```

8. **結果返却**
   ```typescript
   return {
     uploadMode,
     files: uploadedFiles,
     summary: { totalFiles, successfulFiles, failedFiles, totalSize },
     emptyFolders: placeholderResults,
     batch: { batchId, batchName, status }
   };
   ```

**依存サービス**:
- `storageService`: S3/Swiftへのファイルアップロード
- `FileMetadataRepository`: file_metadataテーブルへの保存
- `uploadBatchRepository`: upload_batchテーブルへの記録
- `maimlAnalyzer`: MAIMLファイルの簡易解析（Phase2-3）
- `concurrencyControl`: 並列処理制御（Phase2-2）

## 4. データベース構造

### 4.1 file_metadata テーブル

アップロードされたファイルのメタデータを保存します。

**主要カラム**:
- `organization_id`: 組織ID（マルチテナント分離）
- `file_key`: S3キー（VARCHAR(2048)）
- `original_filename`: 元のファイル名（VARCHAR(512)）
- `file_size`: ファイルサイズ（BIGINT）
- `file_type`: MIMEタイプ（VARCHAR(255)）
- `uploaded_by`: アップロードユーザーID
- `is_maiml_file`: MAIMLファイルフラグ（BOOLEAN）
- `s3_bucket`: S3バケット名
- `upload_batch_id`: バッチID（Phase2-1で追加）
- `upload_method`: アップロード方法（'web_upload'など）

**Phase3-4対応**: VARCHAR長制限
- `file_key`: 2048文字を超える場合は切り詰め（`stringValidator.ts`）
- `original_filename`: 512文字を超える場合は切り詰め

### 4.2 upload_batch テーブル（Phase2-1）

アップロードバッチの管理情報を保存します。

**主要カラム**:
- `batch_id`: バッチID（PRIMARY KEY）
- `batch_name`: バッチ名
- `upload_type`: アップロードタイプ（'single', 'bulk', 'folder'）
- `organization_id`: 組織ID
- `uploaded_by`: アップロードユーザーID
- `total_files`: 総ファイル数
- `status`: バッチステータス（'in_progress', 'completed', 'completed_with_errors', 'failed'）
- `start_time`: 開始時刻
- `end_time`: 終了時刻
- `created_at`: 作成日時

**バッチAPI**:
- `GET /api/v1/files/batches`: バッチ履歴取得
- `GET /api/v1/files/batches/:batchId/progress`: バッチ進捗取得

## 6. 現在の問題点と改善検討事項

### 6.1 BulkUploadDialogの問題点

#### 問題1: モックデータによるフォルダ構造選択
**現状**:
```typescript
const folderStructureOptions: DefaultOptionType[] = [
  {
    value: 'dept_research',
    label: 'dept_research (研究部門)',
    children: [
      { value: 'project_001', label: 'project_001 (合金開発プロジェクト)' },
      // ... モックデータ
    ],
  },
  // ...
];
```

**問題**:
- ハードコーディングされたモックデータを使用
- 実際のプロジェクト一覧と連動していない
- 組織構造が固定されている

**改善案**:
- APIからプロジェクト一覧を動的に取得
- `getProjects()` APIと連携
- 選択中のプロジェクトを自動選択

#### 問題2: パスの不整合
**現状**:
```typescript
const selectedFolderPathString = `${userOrganization.id}/${selectedFolderPath.join('/')}`;
```

**問題**:
- フロントエンドで組織IDをパスに追加している
- バックエンドでも組織IDを付与するため、二重付与の可能性
- パス構造の管理が複雑

**改善案**:
- バックエンドで組織IDを自動付与
- フロントエンドは相対パスのみ送信
- 統一されたパス管理ルールの確立

#### 問題3: projectIdプロパティの未使用
**現状**:
```tsx
<BulkUploadDialog
  projectId={selectedProject?.id || ''}
  preselectedFolder={selectedProject?.folderName || ''}
/>
```

**問題**:
- `projectId`プロパティを受け取るが実際には使用していない
- `preselectedFolder`も使用されていない（モックデータを使用）

**改善案**:
- `projectId`を使用してアップロード先を特定
- モックデータを削除し、動的にパスを構築

### 6.2 API連携の問題点

#### 問題4: アップロード完了後の処理
**現状**:
```typescript
const handleUploadComplete = useCallback((result) => {
  console.log('Upload completed:', result);
  // TODO: ファイル一覧を更新
  handleRefresh();
}, [handleRefresh]);
```

**問題**:
- TODOコメントが残っている
- プロジェクト全体をリフレッシュしている（非効率）
- アップロードされたファイルのみを追加する方が効率的

**改善案**:
- アップロード結果からファイル一覧を取得
- 既存のファイルリストに新しいファイルを追加
- 不要なAPIコールを削減

### 6.3 パフォーマンスの問題点

#### 問題5: 進捗の粒度
**現状**:
- フロントエンド: Axiosの`onUploadProgress`でバイト単位の進捗
- バックエンド: バッチ単位の進捗のみ

**問題**:
- ファイル単位の進捗が取得できない
- 大量ファイルアップロード時に詳細な進捗が不明

**改善案**:
- WebSocketやServer-Sent Eventsでリアルタイム進捗通知
- ファイル単位の進捗情報を返す

### 6.4 UXの改善検討

#### 改善案1: ドラッグ&ドロップの強化
- プロジェクト一覧に直接ドロップ可能に
- ドロップ先のプロジェクトを自動選択

#### 改善案2: アップロード履歴の表示
- バッチ履歴APIを活用
- アップロード履歴タブの追加
- 失敗したファイルの再アップロード機能

#### 改善案3: プレビュー機能
- アップロード前にファイル内容をプレビュー
- MAIMLファイルの構造確認

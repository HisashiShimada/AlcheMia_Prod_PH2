### 🔍 問題が発生する可能性のあるケース（推測）

以下のケースで問題が発生する可能性があります：

#### ケースA: インタラクティブコマンド
**症状**: ユーザー入力を待つコマンドでハング

**例**:
```bash
# ❌ 悪い例 - ヒアドキュメント（EOF入力を待ち続ける）
cat >> file.txt << 'EOF'
content here
EOF

# ❌ 悪い例 - その他のインタラクティブコマンド
npm install  # 場合によって確認プロンプトが出る
docker exec -it container bash  # インタラクティブモード

# ✅ 良い例 - Clineのwrite_to_fileツールを使用
<write_to_file>
<path>file.txt</path>
<content>content here</content>
</write_to_file>

# ✅ 良い例 - echoとリダイレクト
echo "content here" >> file.txt

# ✅ 良い例 - 自動応答オプション
npm install --yes
docker exec container bash -c "command"  # 非インタラクティブ
```

**重要**: ヒアドキュメント（`<< EOF`）は**絶対に使用しないでください**。
Clineではファイル操作は`write_to_file`ツールまたは`echo`+リダイレクトを使用します。

#### ケースB: cd + 複数コマンドチェーン（重要）⚠️
**症状**: `cd`でディレクトリ移動後に複数コマンドを`&&`でチェーンするとPendingになる

**問題のあるパターン:**
```bash
# ❌ これらのパターンがPendingになりやすい
cd /path/to/frontend && npm run build 2>&1 | tail -30
cd backend && ls -lh routes/**/*.ts | tail -10
cd frontend && echo "Changed to: $(pwd)" && npm --version && echo "Done"
```

**原因:**
- `cd`によるディレクトリ変更とコマンドチェーンの組み合わせ
- Clineがカレントディレクトリの変更を追跡できない
- パイプや複雑なリダイレクトが絡むとさらに不安定

**✅ 解決策1: 括弧でサブシェル化（推奨）**
```bash
# cdの影響を括弧内に限定
(cd frontend && npm --version) && echo "npm version checked"
(cd backend && ls -lh src/routes/*.ts | tail -10)
```

**✅ 解決策2: 絶対パスを使用**
```bash
# cdを避けて絶対パスで実行
npm --prefix /home/mi_ito/mmdpf/frontend --version
ls -lh /home/mi_ito/mmdpf/backend/src/routes/*.ts | tail -10
```

**✅ 解決策3: コマンドを分割**
```bash
# Step 1: ディレクトリ移動を確認
cd frontend && pwd

# Step 2（別のコマンド実行で）: npmコマンド実行
npm --version
```

**✅ 解決策4: -C オプションを使用（lsの場合）**
```bash
# cdを使わずにディレクトリ指定
ls -lh -C backend src/routes/*.ts | tail -10
```

#### ケースC: 無限ループや永続プロセス
**症状**: 終了しないコマンド

**例**:
```bash
# 悪い例
npm run dev  # 開発サーバーが起動し続ける
docker-compose up  # フォアグラウンドで実行し続ける

# 良い例
npm run dev &  # バックグラウンド実行
docker-compose up -d  # デタッチモード
# または別のターミナルで実行
```

#### ケースC: 非常に大量の連続出力
**症状**: リアルタイムストリーミング出力でバッファオーバーフロー

**例**:
```bash
# 悪い例
npm install --verbose  # 大量のログ出力
webpack --watch  # 連続的な変更監視と出力

# 良い例
npm install --loglevel=error  # エラーのみ
webpack --watch > /tmp/webpack.log 2>&1  # ファイルにリダイレクト
```

#### ケースD: ネットワークタイムアウト
**症状**: ネットワーク接続待ちでタイムアウト

**例**:
```bash
# 悪い例
curl https://slow-api.example.com/data  # タイムアウト未設定

# 良い例
curl --max-time 30 https://api.example.com/data  # 30秒でタイムアウト
wget --timeout=30 https://api.example.com/data
```

## 3. ベストプラクティス

### 🎯 推奨されるコマンド記述方法

#### 0. echo+リダイレクトの注意点（重要）⚠️

**問題**: `echo "content" > file.txt` のようにリダイレクトだけを使うと、Clineが結果を正しくキャプチャできないことがあります。

**理由**:
- リダイレクト（`>` や `>>`）は標準出力をファイルに送る
- Clineは標準出力から結果を受け取る
- 出力がファイルにリダイレクトされると、Clineが受け取る出力がない
- 結果: "output could not be captured" と表示される

**✅ 解決策1: 確認メッセージを追加（推奨）**
```bash
# リダイレクト後に必ず確認メッセージを出力
echo "content" > /tmp/file.txt && echo "File created successfully"
echo "line1" >> /tmp/file.txt && echo "Line appended"

# ファイルの内容も確認
echo "content" > /tmp/file.txt && cat /tmp/file.txt && echo "Done"
```

**✅ 解決策2: teeコマンドを使用**
```bash
# ファイルと標準出力の両方に出力
echo "content" | tee /tmp/file.txt

# 追記の場合
echo "content" | tee -a /tmp/file.txt
```

**✅ 解決策3: write_to_fileツールを使用（最も確実）**
```xml
<write_to_file>
<path>/tmp/file.txt</path>
<content>content here</content>
</write_to_file>
```

**❌ 避けるべきパターン**
```bash
# これだけではClineが結果を受け取れない
echo "content" > /tmp/file.txt

# これも同様
echo "line1" >> /tmp/file.txt
echo "line2" >> /tmp/file.txt
```

**📝 推奨される記述パターン**
```bash
# パターンA: 作成 + 確認
echo "content" > /tmp/file.txt && echo "✓ File created"

# パターンB: 作成 + 内容表示
echo "content" > /tmp/file.txt && cat /tmp/file.txt

# パターンC: 複数行 + 確認
{
  echo "line1" > /tmp/file.txt
  echo "line2" >> /tmp/file.txt
  echo "line3" >> /tmp/file.txt
} && cat /tmp/file.txt && echo "✓ All lines added"

# パターンD: tee使用（最も明示的）
echo "content" | tee /tmp/file.txt
```

### 🎯 推奨される対応

#### 即時対応（問題が再発した場合）
1. **コマンドを分割する**
   - 長いコマンドチェーンを小さく分割
   - 各ステップで結果を確認

2. **出力を制限する**
   - head, tail, wc等で出力を制限
   - ファイルにリダイレクト

3. **タイムアウトを設定する**
   - timeout コマンドを使用
   - 適切な時間を設定（通常30-120秒）

4. **自動応答を使用する**
   - --yes, -y等のオプション
   - インタラクティブモードを避ける

#### 予防的対応（ベストプラクティス）
1. **コマンドテンプレートを使用する**
   - 本文書の「具体的な回避策テンプレート」を参照
   - プロジェクト固有のテンプレートを作成

2. **リソース監視を実施する**
   - 定期的にメモリ・ディスクを確認
   - 負荷が高い時は大量処理を避ける

3. **ログを記録する**
   - 重要なコマンドはログをファイルに保存
   - 問題発生時の調査に活用

### 📝 次のステップ

問題が再発した場合：
1. **どのコマンドで発生したか記録**
2. **このドキュメントの回避策を適用**
3. **それでも解決しない場合はVS Code/Clineの設定を確認**

## 概要

このレポートは、Reference版の`uploadRoutes.js`と現行版のファイルアップロード機能の差分を分析したものです。

### 分析対象

**Reference版（JavaScript）:**
- `backend/reference/routes/s3/uploadRoutes.js`
- Multer + AWS SDK v3を使用
- 4つの主要エンドポイント実装

**現行版（TypeScript）:**
- `backend/src/routes/fileAccessRoutes.ts` (ルート定義)
- `backend/src/routes/maimlRoutes.ts` (MAIML保存機能)
- `backend/src/controllers/fileAccessController.ts` (コントローラー)
- `backend/src/controllers/maimlController.ts` (MAIMLコントローラー)
- `backend/src/services/fileAccessService.ts` (ビジネスロジック)

### 主な発見事項

1. **機能統合の違い**: Reference版はS3専用ルート、現行版は汎用ファイルアクセスルートに統合
2. **アーキテクチャ**: Reference版はルート内に実装、現行版は3層アーキテクチャ（Route→Controller→Service）
3. **型安全性**: 現行版はTypeScriptで完全な型定義を実装
4. **欠落機能**: Reference版にある一部の機能が現行版には未実装

**機能概要:**

  organizationId: string,

## 詳細差分分析

### 1. MAIML保存機能の差分

#### Reference版の実装
```javascript
// POST /save
// - fileKeyとcontentを受け取る
// - 組織プレフィックスを自動付与
// - 既存ファイルの場合はDB更新、新規の場合はスキップ（メタデータ抽出時に作成）
// - maimlMetadataExtractor.extractSingleFile()を実行
// - キャッシュクリア
```

**特徴:**
- ✅ メタデータ自動抽出統合
- ✅ 既存/新規の判定ロジック
- ✅ 非同期メタデータ処理（失敗しても保存成功とする）

#### 現行版の実装
```typescript
// POST /api/v1/maiml/save
// - fileKeyとcontentを受け取る（fileKeyは実装で未使用）
// - maimlService.saveMaiML()を呼び出す
// - S3/Swift保存のみ実行
```

**特徴:**
- ❌ メタデータ抽出なし
- ❌ 既存ファイル更新検知なし
- ❌ キャッシュクリアなし

**影響:**
- MAIML編集後、DBの解析データが自動更新されない
- キャッシュが残るため、古い情報が表示される可能性

### 2. Draft保存機能の差分

#### Reference版の実装
```javascript
// isDraft: true の場合
// - draftMetadata構築（draftName, editState, autoSaveEnabled等）
// - file_metadata.is_draft = true
// - file_metadata.draft_metadata = draftMetadata
// - upload_source = 'draft_save'
```

**ユースケース:**
- エディタでの一時保存
- 自動保存機能
- 編集途中のファイル管理

#### 現行版の実装
- **未実装**
- maimlRoutes.tsに別途Draft管理API（`/api/v1/maiml/draft`）が存在
- しかし、ファイルアップロードとは別系統

**影響:**
- Draft保存とファイルアップロードが分離
- Reference版の統合Draft機能が使えない

### 3. データレイヤー機能の差分

#### Reference版の実装
```javascript
// dataLayer: 'raw', 'processed', 'archive' の場合
// - 専用のS3キー構造を生成
//   - raw: datalake/raw/{projectId}/{year}/{month}/{day}/{filename}
//   - processed: datalake/processed/{projectId}/{filename}
//   - archive: datalake/archive/{year}/{filename}
// - 組織プレフィックスを追加
```

**ユースケース:**
- データレイク構造でのファイル管理
- 生データ・処理済みデータ・アーカイブの分離
- プロジェクト別データ整理

#### 現行版の実装
- **未実装**
- targetPathで完全パスを指定する方式のみ

**影響:**
- データレイク構造が使えない
- フロントエンド側でパス生成ロジックが必要

### 4. バッチ管理機能の差分

#### Reference版の実装
```javascript
// すべてのアップロードでバッチ管理
// 1. バッチID生成（utils.generateBatchId()）
// 2. upload_batch作成（batch_name, upload_type, total_files）
// 3. 各ファイルにbatch_id紐付け
// 4. 完了時にバッチ更新（completed_files, failed_files, status）
```

**メリット:**
- アップロード履歴の追跡
- 一括操作の進捗管理
- エラー時のロールバック情報

#### 現行版の実装
- **未実装**
- バッチ概念なし

**影響:**
- アップロード履歴が個別ファイル単位
- 一括操作の全体管理ができない

### 5. 並列処理の差分

### Session 0-1: MAIMLメタデータ自動抽出機能

**日時**: Phase 1開始前  
**所要時間**: 2-3時間

#### 理解すべき内容

**1. 機能概要**
- MAIMLファイル保存時に自動的にメタデータをDBに抽出・保存
- `maimlMetadataExtractor.extractSingleFile()`を呼び出し
- 失敗しても保存は成功とする（非同期処理）

**2. Reference版の実装詳細**
```javascript
// POST /save エンドポイント内
// S3保存後にメタデータ抽出
if (validatedFileKey.toLowerCase().endsWith('.maiml')) {
  try {
    const maimlMetadataExtractor = require('../../services/maimlMetadataExtractor');
    const extractResult = await maimlMetadataExtractor.extractSingleFile(
      validatedFileKey, 
      organizationId
    );
    metadataExtracted = extractResult.success;
  } catch (metadataError) {
    console.error('メタデータ抽出エラー:', metadataError.message);
    // エラーでも保存は成功とする
  }
}
```

**3. 抽出されるメタデータ**
- Petri Net構造（place、transition、arc）
- ステレオタイプ情報
- メソッド情報（複数method対応）
- その他MAIML固有情報

**4. 既存ファイルの更新検知ロジック**
```javascript
const existingMetadata = await dbOperations.getFileMetadataByKey(validatedFileKey);
if (existingMetadata) {
  // 既存ファイル: 更新
  await dbOperations.updateFileMetadata(validatedFileKey, {...});
} else {
  // 新規ファイル: メタデータ抽出時に作成
  console.log('新規ファイルのためDB作成はメタデータ抽出時に実行');
}
```

**5. 現行版への適用方法**
- `maimlService.saveMaiML()`に統合
- TypeScript型定義追加

**6. 依存関係**

- DBスキーマ（file_metadata、maiml_analysis_results等）
- キャッシュマネージャーの実装状況

async function createEmptyFolderPlaceholders(
  organizationId: string,
  emptyFolders: string[]
): Promise<PlaceholderResult[]> {
  const results: PlaceholderResult[] = [];
  
  for (const folderPath of emptyFolders) {

      await storageService.uploadFile(

        file_category: 'placeholder',

          folderPath
        },

      });
      
      results.push({ folderPath, placeholderKey, success: true });
    } catch (error) {
      results.push({ folderPath, success: false, error: error.message });
    }
  }

## リスクと対策

### 高リスク項目

#### Risk 1: maimlMetadataExtractorの依存関係不足

**発生確率**: 中  
**影響度**: 高

**リスク内容**:
- `maimlMetadataExtractor`サービスが存在しない
- DBスキーマが不足している
- 実装方式がReference版と異なる

**対策**:
- Phase 0 Session 0-1で必ず依存関係を確認
- 不足がある場合は事前実装（Phase 0.5として1週間追加）
- 代替実装の検討（簡易版の実装）

**早期検知**:
- Week 1月曜に依存関係チェック実施
- 問題発見時は即座にエスカレーション

---

#### Risk 2: ファイルサイズ上限引き上げによるメモリ不足

**発生確率**: 中  
**影響度**: 高

**リスク内容**:
- 500MBファイルアップロードでメモリ不足
- 複数同時アップロードでサーバークラッシュ
- タイムアウト発生

**対策**:
- メモリストレージからディスクストレージへの変更検討
- アップロード同時接続数の制限
- サーバースペックの増強検討

**監視項目**:
- メモリ使用量のリアルタイム監視
- アップロード失敗率の追跡

---

#### Risk 3: DBマイグレーションの失敗

**発生確率**: 低  
**影響度**: 高

**リスク内容**:
- `upload_batch`テーブル作成失敗
- 既存データへの影響
- ロールバック不可

**対策**:
- 本番適用前に開発環境で十分にテスト
- マイグレーションのバックアップ取得
- ロールバックスクリプトの事前準備

**手順**:
1. 開発環境でマイグレーション実行
2. データ整合性確認
3. ロールバックテスト
4. 本番環境適用（メンテナンスウィンドウ内）

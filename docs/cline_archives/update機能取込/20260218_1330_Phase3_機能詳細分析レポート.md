## Task 3-1: Draft保存機能統合

### Reference版の実装

```javascript
// V1.18α拡張パラメータ
v118Params = {
  isDraft: req.body.isDraft === 'true' || req.body.isDraft === true,
  draftName: req.body.draftName || null,
  editState: req.body.editState ? JSON.parse(req.body.editState) : null,
  // ...
};

// Draft用バッチ名
const batchName = v118Params.isDraft 
  ? `Draft Save - ${v118Params.draftName || req.file.originalname}`
  : `Single File Upload - ${req.file.originalname}`;

// Draft用アップロードタイプ
upload_type: v118Params.isDraft ? 'draft' : 'single',

// Draft用メタデータ
let draftMetadata = {};
if (v118Params.isDraft) {
  draftMetadata = {
    draftName: v118Params.draftName || '名称未設定',
    editState: v118Params.editState || {},
    autoSaveEnabled: req.body.autoSaveEnabled !== 'false',
    lastAutoSave: new Date().toISOString(),
    editDuration: parseInt(req.body.editDuration) || 0,
    changeCount: parseInt(req.body.changeCount) || 0
  };
}

// DBメタデータに保存
await dbOperations.saveFileMetadata({
  // ...
  is_draft: v118Params.isDraft,
  draft_metadata: draftMetadata,
  last_edit_timestamp: v118Params.isDraft ? new Date() : null,
  // ...
});

// レスポンス
res.json({
  message: v118Params.isDraft ? '一時保存完了' : 'ファイルアップロード完了',
  file: {
    isDraft: v118Params.isDraft,
    draftName: v118Params.draftName,
    // ...
  }
});
```

### 機能概要

**目的**: MAIMLエディタでの編集中の一時保存（Draft Save）をファイルアップロードAPIで処理

**パラメータ**:
- `isDraft`: Draft保存かどうか（boolean）
- `draftName`: Draft名称
- `editState`: 編集状態（JSON）
- `autoSaveEnabled`: 自動保存有効化
- `editDuration`: 編集時間（秒）
- `changeCount`: 変更回数

**データベース保存内容**:
- `is_draft`: Draftフラグ
- `draft_metadata`: Draft関連メタデータ（JSON）
- `last_edit_timestamp`: 最終編集日時
- `upload_type`: 'draft'

### 現行版の状況

**既存の実装**:
- 専用Draft API: `/api/v1/maiml/draft`（別エンドポイント）
- MAIML固有の機能として分離

### 取込判断

#### メリット
✅ **統合による利点**:
- アップロードAPIに統一
- 一貫したインターフェース
- ファイル管理の一元化

#### デメリット
❌ **統合のリスク**:
- MAIMLエディタ固有の機能を汎用アップロードAPIに混在
- 関心の分離が不明確
- APIの複雑化

### 推奨判断

**❌ 取込不要（現状維持を推奨）**

**理由**:
1. **関心の分離**: Draft保存はMAIMLエディタ固有の機能
2. **既存API**: 専用エンドポイントが既に存在し機能している
3. **複雑化回避**: アップロードAPIに編集状態を持ち込むのは設計上不適切

**代替案**:
- 現在の`/api/v1/maiml/draft`を維持
- 必要に応じてDraft APIを拡張

## Task 3-2: データレイヤー機能

### Reference版の実装

```javascript
// V1.18α拡張パラメータ
v118Params = {
  // ...
  dataLayer: req.body.dataLayer || 'uploads',
  projectId: req.body.projectId || null,
  dataCategory: req.body.dataCategory || null
};

// データレイヤーのバリデーション
const validDataLayers = ['uploads', 'raw', 'processed', 'archive'];
if (!validDataLayers.includes(v118Params.dataLayer)) {
  throw new Error(`Invalid dataLayer: ${v118Params.dataLayer}`);
}

// データレイヤーごとのパス生成
let dataLayerPath;
switch (v118Params.dataLayer) {
  case 'raw':
    // datalake/raw/{projectId}/{year}/{month}/{day}/{filename}
    dataLayerPath = `datalake/raw/${projectPrefix}${year}/${month}/${day}/${sanitizedFilename}`;
    break;
  case 'processed':
    // datalake/processed/{projectId}/{filename}
    dataLayerPath = `datalake/processed/${projectPrefix}${sanitizedFilename}`;
    break;
  case 'archive':
    // datalake/archive/{year}/{filename}
    dataLayerPath = `datalake/archive/${year}/${sanitizedFilename}`;
    break;
  default:
    // uploads/{targetFolder}/{filename}（デフォルト）
    dataLayerPath = null;
}

// DBメタデータに保存
await dbOperations.saveFileMetadata({
  // ...
  data_layer: v118Params.dataLayer,
  // ...
});

// レスポンス
res.json({
  file: {
    dataLayer: v118Params.dataLayer,
    // ...
  }
});
```

### 機能概要

**目的**: データレイク構造をサポートし、データの成熟度に応じた階層管理

**データレイヤー種別**:
1. **raw** - 生データ
   - `datalake/raw/{projectId}/{year}/{month}/{day}/{filename}`
   - 日付ベースの階層化
   - プロジェクトごとに分離

2. **processed** - 処理済みデータ
   - `datalake/processed/{projectId}/{filename}`
   - プロジェクトごとに分離

3. **archive** - アーカイブデータ
   - `datalake/archive/{year}/{filename}`
   - 年別に保存

4. **uploads** - 通常アップロード（デフォルト）
   - `{targetFolder}/{filename}`
   - 既存の方式

### 現行版の状況

**既存の実装**:
- `targetPath`パラメータによるフォルダ指定
- フロントエンドが完全なパスを生成
- シンプルなフォルダ構造

**例**:
```typescript
// 現行版
targetPath = 'projects/sample_project/data'

// データレイヤー版
dataLayer = 'raw'
projectId = 'sample_project'
→ 'datalake/raw/sample_project/2026/02/18/data.csv'
```

### 取込判断

#### メリット
✅ **データレイクのメリット**:
- データの成熟度を明示的に管理
- 日付ベースの自動階層化（raw）
- データガバナンスの向上

#### デメリット
❌ **実装のコスト**:
- バックエンドでパス生成ロジックが複雑化
- DBスキーマ変更（data_layerカラム追加）
- フロントエンドの対応が必要

### 推奨判断

**⏸️ 要件確認後に判断**

**判断ポイント**:
1. **データ管理方針**: データレイク構造が必要か？
2. **現状の問題**: `targetPath`方式で不十分な点は？
3. **運用要件**: 日付ベースの階層化が必要か？

**推奨アプローチ**:
- Phase 3-2として別途検討

## Task 3-4: VARCHAR長制限対応

### Reference版の実装

```javascript
// フィールド長制限確認用ユーティリティ関数
function truncateField(value, maxLength, fieldName = 'field') {
  if (!value) return value;
  
  const stringValue = String(value);
  if (stringValue.length <= maxLength) return stringValue;
  
  const truncated = stringValue.substring(0, maxLength);
  console.warn(`[VARCHAR警告] ${fieldName}が${maxLength}文字を超過: "${stringValue}" → "${truncated}"`);
  return truncated;
}

// 使用例
const fileMetadata = await dbOperations.saveFileMetadata({
  file_extension: truncateField(fileExtension, 10, 'file_extension'),
  file_category: truncateField(fileCategory, 20, 'file_category'),
  parent_folder_path: truncateField(path.dirname(validatedPath), 255, 'parent_folder_path'),
  search_keywords: [
    truncateField(file.originalname, 50, 'filename'), 
    truncateField(fileCategory, 20, 'category'), 
    truncateField(fileExtension, 10, 'extension')
  ]
});
```

### 機能概要

**目的**: 長いフィールド値を自動的に切り詰めてDBエラーを防止

**対象フィールド**:
- `file_extension`: 10文字
- `file_category`: 20文字
- `parent_folder_path`: 255文字
- `search_keywords`: 50文字（個別）

**処理内容**:
1. フィールド値の長さをチェック
2. 上限を超える場合は切り詰め
3. 警告ログを出力
4. 切り詰めた値を返却

### 現行版の状況

**現在の実装**:
- バリデーションなし
- DB制約でエラー発生の可能性

**潜在的な問題**:
```typescript
// 長いファイル名の場合
fileName: 'very_long_filename_that_exceeds_database_varchar_limit_and_causes_error.maiml'
→ DBエラー: value too long for type character varying(255)
```

### 取込判断

#### メリット
✅ **切り詰め処理のメリット**:
- DBエラーの防止
- ユーザー体験の向上（エラーではなく警告）
- データ整合性の維持

#### デメリット
❌ **切り詰めのリスク**:
- 情報の損失
- ファイル名の一意性が失われる可能性

### 推奨判断

**✅ 取込推奨**

**実装方針**:
1. `backend/src/utils/stringValidator.ts` 作成
2. `truncateField()` 関数を実装
3. fileAccessService.tsで使用

**実装例**:
```typescript
// backend/src/utils/stringValidator.ts
export function truncateField(
  value: string | null | undefined,
  maxLength: number,
  fieldName = 'field'
): string | null {
  if (!value) return value as null;
  
  const stringValue = String(value);
  if (stringValue.length <= maxLength) return stringValue;
  
  const truncated = stringValue.substring(0, maxLength - 3) + '...';
  console.warn(
    `⚠️ [Validator] ${fieldName}が${maxLength}文字を超過: "${stringValue.substring(0, 50)}..." → "${truncated}"`
  );
  return truncated;
}

// fileAccessService.tsで使用
import { truncateField } from '../utils/stringValidator';

const fileMetadata = {
  original_filename: truncateField(sanitizedFileName, 255, 'original_filename'),
  file_category: truncateField(fileCategory, 50, 'file_category'),
  // ...
};
```

**推定工数**: 1日

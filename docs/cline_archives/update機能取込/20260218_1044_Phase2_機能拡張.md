## Task 2-1: バッチ管理機能

**期間**: 10日間

### Step 0: 機能説明セッション（実装開始前）

**所要時間**: 2-3時間

#### 理解すべき内容

1. **バッチ管理の目的**
   - アップロード履歴の追跡
   - 一括操作の進捗管理
   - エラー時のロールバック情報

2. **Reference版のバッチフロー**
   ```javascript
   // 1. バッチID生成
   batchId = utils.generateBatchId();
   
   // 2. バッチ作成
   await dbOperations.createUploadBatch({
     batch_id: batchId,
     batch_name: batchName || `Upload ${new Date().toISOString()}`,
     uploaded_by: userId,
     upload_type: 'single' | 'bulk' | 'folder',
     total_files: files.length
   });
   
   // 3. 各ファイルに紐付け
   await dbOperations.saveFileMetadata({
     ...fileMetadata,
     upload_batch_id: batchId
   });
   
   // 4. バッチ完了
   await dbOperations.updateUploadBatch(batchId, {
     completed_files: successCount,
     failed_files: failCount,
     status: 'completed' | 'failed' | 'completed_with_errors',
     end_time: new Date()
   });
   ```

3. **DBテーブル設計**
   ```sql
   CREATE TABLE upload_batch (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     batch_id VARCHAR(100) UNIQUE NOT NULL,
     batch_name VARCHAR(255) NOT NULL,
     uploaded_by UUID NOT NULL REFERENCES users(id),
     organization_id UUID NOT NULL REFERENCES organizations(id),
     upload_type VARCHAR(50) NOT NULL,
     total_files INTEGER NOT NULL,
     completed_files INTEGER DEFAULT 0,
     failed_files INTEGER DEFAULT 0,
     status VARCHAR(50) NOT NULL DEFAULT 'in_progress',
     start_time TIMESTAMP NOT NULL DEFAULT NOW(),
     end_time TIMESTAMP,
     created_at TIMESTAMP NOT NULL DEFAULT NOW(),
     updated_at TIMESTAMP NOT NULL DEFAULT NOW()
   );
   
   ALTER TABLE file_metadata 
   ADD COLUMN upload_batch_id VARCHAR(100) REFERENCES upload_batch(batch_id);
   ```

4. **現行版への統合方法**
   - Repositoryパターンでのバッチ管理実装
   - TypeScript型定義
   - トランザクション処理

## Task 2-2: 並列処理最適化

**期間**: 5日間

### Step 0: 機能説明セッション（実装開始前）

**所要時間**: 2時間

#### 理解すべき内容

1. **Reference版の並列処理**
   ```javascript
   const concurrency = 5;
   const chunks = [];
   for (let i = 0; i < files.length; i += concurrency) {
     chunks.push(files.slice(i, i + concurrency));
   }
   
   for (const chunk of chunks) {
     const chunkPromises = chunk.map(async (file) => {
       // ファイル処理
     });
     await Promise.all(chunkPromises);
   }
   ```

2. **なぜ並列制御が必要か**
   - メモリ使用量の制御
   - S3/Swift APIの同時接続数制限
   - サーバーCPU/メモリリソースの最適利用

3. **並列数の決定**
   - Reference版: 5並列
   - サーバースペックに応じた調整
   - 動的な並列数制御の検討

4. **エラーハンドリング**
   ```javascript
   try {
     await uploadFile(file);
     results.successful.push(...);
   } catch (error) {
     results.failed.push({
       originalName: file.originalname,
       error: error.message
     });
   }
   ```

## Task 2-3: MAIML解析統合

**期間**: 5日間

### Step 0: 機能説明セッション（実装開始前）

**所要時間**: 1.5時間

#### 理解すべき内容

1. **アップロード時の簡易解析**
   ```javascript
   function analyzeMaimlFile(content) {
     const transitionMatches = content.match(/<transition/g) || [];
     const placeMatches = content.match(/<place/g) || [];
     
     return {
       isValid: content.includes('<maiml') || content.includes('<pnml'),
       transitionsCount: transitionMatches.length,
       placesCount: placeMatches.length,
       version: null
     };
   }
   ```

2. **既存の解析APIとの関係**
   - `/api/v1/maiml/parse` - 既存の詳細解析API
   - `/api/v1/maiml/parse-petri-net-structure` - ペトリネット構造解析
   - アップロード時の簡易解析との使い分け

3. **レスポンスへの統合**
   ```javascript
   {
     success: true,
     file: {
       ...fileInfo,
       isMaimlFile: true,
       maimlAnalysis: {
         isValid: true,
         transitionsCount: 10,
         placesCount: 8
       }
     }
   }
   ```

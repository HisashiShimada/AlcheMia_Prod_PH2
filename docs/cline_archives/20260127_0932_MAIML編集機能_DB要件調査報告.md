## 🔍 実装コードの分析

### maimlService.ts の実装状況

```typescript
// 編集セッション管理（メモリ管理）
const editSessions = new Map<string, EditSession>();

interface EditSession {
  sessionId: string;
  fileKey: string;
  fileName: string;
  userId: string;
  startTime: Date;
  lastActivity: Date;
  changes: any[];
  locked: boolean;
}
```

**重要な発見:**
- 編集セッションは**メモリ内Map**で管理
- データベースに永続化されていない
- サーバー再起動時にセッション情報が失われる

### 実装済み機能

1. ✅ **MAIML解析** - DB不要（メモリ内処理）
2. ✅ **ファイル保存** - file_metadataで対応可能
3. ✅ **ファイル読込** - file_metadataで対応可能
4. ✅ **バリデーション** - DB不要（メモリ内処理）
5. ⚠️ **編集セッション管理** - メモリ管理（永続化なし）
6. ⚠️ **バックアップ管理** - S3のみ（DBでの管理なし）

## ⚠️ 発見された課題

### 課題1: 編集セッション情報の永続化不足

**現状:**
- 編集セッションはメモリ内Mapで管理
- サーバー再起動時に全セッション情報が失われる

**影響:**
- 複数ユーザーの同時編集制御が不完全
- 編集ロック情報が失われる可能性
- 編集履歴が記録されない

**推奨対応:**
- `edit_session` テーブルの追加を検討（優先度: 中）

---

### 課題2: Draft/一時保存機能のDB対応

**現状:**
- フロントエンド側でDraft機能を実装（localStorage）
- バックエンドにDraft保存APIなし

**影響:**
- ブラウザ間でDraftが共有されない
- バックアップがブラウザに依存

**推奨対応:**
- `maiml_draft` テーブルの追加を検討（優先度: 低）

---

### 課題3: バックアップ管理の可視性不足

**現状:**
- バックアップはS3に保存
- DBでのバックアップ履歴管理なし

**影響:**
- バックアップ一覧の取得にS3クエリが必要
- リストア操作の履歴が記録されない

**推奨対応:**
- `maiml_backup` テーブルの追加を検討（優先度: 低）

## 💡 提案: 追加テーブル定義（オプション）

### 提案1: edit_session テーブル（優先度: 中）

**目的**: 編集セッション情報の永続化

```sql
CREATE TABLE edit_session (
    session_id VARCHAR(100) PRIMARY KEY,
    organization_id UUID NOT NULL,
    project_id UUID NOT NULL,
    file_key VARCHAR(500) NOT NULL,
    user_id UUID NOT NULL,
    started_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_activity TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP NOT NULL,
    is_locked BOOLEAN NOT NULL DEFAULT TRUE,
    changes_count INTEGER NOT NULL DEFAULT 0,
    session_data JSONB,
    FOREIGN KEY (organization_id, project_id) 
        REFERENCES project(organization_id, project_id) ON DELETE CASCADE
);

CREATE INDEX idx_edit_session_organization_id ON edit_session(organization_id);
CREATE INDEX idx_edit_session_project_id ON edit_session(project_id);
CREATE INDEX idx_edit_session_user_id ON edit_session(user_id);
CREATE INDEX idx_edit_session_expires_at ON edit_session(expires_at);
```

**メリット:**
- サーバー再起動時もセッション情報が保持される
- 複数サーバー間でのセッション共有が可能
- 編集履歴の追跡が可能

**デメリット:**
- 実装コストが増加
- パフォーマンスへの影響（DB I/O）

**推奨**: Phase 2以降での実装を検討

### 提案2: maiml_draft テーブル（優先度: 低）

**目的**: Draft（一時保存）の永続化

```sql
CREATE TABLE maiml_draft (
    organization_id UUID NOT NULL,
    project_id UUID NOT NULL,
    user_id UUID NOT NULL,
    draft_id VARCHAR(50) NOT NULL,
    draft_content TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (organization_id, project_id, user_id, draft_id),
    FOREIGN KEY (organization_id, project_id) 
        REFERENCES project(organization_id, project_id) ON DELETE CASCADE
);

CREATE INDEX idx_maiml_draft_organization_id ON maiml_draft(organization_id);
CREATE INDEX idx_maiml_draft_user_id ON maiml_draft(user_id);
CREATE INDEX idx_maiml_draft_updated_at ON maiml_draft(updated_at);
```

**メリット:**
- ブラウザ間でDraftが共有される
- サーバー側でDraft管理が可能

**デメリット:**
- 現在のフロントエンド実装と重複
- ストレージコストが増加

**推奨**: 必要に応じて実装（現状のlocalStorage方式でも十分）

### 提案3: maiml_backup テーブル（優先度: 低）

**目的**: バックアップ履歴の管理

```sql
CREATE TABLE maiml_backup (
    organization_id UUID NOT NULL,
    project_id UUID NOT NULL,
    backup_id VARCHAR(50) NOT NULL,
    file_key VARCHAR(500) NOT NULL,
    backup_path VARCHAR(500) NOT NULL,
    backup_size BIGINT,
    created_by UUID NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    backup_type VARCHAR(20) DEFAULT 'auto', -- auto, manual
    PRIMARY KEY (organization_id, project_id, backup_id),
    FOREIGN KEY (organization_id, project_id) 
        REFERENCES project(organization_id, project_id) ON DELETE CASCADE
);

CREATE INDEX idx_maiml_backup_organization_id ON maiml_backup(organization_id);
CREATE INDEX idx_maiml_backup_created_at ON maiml_backup(created_at);
```

**メリット:**
- バックアップ一覧の高速取得
- リストア履歴の追跡

**デメリット:**
- S3とDBの二重管理
- 同期ずれのリスク

**推奨**: 必要に応じて実装（現状のS3のみでも十分）

## 🎯 最終結論

### ✅ 現状で問題なし（追加テーブル不要）

**理由:**

1. **基本機能は既存テーブルで対応可能**
   - プロジェクト管理: `project` テーブル
   - ファイルメタデータ: `file_metadata` テーブル
   - イベントログ: `maiml_event_log` テーブル

2. **編集セッション管理はメモリベースで十分**
   - 現状のMap方式で動作可能
   - 複雑なセッション管理は不要
   - 必要に応じてRedis等の外部KVSを検討

3. **Draft機能はフロントエンドで実装済み**
   - localStorageによる一時保存
   - ユーザー体験を損なわない

4. **バックアップはS3管理で十分**
   - S3自体がバージョン管理機能を持つ
   - DBでの二重管理は不要

### ⚠️ 将来的な検討事項（Phase 2以降）

1. **マルチサーバー環境での編集セッション共有**
   - Redis等のKVSを検討
   - edit_sessionテーブルの追加を検討

2. **編集履歴の詳細追跡**
   - `maiml_event_log` の活用を強化
   - 監査ログとしての機能追加

3. **Draft機能のサーバー側実装**
   - ユーザー要望に応じて検討
   - maiml_draftテーブルの追加を検討

## 🎯 Phase 6の目的

**「MAIMLデータの型変換を最小化し、パース時の型定義を直接利用する」**

### Phase 6の背景

Phase 5完了後、ユーザーから以下のフィードバックを受領：

> **ユーザー要望**:
> - Maimlデータを型定義にはめ込むにあたって何度も別の型に入れなおすことは防ぎたい
> - 基本はパースした際の型定義をそのまま使い
> - どうしてもそのままで使えない場合のみ新しい型を使いたい
> - 型拡張だと全容がわかりづらくなるので、XSD形式にプラスの情報が必要なものに関しては別の型として作ってください

### 現状の問題点

```
MAIMLファイル（XML）
    ↓ パース（xml-js）
MaimlRoot（XSD準拠型） ← これをそのまま使いたい
    ↓ 変換1（maimlParserTyped内）
TransitionInfo, TemplateInfo（派生型）
    ↓ 変換2（petriNetExtractor）
TemplateItem, TemplateMapEntry（エディタ型）
    ↓ 使用
PetriNetEditor
```

**問題**:
- ❌ 変換が2回発生している
- ❌ 同じ概念を表す型が3つ存在
- ❌ 型変換のコストが発生

---

## 📋 Phase 6の設計原則（重要）

### 4つの基本原則

1. ✅ **基本はパース時の型定義（XSD準拠型）をそのまま使う**
2. ✅ **何度も別の型に入れ直すことを防ぐ**
3. ✅ **追加情報が必要な場合のみ新しい型を作る**
4. ✅ **型継承（extends）は使わず、全容を明示的に記述する**

### 型定義の3パターン

#### パターン1: XSD準拠型をそのまま使用（型エイリアス）

```typescript
// ✅ 追加情報が不要な場合
import { Template } from '@/types/maiml-unified';

// 型エイリアスで使用（型変換不要）
export type TemplateInfo = Template;
```

**適用条件**: XSD準拠型で十分な場合  
**メリット**: 型変換なし、パフォーマンス最高

#### パターン2: 別の型として全容を明示（推奨）

```typescript
// ✅ 追加情報が必要な場合（extendsは使わない）
export interface TransitionWithMetadata {
  // === XSD準拠型のフィールド（全て明示）===
  id: string;
  name?: string;
  label?: string;
  methodId: string;
  program?: {
    instruction?: string;
  };
  // ... Transition型の全フィールドをここに明示的に記述
  
  // === 追加フィールド（Phase 3-4で追加）===
  displayName?: string;
  isExperimentRelevant?: boolean;
  hasInstruction?: boolean;
}
```

**適用条件**: XSD準拠型 + 追加情報が必要な場合  
**メリット**: 型の全容が一目でわかる、保守性が高い

#### パターン3: 型継承（❌ 非推奨）

```typescript
// ❌ 避ける: extendsを使った型拡張
interface ExtendedTransition extends Transition {
  displayName?: string;
  isExperimentRelevant?: boolean;
  hasInstruction?: boolean;
}
```

**問題点**: 
- 全容がわかりづらい
- Transition型の定義を見に行く必要がある
- 保守性が低い

## ⚠️ 注意事項

### DO（推奨）

✅ **XSD準拠型を最優先で使用**
- Template、Transition、Place等の基本型

✅ **追加情報不要なら型エイリアス**
- `export type TemplateInfo = Template;`

✅ **追加情報必要なら別の型として全容を明示**
- `extends`は使わない
- XSD準拠型のフィールドを全て明示的にコピー

✅ **段階的に移行する**
- Phase 6-1から順番に実施
- 各ステップで動作確認

✅ **後方互換性を一定期間維持**
- 既存コードが動作し続けることを確認

### DON'T（非推奨）

❌ **同じ概念を表す型を複数作らない**

❌ **不要な型変換を行わない**

❌ **extendsを使った型拡張は避ける**
- 理由: 全容がわかりづらい

❌ **XSD準拠型と異なる構造の独自型を作らない**

❌ **一度に全てを変更しない**
- 段階的に実施すること

# mmdpf Dockerで動かす必要のあるコンテナ一覧

## 作成日時
2026-01-14 08:33

## 概要
WSL2上のUbuntuでDockerを使用してmmdpfプロジェクトを実行するために必要なコンテナと、その理由をまとめます。

---

## 必須コンテナ（5つ）

### 1. **PostgreSQL (postgres)**
```yaml
image: postgres:16-alpine
ports: 5432:5432
```

#### 必要な理由
- **役割**: アプリケーションのメインデータベース
- **保存データ**: 
  - ユーザー情報（認証・認可）
  - 組織（organization）データ
  - プロジェクト・実験記録
  - ファイルメタデータ
  - セッション情報
  - マスタデータ（コード、属性、機器情報など）
- **マルチテナント対応**: organization_idによるデータ分離が必要
- **永続化**: `postgres-data`ボリュームでデータを永続化

#### なぜDockerで動かすのか
✅ バージョン管理が容易（PostgreSQL 16を固定）
✅ 開発環境と本番環境の差異を最小化
✅ チーム全体で同じDB環境を共有可能
✅ 初期化スクリプト（DDL）の自動実行が可能
✅ ヘルスチェックによる稼働状態監視

---

### 2. **OpenStack Swift (swift)**
```yaml
image: bouncestorage/swift-aio:latest
ports: 8080:8080
```

#### 必要な理由
- **役割**: オブジェクトストレージ（ファイル保存）
- **保存データ**:
  - 実験データファイル（CSV、画像、TIFF等）
  - MAIMファイル（XML形式）
  - 実験記録の添付ファイル
  - エクスポートされたドキュメント
- **パス構造**: `org_{organization_id}/projects/{project_id}/...`でテナント分離
- **S3互換API**: AWS S3と同等のAPIで操作可能

#### なぜDockerで動かすのか
✅ 本番環境（オンプレミス）と同じストレージシステムを使用
✅ S3のような外部サービスに依存しない
✅ ローカルでのファイル操作テストが可能
✅ マルチテナント分離のテストが可能
✅ 開発環境でコスト削減（AWS S3不要）

#### 補足
- 本番環境（クラウド）ではAWS S3を使用
- 本番環境（オンプレ）ではOpenStack Swiftを使用
- 開発環境でSwiftを使うことで両方に対応可能

---

### 3. **Backend API Server (backend)**
```yaml
build: ./backend/Dockerfile
ports: 3001:3001
```

#### 必要な理由
- **役割**: RESTful APIサーバー（ビジネスロジック層）
- **主な機能**:
  - 認証・認可（JWT + セッション）
  - マルチテナント分離
  - データベースアクセス
  - ファイルアップロード/ダウンロード（Swift連携）
  - MAIML XMLパース・編集
  - Petri Net処理
- **技術スタック**: Node.js 24+ / Express.js / TypeScript
- **ミドルウェア**: 認証、テナント分離、権限チェック、レート制限

#### なぜDockerで動かすのか
✅ Node.jsのバージョンを固定（v24）
✅ 依存ライブラリの環境差異を防止
✅ PostgreSQL・Swiftとのネットワーク接続を簡単に設定
✅ 環境変数による設定管理
✅ ホットリロード（開発時は`volumes`でコードを同期）
✅ ヘルスチェックによるAPI稼働監視

---

### 4. **Frontend (frontend)**
```yaml
build: ./frontend/Dockerfile
ports: 3000:3000
```

#### 必要な理由
- **役割**: Webアプリケーションのフロントエンド
- **主な機能**:
  - ログイン画面（PIN認証含む）
  - ロール別メニュー（5種類）
  - プロジェクト管理
  - 実験記録・進捗確認
  - Petri Net可視化エディタ
  - MAIML XMLエディタ
  - ファイルビューア
- **技術スタック**: Next.js 15+ / React 18 / TypeScript / Ant Design v6

#### なぜDockerで動かすのか
✅ Node.jsのバージョンを固定
✅ Next.jsのビルド環境を統一
✅ バックエンドとのネットワーク接続を簡単に設定
✅ 環境変数による設定管理（API URLなど）
✅ ホットリロード（開発時）
✅ 本番環境と同じコンテナイメージでデプロイ可能

---

### 5. **Nginx (nginx)** ※現在はコメントアウト
```yaml
image: nginx:alpine
ports: 80:80, 443:443
```

#### 必要な理由（本番環境）
- **役割**: リバースプロキシ + セキュリティゲートウェイ
- **主な機能**:
  - HTTPSリダイレクト（HTTP→HTTPS）
  - クライアント証明書認証（mTLS）
  - リバースプロキシ（フロントエンド/バックエンドへのルーティング）
  - 静的ファイル配信
  - セキュリティヘッダー設定
  - レート制限（DDoS対策）
- **証明書管理**:
  - CA証明書（`certs/ca/ca.crt`）
  - サーバー証明書（`certs/server/`）
  - クライアント証明書検証

#### なぜDockerで動かすのか
✅ Nginx設定ファイルのバージョン管理
✅ 証明書の統一管理
✅ セキュリティ設定の一元化
✅ 本番環境と同じ構成でテスト可能
✅ ヘルスチェックによる稼働監視

#### 開発環境では無効化している理由
- 開発中はフロントエンド（3000）とバックエンド（3001）に直接アクセス
- クライアント証明書認証のテストは必要な時だけ有効化
- HTTPS設定のオーバーヘッドを削減

## コンテナ間の依存関係

```
┌─────────────────────────────────────────────────┐
│              Nginx (本番環境)                     │
│    - HTTPSリダイレクト                            │
│    - クライアント証明書認証                        │
│    - リバースプロキシ                             │
└──────────────┬──────────────────────────────────┘
               │
       ┌───────┴────────┐
       ↓                ↓
┌─────────────┐   ┌─────────────┐
│  Frontend   │   │  Backend    │
│  (Next.js)  │←──│ (Express)   │
│  Port 3000  │   │  Port 3001  │
└─────────────┘   └──────┬──────┘
                         │
                  ┌──────┴────────┐
                  ↓               ↓
           ┌──────────┐    ┌────────────┐
           │PostgreSQL│    │   Swift    │
           │Port 5432 │    │  Port 8080 │
           └──────────┘    └────────────┘
```

### 依存関係の説明
1. **Frontend** → Backend（API呼び出し）
2. **Backend** → PostgreSQL（データ保存・取得）
3. **Backend** → Swift（ファイルアップロード・ダウンロード）
4. **Nginx** → Frontend, Backend（リバースプロキシ）

### docker-compose.ymlでの依存関係設定
```yaml
frontend:
  depends_on:
    - backend

backend:
  depends_on:
    - postgres
    - swift

nginx:
  depends_on:
    - backend
    - frontend
```

## データ永続化（Volumes）

### 1. postgres-data
```yaml
volumes:
  postgres-data:
    name: mmdpf_postgres-data
```
- PostgreSQLのデータファイルを永続化
- コンテナを削除してもデータは保持される
- マウント先: `/var/lib/postgresql/data`

### 2. swift-data
```yaml
volumes:
  swift-data:
    name: mmdpf_swift-data
```
- Swiftのオブジェクトストレージデータを永続化
- アップロードされたファイルを保持
- マウント先: `/srv`

---

## ネットワーク設定

```yaml
networks:
  mmdpf-network:
    name: mmdpf-network
    driver: bridge
```

### 役割
- 全コンテナが同じネットワークに所属
- コンテナ名でDNS解決が可能
  - 例: バックエンドから`postgres:5432`でDB接続
  - 例: バックエンドから`swift:8080`でストレージアクセス

### メリット
✅ コンテナ間の通信が容易
✅ ホスト側のIPアドレスに依存しない
✅ ポートマッピングを気にせず内部通信可能

## ヘルスチェック

すべてのコンテナにヘルスチェックを設定：

### PostgreSQL
```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U mmdpf_user"]
  interval: 10s
```
- データベースが接続可能かチェック

### Swift
```yaml
healthcheck:
  test: ["CMD", "swift", "stat"]
  interval: 30s
  start_period: 60s
```
- ストレージAPIが応答するかチェック
- 起動に時間がかかるため`start_period: 60s`

### Backend
```yaml
healthcheck:
  test: ["CMD", "wget", "http://localhost:3001/api/health"]
  interval: 30s
```
- APIサーバーが応答するかチェック

### Frontend
```yaml
healthcheck:
  test: ["CMD", "wget", "http://localhost:3000/"]
  interval: 30s
```
- フロントエンドが応答するかチェック

## 起動順序

```bash
docker-compose up -d
```

### 自動起動順序（depends_on）
1. **PostgreSQL** 起動
2. **Swift** 起動
3. **Backend** 起動（PostgreSQL, Swift起動後）
4. **Frontend** 起動（Backend起動後）
5. **Nginx** 起動（Backend, Frontend起動後）※本番環境のみ

### 注意点
⚠️ `depends_on`はコンテナの起動順序を制御するだけ
⚠️ ヘルスチェックが成功するまで待つわけではない
⚠️ バックエンドは内部で`pg_isready`などを使ってリトライ処理を実装

## まとめ

### 開発環境で動かすコンテナ（4つ）
1. ✅ **PostgreSQL** - データベース
2. ✅ **Swift** - オブジェクトストレージ
3. ✅ **Backend** - APIサーバー
4. ✅ **Frontend** - Webアプリケーション

### 本番環境で追加するコンテナ（1つ）
5. ✅ **Nginx** - リバースプロキシ + セキュリティゲートウェイ

### すべてのコンテナが必要な理由
- **マルチテナント対応**: データベースとストレージの両方が必要
- **分散アーキテクチャ**: フロントエンド・バックエンドの分離
- **セキュリティ**: 本番環境ではNginxでクライアント証明書認証
- **ファイル管理**: 大容量ファイルはデータベースではなくSwiftに保存
- **スケーラビリティ**: 各コンテナを独立してスケール可能

## 参考コマンド

### すべてのコンテナを起動
```bash
docker-compose up -d
```

### 特定のコンテナのみ起動
```bash
docker-compose up -d postgres swift backend
```

### ログ確認
```bash
docker-compose logs -f backend
```

### コンテナの状態確認
```bash
docker-compose ps
```

### すべてのコンテナを停止・削除
```bash
docker-compose down
```

### ボリュームも含めて削除（データも削除される）
```bash
docker-compose down -v
```

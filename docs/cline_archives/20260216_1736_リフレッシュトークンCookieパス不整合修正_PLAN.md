## 1. タスク概要

アクセストークンの有効期限が切れて、リフレッシュトークンが残っている状態でAPIを実行しても、アクセストークンが再発行されない問題を修正します。

## 2. 目的と期待される成果

### 目的
リフレッシュトークンのCookieパス設定が不整合になっており、トークン更新後にリフレッシュトークンが正しく送信されない問題を解決する。

### 期待される成果
- [ ] 初回ログイン時とリフレッシュ時のCookieパスを統一
- [ ] ログアウト時のclearCookieパスも統一
- [ ] アクセストークン有効期限切れ時に自動的にトークンが再発行される

## 3. 問題の根本原因

### 現在のCookieパス設定

| ファイル | 関数 | 行番号 | Cookieパス | 用途 |
|---------|------|--------|-----------|------|
| `authHelpers.ts` | `issueSessionTokens` | 156 | `/api/v1` | 初回ログイン時 |
| `authController.ts` | `refreshToken` | 297 | `/api/v1/auth` | トークン更新時 |
| `authController.ts` | `logout` | 172 | `/api/v1` | ログアウト時 |

### 問題の詳細

**1. 初回ログイン時:**
```typescript
// authHelpers.ts: 156行目
res.cookie('refreshToken', refreshTokenValue, {
  path: '/api/v1',  // すべてのAPIエンドポイントに送信される
});
```

**2. トークン更新時:**
```typescript
// authController.ts: 297行目
res.cookie('refreshToken', result.data.newRefreshToken, {
  path: '/api/v1/auth',  // /api/v1/auth/* にしか送信されない ❌
});
```

**3. 結果:**
- 初回ログイン後: `/api/v1/projects` などの通常のAPIリクエストにもリフレッシュトークンが送信される ✅
- リフレッシュ後: `/api/v1/projects` などの通常のAPIリクエストにはリフレッシュトークンが送信されない ❌
- アクセストークン有効期限切れ時: リフレッシュトークンがないため、401エラーになるがトークン更新ができない ❌

```
[初回ログイン]
  ↓

  ↓
[ユーザーがAPIを操作]
  ↓

  ↓
401エラー → フロントエンドがリフレッシュAPIを呼び出し
  ↓

  ↓

  ↓
```

**問題点:**
- リフレッシュトークンは `/api/v1/auth/*` にしか送信されないため、通常のAPIリクエストではリフレッシュトークンがない状態
- フロントエンドの自動リフレッシュ処理（authUtils.ts）は `/api/v1/auth/refresh` を呼び出すため、リフレッシュ自体は成功する
- しかし、通常のAPIリクエストでは依然としてリフレッシュトークンが送信されない
- 実質的にリフレッシュトークンが機能していない状態

## 補足: Cookieパスの仕様

### RFC 6265 の仕様

Cookieの `path` 属性は、そのパスまたはそのサブパスにマッチするリクエストにのみCookieを送信します。

```
path=/api/v1 の場合:
  /api/v1         → マッチ ✅
  /api/v1/        → マッチ ✅
  /api/v1/auth    → マッチ ✅ (サブパス)
  /api/v1/projects → マッチ ✅ (サブパス)
  /api            → マッチしない ❌
  /api/v2         → マッチしない ❌

path=/api/v1/auth の場合:
  /api/v1/auth        → マッチ ✅
  /api/v1/auth/       → マッチ ✅
  /api/v1/auth/login  → マッチ ✅ (サブパス)
  /api/v1/auth/refresh → マッチ ✅ (サブパス)
  /api/v1             → マッチしない ❌
  /api/v1/projects    → マッチしない ❌
```

### セキュリティ上の考慮

**Q: `/api/v1` に統一しても安全か？**

**A: はい、安全です。理由:**

1. **すべてのエンドポイントが認証必須**
   - `/api/v1/*` 配下のすべてのエンドポイントは認証ミドルウェアで保護されている
   - 認証なしでアクセスできるのは `/auth/login`, `/auth/reset-password-request` など、認証前のエンドポイントのみ

2. **httpOnly属性による保護**
   - JavaScriptからCookieにアクセスできない
   - XSS攻撃からの保護

3. **sameSite='lax'属性**
   - CSRF攻撃からの保護
   - クロスサイトリクエストでは送信されない（GET以外）

4. **secure属性（本番環境）**
   - HTTPS通信のみで送信
   - 中間者攻撃からの保護

したがって、`/api/v1` に統一してもセキュリティリスクは増加しません。

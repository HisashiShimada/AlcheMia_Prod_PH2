# チェックボックス仕様比較

## 比較日時
2026/3/9 11:22

## 比較対象の仕様

### 仕様A: 現状（チェック変更時に即座に追加・削除）

```typescript
const handleCheckboxChange = useCallback((taskId: number, checked: boolean) => {
  setCheckedTaskIds(prev => {
    const newSet = new Set(prev);
    if (checked) {
      newSet.add(taskId);
    } else {
      newSet.delete(taskId);
    }
    return newSet;
  });
}, []);
```

**特徴:**
- チェックボックス変更の度にstateが更新される
- リアルタイムで選択状態を保持

### 仕様B: 保存時にまとめてセット

```typescript
const handleSave = useCallback(async () => {
  // 保存時にチェックされているタスクIDを収集
  const currentCheckedIds = new Set<number>();
  
  // DOMから直接チェック状態を取得、またはtaskDetails配列を走査
  taskDetails.forEach(task => {
    const checkbox = document.querySelector(`input[data-task-id="${task.id}"]`);
    if (checkbox?.checked) {
      currentCheckedIds.add(task.id);
    }
  });
  
  // バリデーションと保存処理
  // ...
}, [taskDetails]);
```

**特徴:**
- 保存ボタン押下時のみstateを更新
- チェック変更中はDOMのみが変更される

## 推奨

### ✅ **仕様A（現状）を推奨**

#### 理由

1. **Reactの設計思想に沿っている**
   - Reactは「UIはstateの関数」という原則
   - DOM操作ではなくstate管理が推奨
   
2. **保守性が高い**
   - コードが読みやすく、理解しやすい
   - 他の開発者が参加してもすぐに理解できる
   
3. **拡張性がある**
   - 例: チェック数を表示する機能を追加する場合
     ```typescript
     const checkedCount = checkedTaskIds.size; // 簡単
     ```
   - 例: 全選択/全解除ボタンの実装が容易
   
4. **バグが少ない**
   - stateとUIが常に同期しているため整合性エラーが起きにくい
   - DOM操作によるバグリスクがない

5. **現代的なフロントエンド開発のベストプラクティス**
   - React、Vue、Angular等、全てのモダンフレームワークで推奨される方法

#### パフォーマンスの懸念について

現状の仕様でパフォーマンス問題が発生する可能性は低い：

- チェックボックス変更は頻繁に発生しない（ユーザー操作）
- 再レンダリングされるのはテーブル行のみ（Virtual DOM最適化）
- タスク数が数百件以上でない限り問題なし

**パフォーマンス最適化が必要な場合の対策:**
```typescript
// React.memoでチェックボックスコンポーネントを最適化
const TaskCheckbox = React.memo(({ taskId, checked, onChange, disabled }) => (
  <input
    type="checkbox"
    checked={checked}
    onChange={(e) => onChange(taskId, e.target.checked)}
    disabled={disabled}
  />
));
```

## 仕様Bが適している場合

以下のケースでは仕様Bを検討する価値がある：

1. **タスク数が非常に多い（1000件以上）**
   - ただし、この場合はページネーションやVirtual Scrollingを導入すべき

2. **チェック変更が非常に頻繁に発生する**
   - 例: 自動チェック機能がある場合
   - ただし、debounceやthrottleで対応可能

3. **メモリ制約が厳しい環境**
   - 組み込みシステムやローエンドデバイス向け
   - ただし、本システムはWebアプリなので該当しない

## 結論

**現状の仕様A（チェック変更時に即座に追加・削除）を維持することを推奨**

### 理由まとめ
- ✅ Reactのベストプラクティスに準拠
- ✅ コードの可読性・保守性が高い
- ✅ 拡張性があり、機能追加が容易
- ✅ バグが少なく、テストしやすい
- ✅ 現時点でパフォーマンス問題は発生していない

### 今後の対応
- パフォーマンス問題が実際に発生した場合のみ、最適化を検討
- 最適化の優先順位:
  1. React.memoによるコンポーネント最適化
  2. useCallbackによる関数メモ化
  3. Virtual Scrollingの導入（タスク数が多い場合）
  4. 最後の手段として仕様Bを検討

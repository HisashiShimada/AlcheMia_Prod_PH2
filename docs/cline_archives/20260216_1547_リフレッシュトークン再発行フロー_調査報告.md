## 調査目的
リフレッシュトークンが再発行されるたびに、cookieとRedisに保存されるかどうかを確認する。

## 結論

**YES**: リフレッシュトークンが再発行されるたびに、新しいトークンがcookieとRedisの両方に保存されます。

export async function refreshToken(req: Request, res: Response): Promise<void> {
  // 既存のリフレッシュトークンをcookieから取得

### 2. トークン再発行処理
**ファイル**: `backend/src/services/authService.ts`

```typescript
async processRefreshToken(params: {
  refreshTokenValue: string;
  ipAddress: string;
  userAgent: string;
}): Promise<Result<any>> {
  // 1. 既存のリフレッシュトークンを検証
  const verifyResult = await this.jwtService.verifyRefreshToken(refreshTokenValue);
  const payload = verifyResult.data;

  // 2. Redisで存在確認
  const existsResult = await this.refreshTokenService.exists(payload.tokenId);

  // 3. ユーザー情報と権限を取得
  const userResult = await this.organizationUserRepository.findByUserIdWithRole(
    this.pool,
    payload.userId,
    payload.organizationId
  );

  // 4. 権限情報を取得
  const permissions = await this.rolePermissionRepository.getPermissionsByRoleId(
    user.role_cd,
    user.organization_id
  );

  // 5. 新しいトークンペアを生成
  const tokenPairResult = await this.jwtService.generateTokenPair({
    userId: user.user_id,
    organizationId: user.organization_id,
    sessionId: newSessionId,
    permissions,
  });

  // 6. ★★★ 新しいリフレッシュトークンをRedisに保存 ★★★
  const newRefreshPayload = this.jwtService.decode(newRefreshToken);
  if (newRefreshPayload && 'tokenId' in newRefreshPayload) {
    await this.refreshTokenService.save(
      newRefreshPayload,
      ipAddress,
      userAgent,
      user.user_name,
      user.mail_address
    );
  }

  // 7. ★★★ 古いリフレッシュトークンを無効化（トークンローテーション） ★★★
  await this.refreshTokenService.revoke(payload.tokenId, payload.userId);

  // 8. 新しいリフレッシュトークンを返す
  return {
    success: true,
    data: {
      accessToken,
      newRefreshToken,
      refreshMaxAge: this.jwtService.getRefreshTokenMaxAge(),
      expiresIn: 900,
      user: { ... },
    },
  };
}
```

### 3. Redisへの保存処理
**ファイル**: `backend/src/services/refreshTokenService.ts`

```typescript
async save(
  payload: RefreshTokenPayload,
  ipAddress?: string,
  userAgent?: string,
  userName?: string,
  email?: string
): Promise<Result<void, ServiceError>> {
  // Redis保存用データ構築
  const storedData: StoredRefreshToken = {
    userId: payload.userId,
    organizationId: payload.organizationId,
    sessionId: payload.sessionId,
    tokenId: payload.tokenId,
    issuedAt: payload.iat,
    expiresAt: payload.exp,
    ipAddress,
    userAgent,
    userName,
    email
  };

  // TTL計算（有効期限まで）
  const now = Math.floor(Date.now() / 1000);
  const ttl = payload.exp - now;

  // Redisに保存（TTL付き）
  const key = `${this.keyPrefix}${payload.tokenId}`;
  await client.setEx(key, ttl, JSON.stringify(storedData));

  // ユーザーごとのトークンセットに追加
  const userKey = `${this.userTokensPrefix}${payload.userId}`;
  await client.sAdd(userKey, payload.tokenId);
  await client.expire(userKey, ttl);

  return { success: true, data: undefined };
}
```

## 保存されるデータの詳細

### Cookie に保存される情報
- **キー**: `refreshToken`
- **値**: JWT形式のリフレッシュトークン文字列
- **属性**:
  - `httpOnly: true` - JavaScriptからアクセス不可
  - `secure: true` (本番環境のみ) - HTTPS通信のみ
  - `sameSite: 'lax'` - CSRF対策
  - `maxAge`: 環境変数により動的（Redis起動時: 30分、未起動時: 8時間）
  - `path: '/api/v1/auth'` - 認証APIエンドポイントのみ

### Redis に保存される情報
- **キー**: `mmdpf:refresh_token:{tokenId}`
- **値**: JSON形式の以下のデータ
  ```typescript
  {
    userId: string;
    organizationId: string;
    sessionId: string;
    tokenId: string;
    issuedAt: number;
    expiresAt: number;
    ipAddress?: string;
    userAgent?: string;
    userName?: string;
    email?: string;
  }
  ```
- **TTL**: トークンの有効期限まで（自動削除）
- **追加のキー**: `mmdpf:refresh_token:user:{userId}` (Set型)
  - ユーザーごとのトークンIDセット（将来の強制ログアウト用）

## トークンローテーション (Token Rotation)

セキュリティ強化のため、リフレッシュトークンは使用されるたびに新しいトークンに置き換えられます：

1. **新しいトークンを発行**: `jwtService.generateTokenPair()`
2. **新しいトークンをRedisに保存**: `refreshTokenService.save()`
3. **古いトークンを無効化**: `refreshTokenService.revoke()`
4. **新しいトークンをcookieに設定**: `res.cookie()`

これにより、トークンの盗聴・再利用攻撃を防ぎます。

## セキュリティ上の利点

1. **httpOnly Cookie**: XSS攻撃からトークンを保護
2. **Redis TTL**: 自動的に期限切れトークンを削除
3. **トークンローテーション**: 使用済みトークンの再利用を防止
4. **ユーザーごとのトークンセット**: 将来の強制ログアウト機能に対応
5. **IPアドレス・User-Agent記録**: セッション管理画面での監視に活用

## 補足調査: セッション管理画面からRedis削除時のcookie動作

### 質問
セッション管理画面からRedisのリフレッシュトークンを削除した場合、cookieに保存されているリフレッシュトークンはどうなる？

### 回答

**cookieは残り続けますが、次回使用時に無効化されます。**

### 詳細な動作フロー

#### 1. セッション削除処理
**ファイル**: `backend/src/services/sessionService.ts`

```typescript
async terminateSession(
  tokenId: string,
  currentUserId: string,
  organizationId: string
): Promise<Result<void, ServiceError>> {
  // 1. トークン情報を取得
  const tokenResult = await this.refreshTokenService.get(tokenId);
  
  // 2. organization_idの検証（マルチテナント分離）
  if (token.organizationId !== organizationId) {
    return { success: false, error: { ... } };
  }
  
  // 3. 自分自身のセッション終了を防止
  if (token.userId === currentUserId) {
    return { success: false, error: { ... } };
  }
  
  // 4. ★★★ Redisからトークンを削除（セッション無効化） ★★★
  const revokeResult = await this.refreshTokenService.revoke(tokenId, token.userId);
  
  // ⚠️ 注意: クライアント側のcookieは削除されない
  return { success: true, data: undefined };
}
```

#### 2. Cookieへの影響

**重要なポイント:**

| 項目 | 状態 | 理由 |
|------|------|------|
| **Redisのトークン** | ✅ 削除される | `refreshTokenService.revoke()` で削除 |
| **クライアントのcookie** | ❌ 残り続ける | サーバーは対象ユーザーのブラウザと直接通信しない |
| **cookieの有効期限** | 変わらず | maxAge設定は変更されない |

**なぜcookieを削除できないか？**

```typescript
// セッション削除APIは管理者が別ユーザーのセッションを削除する
// → 対象ユーザーのブラウザとは直接通信していない
// → res.clearCookie()を呼んでも、リクエストを送った管理者のcookieが削除されるだけ

// ログアウトAPIとの違い:
// ログアウト: 自分自身のセッションを終了 → cookieを削除できる
// セッション削除: 他人のセッションを終了 → cookieを削除できない
```

#### 3. 次回リフレッシュ時の動作

対象ユーザーが次回アクセストークン更新を試みた場合：

```typescript
// クライアント → サーバー: POST /api/v1/auth/refresh
// cookieにリフレッシュトークンを含めて送信

// サーバー側の処理
async processRefreshToken(params) {
  // 1. JWT検証（パス）
  const verifyResult = await this.jwtService.verifyRefreshToken(refreshTokenValue);
  
  // 2. ★★★ Redisで存在確認 ★★★
  const existsResult = await this.refreshTokenService.exists(payload.tokenId);
  
  if (!existsResult.data) {
    // ⚠️ Redisに存在しない → エラーを返す
    return {
      success: false,
      error: {
        code: 'AUTH_TOKEN_INVALID',
        message: 'リフレッシュトークンが無効です。再度ログインしてください',
      },
    };
  }
  
  // 以降の処理は実行されない
}
```

**クライアント側の動作:**

```typescript
// 401 Unauthorized レスポンスを受信
{
  success: false,
  error: {
    code: 'AUTH_TOKEN_INVALID',
    message: 'リフレッシュトークンが無効です。再度ログインしてください'
  }
}

// クライアント側の処理（想定）

  // tokenStorageをクリア
  tokenStorage.removeToken();
  
  // ログイン画面にリダイレクト
  router.push('/login');
}
```

### セキュリティ上の考察

#### これは問題か？

**NO - これは正常な動作です。**

理由：

1. **Redisが真実の情報源 (Source of Truth)**
   - cookieはあくまでトークンの「運搬手段」
   - Redisがトークンの有効性を判定する
   - Redisに存在しなければ、cookieの内容は無意味

2. **httpOnly cookieの制約**
   - JavaScriptからcookieを削除できない（セキュリティ機能）
   - サーバー側でres.clearCookie()を呼んでも、別ユーザーのcookieには届かない

3. **次回アクセス時に自動的に無効化**
   - ユーザーが次にAPIを呼び出すと401エラー
   - クライアントアプリケーションが適切にログアウト処理を実行
   - 結果的にユーザーは再ログインを求められる

#### 代替案との比較

| 方式 | 実装方法 | メリット | デメリット |
|------|---------|---------|-----------|
| **現在の方式** | Redisのみ削除 | シンプル、確実 | cookieが残る（次回使用時に無効化） |
| WebSocket通知 | リアルタイム通知でクライアントに削除指示 | 即座にcookie削除 | 複雑、WebSocket実装が必要 |
| ポーリング | クライアントが定期的にセッション状態を確認 | 比較的シンプル | サーバー負荷増加 |

**現在の方式が最適な理由:**
- 実装がシンプル
- Redisの存在確認で確実にセッションを無効化
- httpOnly cookieのセキュリティを維持
- 次回アクセス時に自動的に処理される

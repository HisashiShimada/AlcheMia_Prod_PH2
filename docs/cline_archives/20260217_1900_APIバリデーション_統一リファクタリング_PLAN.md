## 1. タスク概要

バックエンドAPIのバリデーション処理を、新しい統一規約（`handleValidationErrors`ミドルウェア方式）に全面的に準拠させるリファクタリングを実施します。

**主な問題点:**
1. `maimlRoutes.ts`の全エンドポイント（18個）で`handleValidationErrors`が欠落
2. `maimlController.ts`で独自の`checkValidationErrors`関数を使用（規約違反）
3. `projectRoutes.ts`の一部エンドポイント（6個）で`handleValidationErrors`が欠落
4. バリデーション処理の責務がコントローラー層に残っている

**参考ドキュメント:**
- `docs/20260206_1613_指示一覧取得API_バリデーション修正_PLAN.md` - 新バリデーション規約の定義
- `backend/src/middleware/validationMiddleware.ts` - 統一ミドルウェアの実装
- `.clinerules/development/config.md` - コーディング規約（関心の分離）

## 3. 新旧バリデーション構造の比較

### ❌ 旧構造（規約違反）

```typescript
// Routes層
router.post(
  '/parse',
  authMiddleware,
  [body('content').notEmpty().withMessage('contentは必須です')],
  // ❌ handleValidationErrors なし
  maimlController.parse
);

// Controller層
export async function parse(req: Request, res: Response): Promise<void> {
  try {
    // ❌ コントローラー内でバリデーション処理
    if (checkValidationErrors(req, res)) return;
    
    const { content } = req.body;
    const result = await maimlService.parseMaiML(content);
    res.json({ success: true, data: result });
  } catch (error) {
    handleError(res, error, 'MAIML解析エラー');
  }
}
```

### ✅ 新構造（規約準拠）

```typescript
// Routes層
router.post(
  '/parse',
  authMiddleware,
  [body('content').notEmpty().withMessage('contentは必須です')],
  handleValidationErrors, // ✅ ミドルウェアで処理
  maimlController.parse
);

// Controller層
export async function parse(req: Request, res: Response): Promise<void> {
  try {
    // ✅ バリデーション処理削除、ビジネスロジックのみ
    const { content } = req.body;
    const result = await maimlService.parseMaiML(content);
    res.json({ success: true, data: result });
  } catch (error) {
    handleError(res, error, 'MAIML解析エラー');
  }
}
```

## 6. 技術的詳細

### バリデーション処理の責務分離

**DO（推奨）:**
- ✅ ルート層: express-validatorでバリデーションルールを定義
- ✅ ミドルウェア層: handleValidationErrorsで統一的なエラーレスポンスを返却
- ✅ コントローラー層: バリデーション済みパラメータを使用してビジネスロジックに集中
- ✅ Service層: ビジネスロジックバリデーションのみ実施（ステータス遷移、権限、データ整合性等）

**DON'T（非推奨）:**
- ❌ コントローラー内で `validationResult()` を使用しない
- ❌ コントローラー内でリクエストパラメータの形式チェックをしない
- ❌ Service層でリクエストパラメータの必須チェックや型チェックをしない（Routes層で実施済み）
- ❌ 独自のバリデーションエラーハンドラー関数を作成しない

### バリデーションの責務分離の明確化

**Routes層（express-validator）:**
- リクエストパラメータの形式チェック（必須、型、長さ、パターン等）
- 例: `body('content').notEmpty()`, `param('id').isUUID()`

**Middleware層（handleValidationErrors）:**
- バリデーションエラーの統一的なレスポンス返却

**Controller層:**
- パラメータの受け渡しのみ（バリデーション済みと信頼）

**Service層:**
- ビジネスロジックバリデーション（ステータス遷移、権限、データ整合性等）
- 例: `validateStatusTransition()`, `checkUserPermission()`, `validateBusinessRule()`
- ❌ リクエストパラメータの形式チェック（Routes層で実施済みのため不要）

### 統一されたエラーレスポンス形式

```typescript
// handleValidationErrors が返却する形式
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "バリデーションエラーが発生しました",
    "details": [
      {
        "field": "content",
        "message": "contentは必須です",
        "code": "REQUIRED_FIELD"
      }
    ]
  },
  "meta": {
    "timestamp": "2026-02-17T10:00:00.000Z",
    "requestId": "uuid-v4"
  }
}
```

### ミドルウェアチェーンの標準パターン

```typescript
router.post(
  '/endpoint',
  authMiddleware,           // 1. 認証
  [
    // 2. バリデーションルール定義
    body('field').notEmpty().withMessage('エラーメッセージ'),
  ],
  handleValidationErrors,   // 3. バリデーションエラーハンドリング
  controller.method         // 4. コントローラー実行
);
```

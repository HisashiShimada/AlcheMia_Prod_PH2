# 認証ミドルウェアとログイン画面のセッション情報乖離 - 影響分析レポート

**作成日時**: 2026-01-20 17:16  
**分析対象**: 認証ミドルウェア（authMiddleware）とログイン画面のセッション情報の乖離による影響

---

## 🎯 現状の確認

### 現在の実装状況

#### 1. authMiddleware (req.user) の情報
```typescript
interface JwtPayload {
  userId: string;         // ユーザーID
  organizationId: string; // 組織ID
  role: UserRole;         // ロール（権限）
  sessionId: string;      // セッションID
  iat: number;           // 発行時刻
  exp: number;           // 有効期限
}
```

#### 2. フロントエンド（ログイン画面経由）の情報
```typescript
interface User {
  id: string;              // ユーザーID
  username: string;        // ユーザー名
  email: string;           // メールアドレス
  role: UserRole;          // ロール（権限）
  organizationId: string;  // 組織ID
  organizationName: string;// 組織名
  displayName: string;     // 表示名
}
```

### ✅ 現状の評価

**結論**: 現在の実装では**適切に設計されており、問題なし**

**理由**:
- バックエンド（JWT）: 最小限の識別情報のみ（セキュリティ考慮）
- フロントエンド（User）: UI表示用の詳細情報
- **共通情報（userId, organizationId, role）は一致している**

## 🚨 乖離が発生した場合の問題

### シナリオ1: organizationId の不一致

#### 状況
```typescript
// authMiddleware (req.user)
organizationId: "org_a"

// フロントエンド (User)
organizationId: "org_b"
```

#### 影響

##### 1. セキュリティ侵害（重大）
```typescript
// バックエンドAPI
router.get('/projects', authMiddleware, (req, res) => {
  // req.user.organizationId = "org_a" を使用
  const projects = await db.query(
    'SELECT * FROM projects WHERE organization_id = $1',
    [req.user.organizationId]  // org_a のデータを取得
  );
  
  res.json({ data: projects });
});

// フロントエンド
const response = await apiClient.get('/projects', {
  headers: {
    'X-Organization-Id': user.organizationId  // org_b を送信
  }
});
```

**問題点**:
- **マルチテナント分離の破綻**
- ユーザーは org_b の画面を見ているが、org_a のデータにアクセス
- **データ漏洩リスク**
- 不正なデータ操作の可能性

##### 2. データ不整合
```typescript
// ファイルアップロード
await s3Service.uploadFile(
  user.organizationId,  // org_b のパス
  'projects/file.txt',
  content
);
// → org_b/projects/file.txt に保存

// しかし、データベースには org_a で記録
await db.query(
  'INSERT INTO files (organization_id, path) VALUES ($1, $2)',
  [req.user.organizationId, 'projects/file.txt']  // org_a で保存
);
```

**問題点**:
- S3とDB間でデータの不整合
- ファイルが見つからないエラー
- データ復旧が困難

### シナリオ2: role（権限）の不一致

#### 状況
```typescript
// authMiddleware (req.user)
role: "experiment_worker"  // 作業者権限

// フロントエンド (User)
role: "experiment_admin"   // 管理者権限
```

#### 影響

##### 1. 権限昇格の脆弱性（重大）
```typescript
// フロントエンド（UI表示）
{user.role === 'experiment_admin' && (
  <Button onClick={handleDeleteProject}>
    プロジェクト削除  {/* 管理者のみ表示 */}
  </Button>
)}
// → ボタンが表示される

// バックエンドAPI
router.delete('/projects/:id', authMiddleware, (req, res) => {
  // permissionCheck で検証
  if (req.user.role !== 'experiment_admin') {
    return res.status(403).json({ error: 'Insufficient permissions' });
  }
  // → 403 Forbidden（実際は作業者権限）
});
```

**問題点**:
- UIでは削除ボタンが表示される
- しかしAPIリクエストは403エラー
- **ユーザー体験の悪化**
- 不正アクセス試行の記録

##### 2. 監査ログの不整合
```typescript
// Admin監査ログ記録
if (user.role === 'system_admin') {  // フロントエンドのrole
  // 監査ログを記録する処理
  await logAdminAction(user.id, 'delete_project');
}

// しかし実際のroleは experiment_worker
// → 本来記録すべきでない監査ログが記録される
```

**問題点**:
- 監査ログの信頼性低下
- コンプライアンス違反のリスク
- 不正アクセスの検知困難

### シナリオ3: userId の不一致

#### 状況
```typescript
// authMiddleware (req.user)

// フロントエンド (User)

```

#### 影響

##### 1. なりすまし攻撃（最重大）
```typescript

router.put('/users/profile', authMiddleware, async (req, res) => {
  // JWTのuserIdを使用（正しい）
  await db.query(
    'UPDATE organization_user SET display_name = $1 WHERE user_id = $2',
```

**問題点**:
- ユーザーは user_002 の画面を見ている
- しかし user_001 のデータを更新

- 重大なセキュリティ侵害

##### 2. アクセス履歴の混乱

```typescript
  'INSERT INTO access_log (user_id, action) VALUES ($1, $2)',
  [user.id, 'view_project']  // user_002 で記録

// しかし実際のセッションは user_001
```

**問題点**:
- ログ分析の信頼性喪失
- 不正アクセスの追跡不能
- セキュリティ監査の失敗

## 🔍 乖離が発生する原因

### 1. 実装ミス

#### パターンA: JWT生成時のデータ不正
```typescript
// ❌ 悪い例
const jwtResult = await jwtService.generate({
  userId: userInfo.id,
  organizationId: 'hardcoded-org-id',  // ハードコーディング
  role: userInfo.role,
  sessionId: uuidv4(),
});
```

#### パターンB: データベース不整合
```typescript
// ユーザーテーブルとJWT生成の間で organizationId が変更された
// トランザクション管理の欠如
```

### 2. セキュリティ攻撃

#### トークン改ざん攻撃
```
1. 攻撃者がJWTトークンを取得
2. ペイロードを改ざん（role: "worker" → "admin"）
3. 署名なしで再送信
4. 検証失敗 → 攻撃は防げる（現在の実装は安全）
```

#### セッションハイジャック
```
1. 攻撃者が別ユーザーのセッショントークンを取得
2. フロントエンドには自分の情報を表示
3. バックエンドには被害者のトークンを使用
```

### 3. 同期ミス

#### ユーザー情報更新の非同期性
```typescript
// 1. ユーザーがロールを変更
await db.query(
  'UPDATE organization_user SET role = $1 WHERE user_id = $2',
  ['experiment_admin', userId]
);

// 2. しかしJWTは古いまま（role: 'experiment_worker'）
// → 次回ログインまで不一致が続く
```

## ✅ 予防策と検証方法

### 1. 整合性チェック（推奨実装）

#### ログイン時の検証
```typescript
// authController.ts - verifyPin
const organizationId = req.headers['x-organization-id'] as string;

// ユーザー情報取得後
if (userInfo.organizationId !== organizationId) {
  res.status(403).json({
    success: false,
    error: {
      code: 'AUTH_ORGANIZATION_MISMATCH',
      message: '組織IDが一致しません',
    },
  });
  return;
}

// JWT生成前にも再確認
const jwtPayload = {
  userId: userInfo.id,
  organizationId: userInfo.organizationId,  // DBから取得した値
  role: userInfo.role,
  sessionId: uuidv4(),
};
```

#### API実行時の検証
```typescript
// authMiddleware の後に追加検証ミドルウェア
export function validateSessionConsistency(
  req: Request,
  res: Response,
  next: NextFunction
) {
  const headerOrgId = req.headers['x-organization-id'] as string;
  const jwtOrgId = req.user?.organizationId;
  
  if (headerOrgId !== jwtOrgId) {
    res.status(403).json({
      success: false,
      error: {
        code: 'SESSION_INCONSISTENCY',
        message: 'セッション情報の不整合が検出されました',
      },
    });
    return;
  }
  
  next();
}
```

### 2. 定期的な整合性チェック

#### フロントエンドでの検証
```typescript
// ページ初期化時
useEffect(() => {
  const verifySessionConsistency = async () => {
    try {
      // 現在のユーザー情報を再取得
      const response = await apiClient.get('/auth/me');
      
      // SessionStorage の情報と比較
      const savedUser = JSON.parse(sessionStorage.getItem('user') || '{}');
      
      if (savedUser.id !== response.data.id ||
          savedUser.organizationId !== response.data.organizationId ||
          savedUser.role !== response.data.role) {
        // 不一致検出 → 強制ログアウト
        console.error('Session inconsistency detected');
        handleLogout();
      }
    } catch (error) {
      console.error('Session verification failed:', error);
      handleLogout();
    }
  };
  
  verifySessionConsistency();
}, []);
```

### 3. 監査ログ

#### 不整合検出ログ
```typescript
// 不整合検出時に記録
if (userInfo.organizationId !== organizationId) {
```

## 📊 まとめ

### 🎯 質問への回答

**Q: 認証用のミドルウェアとログイン画面が保存するセッション情報に乖離があるとどのような問題がある？**

**A: 以下の重大な問題が発生します:**

1. **セキュリティ侵害**
   - マルチテナント分離の破綻
   - 権限昇格攻撃
   - なりすまし攻撃
   - データ漏洩

2. **データ不整合**
   - DBとS3間の不整合
   - ファイルアクセスエラー
   - データ復旧困難

3. **ユーザー体験の悪化**
   - UI表示と実際の権限の不一致
   - 予期しないエラー
   - 混乱とフラストレーション

4. **監査・コンプライアンス問題**
   - 監査ログの信頼性喪失
   - アクセス追跡不能
   - コンプライアンス違反リスク

### ✅ 現状の評価

**現在の実装は適切**:
- 共通情報（userId, organizationId, role）は一致
- 最小限の情報のみJWTに格納（セキュリティ考慮）
- 詳細情報はフロントエンドで保持（UI表示用）

### ⚠️ 推奨対応

1. **整合性チェックの追加** - ログイン時とAPI実行時
2. **定期的な検証** - フロントエンドでの再確認
3. **監査ログ** - 不整合検出時の記録

# role → role_id 移行影響調査 補足レポート

## 📢 重要な前提条件の明確化

### データ形式の変更内容

**変更前（roleカラム）:**
```
型: VARCHAR(30)
値: 'provider', 'system_admin', 'data_admin', 'experiment_admin', 'experiment_worker', 'mi_engineer'
```

**変更後（role_idカラム）:**
```
型: VARCHAR(30)
値: 'ROLE001', 'ROLE002', 'ROLE003', 'ROLE004', 'ROLE005', 'ROLE006'
```

### 対応表（推測）

| role_id | role_name (旧role) | 説明 |
|---------|-------------------|------|
| ROLE001 | provider | プロバイダ |
| ROLE002 | system_admin | システム管理者 |
| ROLE003 | data_admin | データ管理者 |
| ROLE004 | experiment_admin | 実験管理者 |
| ROLE005 | experiment_worker | 実験作業者 |
| ROLE006 | mi_engineer | MIエンジニア |

※ 実際の対応表はroleテーブル（またはマスタテーブル）で定義されていると思われます。

## 🔄 影響評価の修正

### 元のレポートとの違い

元のレポート（docs/20260129_0925_role_id移行_影響調査_REPORT.md）では、role_idを**数値型の外部キー**と想定していましたが、実際は**文字列型のIDコード**です。

### 影響箇所は変わらないが、修正方法が変わる

**元の想定:**
- role_id: 1, 2, 3（数値）
- 課題: 数値をキーとしたマッピングが使えない

**実際:**
- role_id: 'ROLE001', 'ROLE002', 'ROLE003'（文字列）
- 課題: IDコードからrole_name文字列への変換が必要

## 結論

**元の調査結果との主な違い:**

1. **型変換の課題が解消**
   - 数値 → 文字列の変換は不要
   - IDコード → role_name の変換が必要（SQLでJOIN）

2. **マッピングオブジェクトは変更不要**
   - role_name（文字列）を引き続き使用可能

3. **修正箇所が削減**
   - 主にSQLクエリとテストデータのみ
   - コードロジックの大幅な変更は不要

4. **修正難易度が低下**
   - 高 → 中に変更

**推奨される移行方式は変わらず「オプションA: 段階的移行」**
- role_idカラム追加時にroleカラムを維持
- SQLクエリを修正してrole_nameを取得
- 十分な検証期間を経てroleカラムを削除

## 1. タスク概要

現在のJWT認証システムに、各ロールに対応した権限情報（機能ID配列）を追加します。
`role_permission`テーブルに登録されている各ロールの許可機能IDを、JWT生成時に取得し、`req.user`に含めることで、フロントエンドおよびバックエンドで権限チェックを容易にします。

## 2. 目的と期待される成果

### 目的
- ロールベースの権限管理をより細かく制御できるようにする
- フロントエンドで機能単位の表示制御を可能にする
- バックエンドで機能単位のアクセス制御を強化する

### 期待される成果

## 5. 技術的詳細

### JwtPayloadインターフェース更新後
```typescript
export interface JwtPayload {
  userId: string;
  organizationId: string;
  role: UserRole;
  sessionId: string;
  permissions: string[];  // 追加: 機能IDの配列
  iat: number;
  exp: number;
}
```

### role_permissionテーブル構造
```sql
-- 主キー: (role, function_id)
CREATE TABLE role_permission (
  role VARCHAR(30),
  function_id VARCHAR(30),
  permission VARCHAR(50)  -- CRUDの権限
);
```

### 権限取得クエリ例
```sql
SELECT DISTINCT function_id 
FROM role_permission 
WHERE role = $1
ORDER BY function_id;
```

### セキュリティ考慮事項
- [ ] SQLインジェクション対策（Parameterized Queries使用）
- [ ] role_permissionテーブルへのアクセスはバックエンドのみ
- [ ] JWT内の権限情報は改ざん不可（署名検証済み）
- [ ] 権限情報のサイズがJWTトークンサイズに影響（通常は問題なし）

## 6. リスクと対策

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|----------|------|
| JWTトークンサイズの増加 | 低 | 中 | 機能IDが少数の場合は問題なし。多数の場合はクレームサイズを監視 |
| 既存コードの型エラー | 中 | 低 | TypeScriptの型チェックで事前検出可能 |
| データベースクエリの失敗 | 高 | 低 | エラーハンドリングを適切に実装し、フォールバックとして空配列を返す |
| 権限情報の不整合 | 中 | 低 | role_permissionテーブルの整合性を事前に確認 |

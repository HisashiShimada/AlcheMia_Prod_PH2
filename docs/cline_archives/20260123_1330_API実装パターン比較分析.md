## 4. projectApiService.ts の優れた点

### 4.1. 統一されたAxiosインスタンス作成

```typescript
const createApiClient = () => {
  const client = axios.create({
    baseURL: API_BASE_URL,
    timeout: 30000, // ✅ タイムアウト設定
    withCredentials: true, // ✅ Cookie認証
  });

  // ✅ リクエストインターセプター
  client.interceptors.request.use(...);
  
  // ✅ レスポンスインターセプター（統一エラーハンドリング）
  client.interceptors.response.use(...);

  return client;
};
```

**メリット**:
- タイムアウト設定で無限待機を防止
- インターセプターで一元的なエラーハンドリング
- 再利用可能な設計

### 3.2. API規約に準拠したレスポンス処理

```typescript
const response = await client.get<{
  success: true;
  data: FileListResponse;
  meta: {
    timestamp: string;
    requestId: string;
  };
}>(`/api/v1/projects/${encodeURIComponent(projectName)}/files`);

return response.data.data; // ✅ dataプロパティから取得
```

**API規約との整合性**:
```json
{
  "success": true,
  "data": { ... },  // ← ここを返す
  "meta": { ... }
}
```

### 3.3. 適切なエラーハンドリング

```typescript
client.interceptors.response.use(
  (response) => response,
  (error: AxiosError<ApiErrorResponse>) => {
    if (error.response?.data) {
      const apiError = error.response.data;
      const errorMessage = apiError.error?.message || 'APIエラーが発生しました';
      throw new Error(errorMessage); // ✅ ユーザーフレンドリーなエラー
    } else if (error.request) {
      throw new Error('サーバーに接続できませんでした');
    } else {
      throw new Error('リクエストの送信に失敗しました');
    }
  }
);
```

### 3.4. 型安全性

```typescript
// ✅ 明示的な型定義
export interface FileListResponse {
  projectId: string;
  projectName: string;
  files: ProjectFile[];
  archiveFiles: ProjectFile[];
}

// ✅ 型付きレスポンス
const response = await client.get<{
  success: true;
  data: FileListResponse;
  meta: { ... };
}>(...);
```

## 4. apiClient.ts の問題点

### 4.1. HTTPクライアントの混在

```typescript
// ❌ fetchを使用（一部の関数）
export async function fetchProjects(): Promise<ApiResponse<ProjectListResponse>> {
  const response = await fetch(`${API_BASE_URL}/projects`, {
    method: 'GET',
    credentials: 'include',
    headers: { 'Content-Type': 'application/json' },
  });
}

// ❌ モックデータ（他の関数）
export async function fetchProjectFiles(...) {
  await simulateApiDelay(); // モック遅延
  return { success: true, data: { ... } }; // モックデータ
}
```

**問題点**:
- fetchとモックが混在し、一貫性がない
- エラーハンドリングが統一されていない
- タイムアウト設定がない

### 4.2. エラーハンドリングの不統一

```typescript
// ❌ 各関数で個別にエラーハンドリング
try {
  const response = await fetch(...);
  if (!response.ok) {
    const errorData = await response.json().catch(() => ({}));
    throw new Error(errorData.error?.message || 'エラー');
  }
} catch (error) {
  console.error('fetchProjects error:', error);
  throw error;
}
```

**問題点**:
- 同じエラーハンドリングコードを各関数で重複記述
- 保守性が低い

### 4.3. タイムアウト設定なし

```typescript
// ❌ タイムアウト設定がない
const response = await fetch(`${API_BASE_URL}/projects`, {
  method: 'GET',
  credentials: 'include',
});
```

**問題点**:
- ネットワーク遅延時に無限待機の可能性
- ユーザー体験の悪化

## 7. ベストプラクティス

### 7.1. DO（推奨）

✅ **Axiosで統一する**
```typescript
const client = createApiClient();
const response = await client.get(...);
```

✅ **インターセプターでエラーハンドリング統一**
```typescript
client.interceptors.response.use(
  (response) => response,
  (error) => { /* 統一エラー処理 */ }
);
```

✅ **タイムアウトを設定する**
```typescript
axios.create({ timeout: 30000 });
```

✅ **型を明示する**
```typescript
const response = await client.get<ApiResponse<T>>(...);
```

### 7.2. DON'T（非推奨）

❌ **HTTPクライアントを混在させない**
```typescript
// 悪い例
await fetch(...);  // fetchとAxiosを混在させない
await axios.get(...);
```

❌ **各関数で個別にエラーハンドリングしない**
```typescript
// 悪い例
try { ... } catch { /* 個別処理 */ }
try { ... } catch { /* 個別処理 */ }
```

❌ **モックと本番コードを混在させない**
```typescript
// 悪い例
export async function fetchData() {
  if (isDevelopment) {
    return mockData; // モックと本番を同じファイルに書かない
  }
  return await api.get(...);
}
```

## 3. 根本原因分析

### テーブル構造の理解

**project_taskテーブル（親テーブル）:**
- 主キー: (organization_id, project_id, method_id)
- メソッド単位の情報を格納（1メソッド = 1レコード）
- カラム: organization_id, project_id, method_id, task_name, experiment_order, experiment_condition, attempts_count, create_user_id, create_at, update_user_id, update_at
- **experiment_user_id、task_status、task_no、experiment_start_at、experiment_end_atカラムは存在しない**

**project_task_detailテーブル（子テーブル）:**
- 主キー: (organization_id, project_id, method_id, task_no)
- タスク単位の情報を格納（1タスク = 1レコード）
- カラム: organization_id, project_id, method_id, task_no, task_status, experiment_start_at, experiment_end_at, experiment_user_id, reviewed_at, review_user_id, create_user_id, create_at, update_user_id, update_at
- **experiment_user_id、task_status等のタスク固有情報を持つ**

#### Phase 5: 第2のエラー修正（FOR UPDATE制約）
**発生したエラー:**
```json
{
  "code": "0A000",
  "message": "FOR UPDATE cannot be applied to the nullable side of an outer join"
}
```

**エラー原因:**
- PostgreSQLでは、LEFT JOIN（外部結合）のnullable側（結合先テーブル）に対して`FOR UPDATE`を適用できない
- 元のSQLでは`FOR UPDATE`が全テーブル（ptd, p, ou）に適用されようとしていた

**修正内容:**
- `FOR UPDATE` → `FOR UPDATE OF ptd`
- ロック対象を`project_task_detail`テーブル（ptd）のみに限定

**修正理由:**
- 楽観的ロック制御で必要なのは`project_task_detail`テーブルのロックのみ
- LEFT JOINで取得する`project`と`organization_user`テーブルはロック不要（参照のみ）

#### Phase 6: 第3のエラー修正（楽観的ロック - タイムスタンプ精度）
**発生したエラー:**
```json
{
  "code": "CONCURRENT_UPDATE_DETECTED",
  "message": "Concurrent update detected. Please fetch the latest data and retry."
}
```

**エラー原因:**
- PostgreSQLの`timestamp`型はマイクロ秒（6桁）の精度を持つ
- JavaScriptの`Date.toISOString()`はミリ秒（3桁）の精度しか持たない
- 精度の違いにより、`update_at = $6`の比較が失敗していた

**例:**
- DB: `2026-02-23 14:30:00.123456`（マイクロ秒精度）
- JS: `2026-02-23T14:30:00.123Z`（ミリ秒精度）
- 比較結果: 不一致 → 楽観的ロック失敗

**修正内容:**
- `WHERE update_at = $6` → `WHERE DATE_TRUNC('milliseconds', update_at) = DATE_TRUNC('milliseconds', $6::timestamp)`
- 両方のタイムスタンプをミリ秒単位に丸めて比較

**修正理由:**
- JavaScriptから送信されるタイムスタンプはミリ秒精度
- データベース側もミリ秒精度に丸めることで、正確に比較できる

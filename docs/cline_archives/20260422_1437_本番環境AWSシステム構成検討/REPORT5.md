# 調査報告: ALB と NLB の特徴・メリット・デメリット比較

- **作成日**: 2026-04-22
- **対象**: SaaS版 AWS環境（ECS Fargate）本番環境構成検討
- **関連レポート**: REPORT1.md（ALB mTLS 構成検討）、REPORT.md（本番環境問題点一覧）

---

## 1. ALB（Application Load Balancer）とは

### 基本的な役割

ALB は **「インターネットから来たリクエストを、複数のサーバーに振り分ける装置（ロードバランサー）」** です。

OSI モデルの **レイヤー7（アプリケーション層）** で動作し、HTTP/HTTPS の内容を理解した上でルーティングを行います。

```
ユーザーのブラウザ
       ↓
   [ALB] ← HTTPを解読できる
    ├── /api/* → バックエンドタスク（ECS Fargate）
    └── /      → フロントエンドタスク（ECS Fargate）
```

### HTTPS 終端（TLS Termination）

ALB は HTTPS（暗号化通信）を受け取り、バックエンドには HTTP で渡すことができます。

```
ユーザー ──HTTPS（暗号）──→ [ALB] ──HTTP（平文）──→ ECS タスク
```

サーバー証明書の管理は ALB（ACM）に委ねることができ、バックエンドの ECS タスクは HTTPS を意識しなくてよくなります。

### mTLS（相互TLS認証）のネイティブサポート

ALB は 2023年に mTLS をネイティブサポートしました。ALB 自身がクライアント証明書を検証し、証明書情報をヘッダーとしてバックエンドに転送します。

```
ブラウザ（クライアント証明書 .p12 を提示）
       ↓
   [ALB]
    ├── ① HTTPS 終端（ACM サーバー証明書）
    ├── ② クライアント証明書検証（ACM Trust Store の CA で検証）
    └── ③ X-Amzn-Mtls-Clientcert-Subject: CN=<uuid>,O=... ヘッダーを付与
                ↓
          ECS タスク（nginx コンテナ不要）
```

## 2. NLB（Network Load Balancer）とは

### 基本的な役割

NLB は OSI モデルの **レイヤー4（トランスポート層）** で動作します。  
HTTP の内容は解釈せず、**TCP/UDP パケットをそのまま転送** します。

### TCPパススルー（本システムで使用中の構成）

TLS を終端せずにバックエンドにそのまま転送できます。  
これにより、クライアント証明書の情報がバックエンド（nginx）まで届きます。

```
【検証環境（NLB TCPパススルー）】
ユーザー ──HTTPS──→ NLB ──HTTPS そのまま──→ nginx（証明書を検証・CN抽出）──→ バックエンド
                    ↑                         ↑
              暗号を解かない          ここで初めてHTTPS終端
              （パススルー）          + クライアント証明書の検証
                                     + X-Organization-Id ヘッダー付与
```

## 3. ALB の特徴・メリット・デメリット

### メリット

| カテゴリ | 内容 |
|---------|------|
| **mTLS ネイティブサポート** | ALB 自身がクライアント証明書を検証。nginx コンテナが不要になる |
| **ACM との統合** | サーバー証明書を ACM で管理。カスタムドメインの場合は自動更新（60日前）。証明書の有効期限切れリスクを排除 |
| **AWS WAF との統合** | IP制限・レートリミット・SQLインジェクション検知・DDoS対策を宣言的に設定可能。NLBには WAF を適用できない |
| **HTTP レベルのアクセスログ** | リクエストパス・ステータスコード・レスポンスタイム・クライアントIPなどを S3 に出力可能 |
| **高度なルーティング** | パスベース（`/api/*`→backend）・ホストベース・ヘッダーベースのルーティングが可能 |
| **HTTP→HTTPS リダイレクト** | ALBリスナールールでネイティブに設定可能（nginx 設定不要） |
| **ヘルスチェックの充実** | HTTP レベル（`/api/health` が 200 を返すか）でヘルスチェック可能 |
| **コスト削減（本構成の場合）** | NLB + nginx コンテナ管理が不要になり、ALB 1台構成にシンプル化できる |
| **スティッキーセッション** | Cookie ベースのセッション維持が可能 |

### デメリット

| カテゴリ | 内容 |
|---------|------|
| **NLB比で若干のレイテンシ増** | HTTP プロトコルをパースするオーバーヘッドがある（一般的なWebアプリには実用上影響なし） |
| **静的IPが割り当てられない（デフォルト）** | NLBは Elastic IP を割り当て可能だが、ALBは DNS 名のみ（Route 53 Alias で対応可） |
| **カスタムドメインが実質必須（mTLS利用時）** | ACM の公的証明書（無料・自動更新）はカスタムドメインが必要。ドメインなしの場合は自己署名証明書を手動インポートし、自動更新されない |
| **ヘッダー改ざんリスク** | ALBが付与した `X-Amzn-Mtls-Clientcert-Subject` は ECS タスク内から偽装可能。セキュリティグループで ALB のみからのアクセスに制限する設計が必要 |
| **バックエンドコード変更が必要（本構成の場合）** | 既存の `X-Organization-Id` ヘッダーを読む実装を `X-Amzn-Mtls-Clientcert-Subject` の解析に変更する必要がある（REPORT3.md に詳細あり） |

## 4. NLB の特徴・メリット・デメリット

### メリット

| カテゴリ | 内容 |
|---------|------|
| **超低レイテンシ・高スループット** | TCP をほぼそのまま転送するため、レイテンシが非常に低い（マイクロ秒レベル） |
| **TCPパススルー** | TLS を終端せずバックエンドに転送できる。クライアント証明書の情報をバックエンド（nginx）に届けられる |
| **静的IP（Elastic IP）の割り当て可能** | ファイアウォールの IP 許可リストに固定 IP を登録できる |
| **UDP サポート** | ALBがサポートしない UDP プロトコルに対応 |
| **バックエンドコード変更不要（本構成の場合）** | 現在の nginx + `X-Organization-Id` ヘッダーの実装をそのまま維持できる |

### デメリット

| カテゴリ | 内容 |
|---------|------|
| **WAF との統合不可** | AWS WAF をアタッチできない。DDoS対策・IP フィルタリング・レートリミットは別途構築が必要 |
| **HTTPルーティング不可** | パスベース・ホストベースのルーティングはできない |
| **アクセスログが TCP レベルのみ** | HTTP レベルの情報（パス・ステータスコード）は記録されない |
| **ヘルスチェックが TCP レベルのみ** | TLSパススルー時は HTTP ヘルスチェック不可。コンテナ単位の障害を正確に検知できない（後述） |
| **mTLS をネイティブにサポートしない** | NLB 自体はクライアント証明書を検証できない。nginx コンテナが SSL 終端・証明書検証・CN抽出・ヘッダー付与をすべて担う必要があり、管理コストが発生する |
| **SSL証明書の手動管理** | nginx コンテナ内の証明書は SSM Parameter Store や手動ビルドで管理する必要があり、有効期限切れリスクがある |
| **セキュリティグループの制限** | NLBはセキュリティグループを持たないため、ターゲット（ECSタスク）側のSGで制御する必要がある（`0.0.0.0/0` を開放しがちになる） |

## 5. 負荷分散（複数タスク構成）での動作比較

### ALB の場合（2タスク構成）

ALB はターゲットグループに登録されているタスクに対して、順番にリクエストを振り分けます（ラウンドロビン）。

```
ユーザーAのリクエスト → [ALB] → フロントエンド タスク①
ユーザーBのリクエスト → [ALB] → フロントエンド タスク②
ユーザーCのリクエスト → [ALB] → フロントエンド タスク①
           ↑
       交互に振り分け（ラウンドロビン）
```

#### フェイルオーバーの動作

タスク①が停止した場合、ALB は HTTP レベルのヘルスチェック（`/api/health` → 200 OK）で異常を即座に検知し、タスク①への振り分けを自動的に停止します。

```
        [ALB]
    ┌────┴────┐
    ▼         ▼
タスク①     タスク②
（❌ 停止）   （稼働中）
         ↓
    ALB が ヘルスチェック失敗を検知 → タスク①には振り分けない
```

→ ユーザーはサービス停止を体感しない（ダウンタイムゼロ）

#### セッション（ログイン状態）への影響

このシステムは **ElastiCache Redis でセッションを集中管理** しているため、どちらのタスクに振り分けられてもセッション切れは発生しません。

```
タスク①  ─┐
           ├──→ ElastiCache Redis（セッション共有）
タスク②  ─┘
```

---

### NLB の場合（2タスク構成）

NLB も複数タスクへの振り分けは可能ですが、**TCP コネクション単位**での振り分けになります。

```
NLB（TCPパススルー）
    ├── nginx + frontend タスク①（ポート443）
    └── nginx + frontend タスク②（ポート443）
```

1つの TCP コネクション（＝1回の HTTPS 接続）は同じタスクに固定されます。

#### ヘルスチェックの課題（重大）

NLB は TCP レベルのヘルスチェックしかできないため、**コンテナ単位の障害を正確に検知できません**。

```
タスク①の状態:
  nginx コンテナ ✅ 起動中（ポート443が開いている）
  frontend コンテナ ❌ クラッシュ

NLB のヘルスチェック（TCPレベル）: ✅ 正常と誤判定
→ ユーザーはタスク①に振り分けられると 502 エラーになる
```

ALB であれば `/api/health` が 502 を返した時点でタスク①への振り分けを停止しますが、NLB は TCP が繋がる限り気づけません。

## 6. 比較まとめ

### 基本特性

| 比較項目 | ALB | NLB |
|--------|-----|-----|
| OSI層 | レイヤー7（アプリケーション） | レイヤー4（トランスポート） |
| プロトコル | HTTP / HTTPS / WebSocket | TCP / UDP / TLS |
| レイテンシ | やや高い（HTTPパース分のオーバーヘッド） | 超低レイテンシ（マイクロ秒） |
| スループット | 高い（一般Webアプリには十分） | 非常に高い |
| 静的IP | ❌（DNS名のみ） | ✅（Elastic IP 割り当て可） |

### mTLS / 証明書管理

| 比較項目 | ALB | NLB |
|--------|-----|-----|
| mTLS ネイティブサポート | ✅（2023年〜） | ❌（TCPパススルーで nginx に委ねる） |
| サーバー証明書管理 | ACM（自動更新） | SSM + 手動管理（年次更新） |
| nginx コンテナの必要性 | **不要** | **必要** |
| バックエンドコード変更（本構成） | 必要（ヘッダー解析変更） | 不要（現状維持） |

### セキュリティ・運用

| 比較項目 | ALB | NLB |
|--------|-----|-----|
| AWS WAF 統合 | ✅ 可能 | ❌ 不可 |
| アクセスログ | HTTP レベル（パス・ステータスコード） | TCP レベルのみ |
| ヘルスチェック | HTTP レベル（正確） | TCP レベル（コンテナ障害を検知しにくい） |
| セキュリティグループ | ALB 自体に SG を持てる | ECS タスク側 SG での制御のみ（開放しがち） |

### 負荷分散（複数タスク構成）

| 比較項目 | ALB（2タスク） | NLB（2タスク） |
|--------|--------------|--------------|
| 振り分け方式 | ラウンドロビン（リクエスト単位） | TCPコネクション単位 |
| フェイルオーバー精度 | 高い（HTTP ヘルスチェック） | 低い（TCP レベルのみ） |
| コンテナ単体クラッシュの検知 | ✅ 即座に検知・切り離し | ❌ nginx が生きていると気づけない |
| セッション維持 | ✅（Redis 共有のため問題なし） | ✅（Redis 共有のため問題なし） |

## 7. このシステムへの適用結論

### 検証環境で NLB を採用した理由

`deploy-guide-aws.md` に記載の通り、nginx が mTLS（クライアント証明書認証）を行う構成上、  
ALB でHTTPS終端するとクライアント証明書の情報が消えてしまうため、NLBのTCPパススルーを選択していた。

### 本番環境では ALB 採用を推奨

AWS が2023年に ALB の mTLS ネイティブサポートを追加したことで、検証環境での技術的制約は解消されている。  
本番環境では以下の理由から ALB 採用を推奨する。

| 推奨理由 | 詳細 |
|---------|------|
| **セキュリティ強化** | WAF 統合によるDDoS対策・IP制限が可能。NLBでは対応不可 |
| **運用コスト削減** | nginx コンテナ・SSM証明書管理・年次証明書更新作業が不要になる |
| **証明書自動更新** | ACM サーバー証明書の自動更新でリスク排除（カスタムドメイン取得が前提） |
| **障害検知の精度向上** | HTTPヘルスチェックにより、コンテナ単体の障害を即座に検知・切り離し可能 |
| **アーキテクチャのシンプル化** | NLB + nginx タスク管理 → ALB 1台に集約 |
| **HTTPアクセスログ** | S3 への詳細ログ出力で障害調査・監査が容易 |

移行に際してバックエンドコードの変更が必要だが、REPORT3.md にまとめた通り  
`authController.ts` と `authRoutes.ts` の局所的な修正で対応可能。  
また、カスタムドメインの取得（REPORT.md 問題点9）と合わせて対応することで  
ACM 自動更新の恩恵も受けられる。

## 3. 現状分析

### 3.1 現在の実装

**ルート定義** (`backend/src/routes/projectRoutes.ts`):
```typescript
router.put(
  '/:projectName/instructions/:instructionId/confirm',
  authMiddleware,
  [
    param('projectName')
      .notEmpty()
      .withMessage('projectNameは必須です')
      .isLength({ min: 1, max: 255 })
      .withMessage('projectNameは1〜255文字である必要があります'),
    param('instructionId')
      .isUUID()
      .withMessage('instructionIdはUUID形式である必要があります'),
  ],
  projectController.confirmInstruction
);
```

**コントローラー** (`backend/src/controllers/projectController.ts`):
```typescript
export async function confirmInstruction(req: Request, res: Response): Promise<void> {
  // ...認証チェック省略...
```

### 3.2 問題点

1. **ミドルウェアチェーンの不備**
   - `handleValidationErrors`ミドルウェアが使用されていない
   - バリデーションエラーがコントローラーまで到達してしまう

2. **バリデーション処理の重複**
   - ルート定義でバリデーションを定義しているのに
   - コントローラー内でも同じバリデーションを実施している
   - DRY原則に違反

3. **エラーレスポンスの非統一**
   - コントローラー内で個別にエラーレスポンスを生成
   - `handleValidationErrors`の統一形式が使われていない

## 6. 技術的詳細

### 6.1 バリデーション方針（backend.md準拠）

**ミドルウェアチェーンの順序:**
```
auth → tenantIsolation → [バリデーションルール] → handleValidationErrors → controller
```

ただし、このAPIの場合：
- `tenantIsolation`は不要（authMiddlewareがorganization_idを処理）
- 実際のチェーン: `auth → [バリデーションルール] → handleValidationErrors → controller`

**バリデーションエラーレスポンス形式:**
```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "バリデーションエラーが発生しました",
    "details": [
      {
        "field": "projectName",
        "message": "projectNameは必須です",
        "code": "REQUIRED_FIELD"
      }
    ]
  },
  "meta": {
    "timestamp": "2026-02-06T15:59:00.000Z",
    "requestId": "req_abc123"
  }
}
```

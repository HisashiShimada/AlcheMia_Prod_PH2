# タスク計画書: ログイン時に部門CDを保存する機能の検討と実装

## メタデータ
- **作成日時**: 2026-02-02 14:58
- **タスクID**: login-department-cd-storage
- **優先度**: 中
- **推定工数**: 2-4時間（実装方針による）

## 1. タスク概要

ログイン時にユーザーの部門CD（department_cd）を保存し、後続のリクエストで利用できるようにする機能の検討と実装。

## 2. 現状分析

### 2.1. データベース構造
✅ **organization_userテーブルに部門CDカラムが存在**
- カラム名: `depertment_cd` （※スペルミス: depertment → department）
- 型: `CHARACTER VARYING(50)`
- NULL許容

### 2.2. 現在のセッション管理方式
- **JWT + sessionStorage方式**
  - JWTトークンをクライアント側sessionStorageに保存
  - サーバー側でのセッション管理なし
  - **Redisは未使用**

### 2.3. 現在のログイン処理
```typescript
// authController.ts - login関数
const userQuery = `
  SELECT 
    user_id,
    user_name,
    mail_address,
    role,
    organization_id,
    is_active,
    locked_until
  FROM organization_user
  WHERE user_name = $1 AND organization_id = $2
`;
```
**問題**: 部門CD（depertment_cd）を取得していない

### 2.4. JWT生成処理
```typescript
// authController.ts - verifyPin関数
const jwtResult = await jwtService.generate({
  userId: userInfo.id,
  organizationId: userInfo.organizationId,
  role: userInfo.role,
  sessionId: uuidv4(),
  permissions,
});
```
**問題**: 部門CDをJWTペイロードに含めていない

## 3. 実装方針の検討

### 方針A: JWTペイロードに部門CDを追加（推奨）★

**メリット**:
✅ 既存のJWT認証基盤を活用
✅ 追加インフラ不要
✅ 実装が最もシンプル
✅ クライアント側でも参照可能
✅ ステートレスな設計を維持

**デメリット**:
❌ トークンサイズが若干増加（50バイト程度）

**実装箇所**:
1. `authController.ts` - login関数でdepertment_cdを取得
2. `authController.ts` - verifyPin関数でJWTペイロードに追加
3. `jwtService.ts` - JWTペイロード型定義に追加
4. `authMiddleware.ts` - req.userに部門CDを設定

### 方針B: Redisにセッション情報として保存

**メリット**:
✅ サーバー側で集中管理
✅ セッション無効化が容易
✅ 複数サーバー間でセッション共有可能

**デメリット**:
❌ Redisインフラが必要（追加コスト）
❌ 実装工数が大きい
❌ 既存のJWT方式と二重管理になる
❌ ステートフルな設計になる

**実装箇所**:
1. Redisクライアントのセットアップ
2. Redis接続設定
3. セッションサービスの実装
4. ログイン時にRedisに保存
5. authMiddlewareでRedisから取得

### 方針C: データベースから必要時に取得

**メリット**:
✅ 実装が最もシンプル
✅ 常に最新の部門CDを取得

**デメリット**:
❌ 毎回DBアクセスが発生（パフォーマンス低下）
❌ DB負荷増加

## 4. 推奨実装方針: **方針A（JWTペイロード追加）**

### 理由
1. 既存のJWT認証基盤を最大限活用
2. 追加インフラ不要
3. 実装工数が最小
4. ステートレスな設計を維持
5. パフォーマンスへの影響なし

## 8. セキュリティ考慮事項

### 8.1. データの機密性
- 部門CDは機密情報ではない（組織内の部署コード）
- JWTトークンに含めても問題なし

### 8.2. JWT検証
- 既存のJWT検証機能で自動的に改ざん検知
- 特別なセキュリティ対策不要

### 8.3. NULL処理
- 部門CDはNULL許容カラム
- NULL値を適切にハンドリング

## 9. リスクと対策

| リスク | 影響度 | 発生確率 | 対策 |
|--------|--------|----------|------|
| 既存のJWT検証が部門CDを拒否 | 低 | 低 | 型定義を正しく更新すれば問題なし |
| 部門CDがNULLの場合のエラー | 中 | 中 | NULL許容型として扱い、デフォルト値を設定 |
| フロントエンドでの表示崩れ | 低 | 低 | UserInfo型を更新して対応 |
| トークンサイズ増加 | 極低 | 高 | 50バイト程度の増加は無視できる |

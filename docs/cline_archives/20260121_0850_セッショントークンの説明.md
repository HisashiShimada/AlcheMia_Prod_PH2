# セッショントークンの説明

## 📖 セッショントークンとは？

**セッショントークン（Session Token）** は、2段階認証プロセスの第1段階（ログイン）と第2段階（PINコード検証）をつなぐための **一時的な識別子** です。

## 🔐 2段階認証における役割

### 全体フロー

```
【第1段階】ログイン
↓
ID・パスワード入力
↓
サーバー: 認証成功 → セッショントークン生成 ← ここ！
↓
サーバー: PINコード生成・メール送信
↓
クライアント: セッショントークンを保存
↓
↓
【第2段階】PINコード検証
↓
PINコード入力
↓
クライアント: セッショントークン + PINコードを送信 ← ここでも使う！
↓
サーバー: セッショントークンでユーザーを特定
↓
サーバー: PINコードを検証
↓
サーバー: 検証成功 → JWTトークン（本セッション）生成
↓
ログイン完了
```

## 💻 実際のコード（backend/src/controllers/authController.ts）

### 第1段階：ログイン時にセッショントークン生成

```typescript
// authController.ts の login 関数（214-215行目）
export async function login(req: Request, res: Response): Promise<void> {
  // ... ID・パスワード検証処理 ...

  const sessionToken = `temp_session-${uuidv4()}_${Date.now()}`;
  //                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  //                    形式: temp_session-{UUID}_{タイムスタンプ}
  
  // このセッショントークンと紐づけてPINコードを保存
  const pinResult = await pinCodeService.generateAndSave(
    user.user_id,
    user.organization_id,

  };

  res.status(200).json({
    success: true,
    data: responseData,
    // ...
  });
```

### 第2段階：PINコード検証時にセッショントークンを使用

```typescript
// authController.ts の verifyPin 関数（862行目〜）
export async function verifyPin(req: Request, res: Response): Promise<void> {
  // クライアントから送られてきたセッショントークンを取得
  const authHeader = req.headers.authorization; // "Bearer temp_session-..."
  const sessionToken = tokenMatch[1]; // "temp_session-..."
  const pinCode = req.body.pinCode;   // "123456"

  // セッショントークンとPINコードで検証
  const verifyResult = await pinCodeService.verify(pinCode, sessionToken);
  //                                                         ↑
  //                                        ここでセッショントークンを使って
  //                                        ユーザーを特定してPINコード検証

  if (!verifyResult.success) {
    // PINコード不正
    return;
  }

  // 検証成功 → JWTトークン（本セッション）を生成
  const jwtToken = await jwtService.generate({
    userId: userInfo.id,
    organizationId: userInfo.organizationId,
    role: userInfo.role,
    sessionId: uuidv4(),
  });

  // JWTトークンをHTTPOnly Cookieに設定
  res.cookie('maiml_session', jwtToken, {
    httpOnly: true,
    secure: true,
    maxAge: 24 * 60 * 60 * 1000, // 24時間
  });

  // セッショントークンは使用済みなので削除
  await pinCodeService.delete(sessionToken);
  
  // ログイン完了
}
```

## 🔑 セッショントークンとJWTトークンの違い

| 項目 | セッショントークン | JWTトークン |
|------|------------------|------------|
| **用途** | 2段階認証の途中状態を管理 | ログイン完了後のセッション管理 |
| **有効期限** | 5分（短い） | 12〜48時間（ロール別） |
| **保存場所（クライアント）** | メモリ（useState） | HTTPOnly Cookie |
| **保存場所（サーバー）** | pin_codesテーブル | なし（ステートレス） |
| **形式** | `temp_session-{UUID}_{timestamp}` | JWT形式（署名付き） |
| **使用回数** | 1回限り（使用後削除） | 有効期限まで何度でも |
| **セキュリティレベル** | 一時的・限定的 | 高（署名付き、暗号化） |

## ⚠️ なぜセッショントークンが必要なのか？

### 問題: セッショントークンがない場合

```
ユーザーがPINコードを入力
↓
サーバー: 「このPINコードは誰のもの？」 ← わからない！
```

PIN<br/>コードだけだと、以下の問題が発生します：

1. **ユーザーを特定できない**
   - 同時に複数のユーザーがログイン中の場合、どのPINコードが誰のものかわからない
   
2. **セキュリティリスク**
   - PINコードだけで認証すると、他人のPINコードを入力できてしまう

### 解決: セッショントークンを使う

```
ユーザーがPINコード + セッショントークンを送信
↓
サーバー: セッショントークンでユーザーを特定
↓
サーバー: そのユーザーのPINコードと照合
↓
検証成功！
```

## 🔒 セキュリティ上の特徴

### 1. 短い有効期限
- **5分間**のみ有効
- 時間切れ後は無効化

### 2. 1回限りの使用
- PINコード検証成功後、即座に削除
- 再利用不可

### 3. 試行回数制限
- PINコード入力失敗を追跡
- 5回失敗でロックアウト

### 4. 組織ID必須
- マルチテナント分離
- 他組織のセッショントークンは使用不可

## 📝 まとめ

**セッショントークンの役割:**

1. **第1段階と第2段階の橋渡し**
   - ログイン → PINコード検証の間を繋ぐ

2. **ユーザーの一時的な識別**
   - 「誰がログインしようとしているか」を追跡

3. **PINコードとの紐付け**
   - どのユーザーのPINコードかを管理

4. **セキュリティ確保**
   - 短い有効期限（5分）
   - 1回限りの使用
   - 試行回数制限

**開発環境でスキップされている問題:**

現在の実装では、デバッグユーザーでログインすると：
- ❌ セッショントークンが生成されない
- ❌ PINコードが生成・保存されない
- ❌ 2段階認証フローがテストできない

これが、調査レポートで指摘した問題の核心です。

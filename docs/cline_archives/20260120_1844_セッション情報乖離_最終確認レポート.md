## 🚨 セキュリティ脆弱性

### 攻撃シナリオ

```
ステップ1: 攻撃者が組織Aの有効なクライアント証明書を入手
ステップ2: 組織Bのユーザー名/パスワードを何らかの方法で入手
ステップ3: 組織Aの証明書で接続し、組織Bのユーザーでログイン試行
ステップ4: 現在の実装では、以下の理由でログイン成功してしまう：
  - login関数: 証明書の組織ID（A）でユーザー検索 → 見つからない
  - しかし、整合性チェックがないため、異なる組織のユーザーでもパスワードが合えば通過する可能性
```

### 影響
- **データ漏洩**: 他組織のデータへの不正アクセス
- **マルチテナント分離の崩壊**: 組織間の壁が破られる
- **コンプライアンス違反**: データ保護規制に抵触

## ✅ 具体的な乖離ポイント

### 乖離1: 証明書の組織IDとユーザーの組織IDの不一致を検出できない

| 項目 | クライアント証明書ミドルウェア | ログインコントローラー | 問題 |
|------|-------------------------------|----------------------|------|
| 組織ID取得元 | Nginx（証明書CN） | X-Organization-Idヘッダー | ✅ 同じ |
| 使用タイミング | リクエスト開始時 | ユーザー検索時 | ✅ OK |
| DBユーザーとの整合性チェック | - | ❌ **未実装** | 🚨 **危険** |

### 乖離2: セッションに保存される組織IDの検証不足

| 項目 | 値 | 検証 |
|------|-----|------|
| 証明書の組織ID | `req.organizationId` | Nginxで検証済み ✅ |
| DBユーザーの組織ID | `user.organization_id` | パスワード検証のみ ✅ |
| **両者の一致** | - | ❌ **未検証** |
| JWTに保存される組織ID | `userInfo.organizationId` | DBから取得（検証なし） ❌ |

## 🔧 必要な修正

### 修正1: login関数に整合性チェック追加（必須）

```typescript
// ユーザー検索成功後、パスワード検証前に追加
if (user.organization_id !== organizationId) {
  // 監査ログ記録
  const historyQuery = `
    INSERT INTO login_history (user_name, organization_id, login_at, login_sf, failure_reason)
    VALUES ($1, $2, NOW(), $3, $4)
  `;
  await pool.query(historyQuery, [
    user.user_name,
    organizationId,  // 証明書の組織ID
    false,
    'Organization ID mismatch (certificate vs user)',
  ]);

  res.status(403).json({
    success: false,
    error: {
      code: 'AUTH_ORGANIZATION_MISMATCH',
      message: '組織IDが一致しません。正しいクライアント証明書を使用してください',
    },
    meta: {
      timestamp: new Date().toISOString(),
      requestId,
    },
  });
  return;
}
```

# MaiMLデータのWEB反映問題 - 調査レポート

**作成日**: 2026-03-03 14:09  
**優先度**: Critical  
**実装難易度**: High  
**影響範囲**: Frontend + Backend

---

## 📋 問題概要

### 現状の問題点
- アップロードしたMaiMLファイルにデータがある場合、WEB上で反映されない
- Data要素の解析・抽出・表示が不完全

### 改善の目的
- データの完全な表示
- アップロードファイルの即座反映

---

## 🔍 調査結果

### 1. バックエンド側の現状

#### 1.1 MaiMLパーサー（`maimlParser.ts`）
**現状**: 
- `analyzeMaiMLFile()`: 構造解析、バリデーション、統計情報の収集
- **Data要素の解析なし** ❌

**確認項目**:
```typescript
// maimlParser.ts の解析対象
- syntax validation
- structure validation
- reference validation
- duplicate ID validation
- places/transitions/arcs の統計
```

**問題点**:
- `<data>` タグの解析ロジックが存在しない
- `analyzeContent()` 関数でData要素をカウントしていない
- Data要素の内容を抽出する処理がない

#### 1.2 メタデータ抽出（`maimlMetadataExtractor.ts`）
**現状**:
```typescript
export interface MetaData {
  document_uuid: string;
  document_name: string;
  document_description: string;
  measurement_values: string[];  // ✅ 抽出済み
  units: string[];               // ✅ 抽出済み
  section_types: string[];
  ids: string[];
  refs: string[];
  keys: string[];
  elements: string[];
  values: string[];              // ✅ 抽出済み（プリミティブ値）
}
```

**確認結果**:
- `extractFromNode()`: 再帰的にXMLを走査
- `measurement_values`, `units`, `values` を収集
- ただし、**Data要素の構造化されたデータは抽出していない**

**問題点**:
- `<data>` タグ配下の構造化されたデータ（key-value pair、配列等）を抽出していない
- Place/Transitionごとのデータ紐付けがない

#### 1.3 MaiMLサービス（`maimlService.ts`）
**現状**:
```typescript
// saveMaiML() - MAIMLファイル保存時
1. S3/Swiftにアップロード
2. maimlMetadataExtractorでメタデータ抽出
3. file_metadataテーブルに保存（JSONB形式）
   - maiml_measurement_values
   - maiml_units
   - maiml_values
   - 等...
4. project_maiml_flg を true に更新
```

**確認結果**:
- メタデータは `file_metadata` テーブルのJSONBカラムに保存される
- しかし、**Place/Transitionごとの詳細データは保存されていない**

#### 1.4 データベーススキーマ

##### `file_metadata` テーブル
```sql
-- メタデータのみを格納（JSONB形式）
maiml_measurement_values JSONB,
maiml_units JSONB,
maiml_values JSONB,
...
```

##### `template_data` テーブル（存在確認済み）
```sql
CREATE TABLE template_data (
    id UUID PRIMARY KEY,
    organization_id VARCHAR(255) NOT NULL,
    project_id UUID NOT NULL,
    method_id VARCHAR(255) NOT NULL,
    task_no INTEGER NOT NULL,
    place_id VARCHAR(255) NOT NULL,
    template_type VARCHAR(50) NOT NULL,  -- material/condition/result
    template_id VARCHAR(255) NOT NULL,
    data JSONB NOT NULL,                  -- 🎯 実験データ本体
    status VARCHAR(50),
    comment TEXT,
    recorded_by UUID NOT NULL,
    recorded_at TIMESTAMP NOT NULL,
    ...
    CONSTRAINT template_data_unique_key 
        UNIQUE (organization_id, project_id, method_id, task_no, place_id)

```

**用途**:
- **実験記録画面** で作業者が入力したデータを保存
- Place単位でデータを管理
- Material/Condition/Result の3タイプに対応

**問題点**:
- **アップロード時にMaiMLファイル内のData要素を `template_data` に保存する処理がない** ❌

## 📐 考慮すべき仕様

### 1. MaiML XML構造の理解

#### Data要素の配置場所（推測）
```xml
<maiml>
  <protocol>
    <method>
      <pnml>
        <place id="place_1">
          <name>Material A</name>
          <!-- Data要素はここに配置される可能性 -->
          <data>
            <property key="weight">100</property>
            <property key="unit">g</property>
            <property key="purity">99.5</property>
          </data>
        </place>
        
        <transition id="trans_1">
          <name>Mixing</name>
          <!-- Transitionにもデータがある可能性 -->
          <data>
            <parameter key="temperature">25</parameter>
            <parameter key="duration">300</parameter>
          </data>
        </transition>
      </pnml>
    </method>
  </protocol>
</maiml>
```

**確認が必要**:
- 実際のMaiML XMLファイルのサンプルを確認
- `<data>` タグの正確な構造を特定
- XSD（XML Schema Definition）があれば参照

### 2. データ型の対応

#### 想定されるデータ型
- **文字列**: `<property key="name">Sample</property>`
- **数値**: `<property key="weight">100</property>`
- **単位付き数値**: `<measurement value="25" unit="°C" />`
- **配列**: `<list>...<item>...</item>...</list>`
- **ネスト構造**: `<group><subgroup>...</subgroup></group>`

#### データ型の判定ロジック
```typescript
// 数値判定
if (!isNaN(Number(value))) {
  return { type: 'number', value: Number(value) };
}

// 日付判定
if (!isNaN(Date.parse(value))) {
  return { type: 'date', value: new Date(value) };
}

// 文字列
return { type: 'string', value: String(value) };
```

### 3. データの保存戦略

#### オプション1: 完全なJSONB保存（推奨）
```typescript
// template_data.data カラムに完全な構造を保存
{
  "properties": {
    "weight": { "value": 100, "type": "number", "unit": "g" },
    "purity": { "value": 99.5, "type": "number", "unit": "%" }
  },
  "measurements": [
    { "timestamp": "2026-01-15T10:00:00Z", "value": 25.5, "unit": "°C" }
  ]
}
```

**利点**:
- 柔軟性が高い（任意の構造を保存可能）
- 検索が容易（GINインデックス使用）
- 既存の `template_data` テーブル構造と整合

**欠点**:
- 型チェックが弱い（実行時エラーの可能性）

#### オプション2: 正規化テーブル
```sql
CREATE TABLE data_properties (
    id UUID PRIMARY KEY,
    template_data_id UUID REFERENCES template_data(id),
    property_key VARCHAR(255) NOT NULL,
    property_value TEXT,
    data_type VARCHAR(50),  -- string/number/date/boolean
    unit VARCHAR(50),
    ...
);
```

**利点**:
- データ整合性が高い
- 検索・集計が高速

**欠点**:
- スキーマ変更が必要
- 複雑なクエリが必要

**推奨**: **オプション1（JSONB保存）** を採用
- 既存テーブル構造を活用
- 実装が容易
- Phase 1としては十分

### 4. パフォーマンス考慮事項

#### 大量データの処理
- **想定**: 1ファイルに100〜1,000個のPlaceがある場合
- **対策**:
  - バッチINSERT（一括保存）
  - トランザクション使用
  - 非同期処理（fire-and-forget）

#### データ取得の最適化
- **問題**: ノードクリック毎にAPIリクエスト
- **対策**:
  - 初回ロード時に全データをキャッシュ
  - useContextで共有
  - または、React Queryでキャッシュ管理

#### 例: キャッシュ戦略
```typescript
// 初回ロード時に全データ取得
useEffect(() => {
  if (fileContent && projectId && taskNo) {
    fetchAllTemplateData(projectId, taskNo).then(data => {
      setDataCache(data);  // 全データをキャッシュ
    });
  }
}, [fileContent, projectId, taskNo]);

// ノードクリック時はキャッシュから取得
const handleNodeClick = (node) => {
  const cachedData = dataCache[node.id];
  if (cachedData) {
    // キャッシュから即座に表示
  }
};
```

### 5. データバインディングのフロー

```
[アップロード]
  ↓
[XMLパース] (maimlParser.ts)
  ├─ Place/Transition抽出
  └─ Data要素抽出 🆕
  ↓
[DB保存] (maimlService.ts + templateDataRepository.ts)
  ├─ file_metadata (メタデータ)
  └─ template_data (Data要素) 🆕
  ↓
[UI表示] (PetriNetViewer.tsx)
  ├─ ノードクリック
  ├─ API呼び出し (fetchTemplateData) 🆕
  └─ PropertyViewer表示 (dataタブに表示) 🆕
```

### 6. エラーハンドリング

#### 想定エラーケース
1. **Data要素が存在しない**
   - メッセージ: "このPlaceにはデータがありません"
   - 対応: 空のオブジェクトを返す

2. **Data要素のパースエラー**
   - ログ記録: `console.error('[DataParser] Parse error:', error)`
   - 対応: エラー内容を `maiml_analysis_results` に記録

3. **DB保存エラー**
   - ロールバック: トランザクション使用
   - リトライ: 3回まで再試行

4. **API呼び出しエラー**
   - メッセージ: "データの取得に失敗しました"
   - 対応: リトライボタン表示

### 7. セキュリティ考慮事項

#### マルチテナント分離
- **必須**: すべてのクエリに `organization_id` フィルタ
- **検証**: tenantIsolationミドルウェアの適用

#### SQLインジェクション対策
- **必須**: Parameterized Queries使用
- **禁止**: 文字列連結でSQLクエリ構築

#### データサイズ制限
- **JSONB**: 最大1GB（PostgreSQL制限）
- **実用的制限**: 1MB程度を推奨
- **対策**: 大きすぎるデータは警告表示

### 8. テスト方針

#### 正常系テスト
1. **データを含むMaiMLファイルをアップロード**
   - 期待: template_dataテーブルにデータが保存される
   - 検証: DBレコード確認

2. **Placeノードをクリック**
   - 期待: データタブにデータが表示される
   - 検証: UI表示確認

3. **様々なデータ型の表示**
   - 文字列、数値、日付、配列等
   - 期待: 正しくフォーマットされて表示

#### 異常系テスト
1. **不正なデータ形式**
   - 期待: エラーメッセージ表示
   - 検証: エラーハンドリング確認

2. **Data要素が存在しないファイル**
   - 期待: "データはありません"と表示
   - 検証: 空状態の表示確認

3. **非常に大きなデータ**
   - 期待: 警告表示またはページネーション
   - 検証: パフォーマンス確認

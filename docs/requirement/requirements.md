## 1. 背景と目的

### 1.1 背景

材料開発に関わるデータを統合的に管理し、MI（Materials Informatics）や材料開発の効率性を高めることを目指している。データ統合管理のためにはデータフォーマットの標準化と用語の統一が必要であり、JIS標準化（JIS K0200）され現在ISO化も進められているMaiMLフォーマットを活用したデータ管理システムの開発を検討している。

**MaiMLについて**
- MaiML（Measurement/Analysis Instrument Markup Language）は、JIS K0200「計測分析装置の分析データ共通フォーマット」として2024年5月に標準制定されたXMLベースの共通フォーマット
- 国内複数の計測機器メーカ、計測機器ユーザ、アカデミアが協力して策定
- 多様な観点から見て実験を再現するに足る全ての情報を管理できるフォーマット
- 材料開発の実験から生産プロセスまで、あらゆる材料開発の作業と関係するデータを統合管理できる
- MaiMLはデータフォーマットのみを規格したものであり、システム仕様は規定していない

### 1.2 本ドキュメントの目的

本ドキュメントは、MaiMLフォーマットを活用したデータ管理システムを利用する社内ユーザが必要とする機能の共通認識を得て、過不足のない機能要求を明確にするために、システム開発のための要求を整理・分析した要件定義書である。

## 2. 現状の課題

材料開発全般でのデータ管理において以下の課題が存在する。

| # | 課題 | 詳細 |
|---|------|------|
| 1 | データ管理の属人化・分散化 | データ管理が属人的・個別かつ分散蓄積されており、他者の実験データの閲覧や再利用が困難 |
| 2 | 用語の不統一 | 同一材料や同一実験条件であっても部門ごとに異なる用語を利用。個人の管理データ内でも表記ゆれが生じ、再利用の障壁となっている |
| 3 | 実験ワークフローの未管理 | 実験の作業手順やフローが統一管理されておらず、記録されていない場合もある |
| 4 | 実験過程の記録不足 | 実験結果データは記録されているが、実験の作業実績やワークフローが一緒に記録されておらず、実験の経過を判断できない |
| 5 | 実験中の気づきが記録されない | 実験作業者が気づいたことや失敗原因などが記録されておらず、改善に向けたデータ利活用がなされていない |
| 6 | 計測データフォーマットの多様性 | 計測装置や計測装置メーカごとに異なるフォーマットでのデータを出力するため、統一管理が困難 |
| 7 | データの真正性確認が困難 | 記録・蓄積されているデータの真正性を確認できず、再利用が阻まれる（実データか記録エラーか改ざんデータか判断できない） |
| 8 | 外部共同研究のデータ活用困難 | 共同研究先や外部委託開発先でのデータフォーマットが共通化されておらず、入手できたデータの活用が困難 |

## 3. システム導入の目的とゴール

### 3.1 目的

- 分散・属人化しているデータを統合管理する部門横断的なデータ基盤を整備する
- 記録・蓄積データを活用したMI/PIでのシミュレーションやプロセス最適化を実施する
- 実験効率の向上や再現性の改善を実現する

### 3.2 ゴール

- 過去や他部門の類似実験データ・失敗実験を含む記録データを活用し、MI/PIによる材料特性推定の精度向上
- 実験データのみならず実験プロセス・実験中のエラーとその想定原因・実験に関する洞察を記録
- 実験作業者が気づいたこと、新たな発想、ワークフロー内のどの時点で気付いたかをメモとして記録
- 実験結果の信頼性フラッグ（○：デフォルト、×：誤り確実、△：誤り可能性あり）を実験管理者が付記
- 事前設定した実験条件と異なる条件で実験した場合、実際の実験条件を記録
- データの改ざん防止と、ヒューマンエラー防止により、実験データを安心して再利用可能にする
- 将来的には共同研究先や連携機関での材料実験データも管理できる仕組みとする

## 4. 用語定義

本システムで扱う主要アイテムの定義を以下に示す。

### 4.1 ユーザが主に編集する6種類のアイテム

| アイテム | 意味 | 対応するMaiML要素 |
|---------|------|-----------------|
| プロジェクト | 一連の実験/計測の工程（ワークフロー）と、この工程を用い実験条件を変えて繰り返す実験/計測（タスク）の集合を表す | （なし） |
| ワークフロー | 実験/計測の工程を表す | `<pnml>`, `<program>` |
| 作業手順 | 最小単位の実験/計測の作業とその手順を表す | `<pnml>`, `<instruction>` |
| テンプレート | MaiML仕様のテンプレートを表す。実験/計測の条件として設定されるプロパティ群、または実験/計測結果として記録されるプロパティ群を表す | `<materialTemplate>` / `<conditionTemplate>` / `<resultTemplate>` |
| タスク | 実験条件を変えて実施するそれぞれの実験/計測を表す。テンプレートのプロパティ群に対して値を設定していくことでタスクは進行する。タスクは実験条件および実験結果を持つ | `<results>` |
| タスクログ | 各タスクにおける実験/計測のログを表す | `<eventlog>` |

### 4.2 参照用ベースアイテム

| アイテム | 意味 | 対応するMaiML要素 |
|---------|------|-----------------|
| ワークフローベース | ワークフローを作成する際に参照・引用するベース（お手本） | `<pnml>`, `<program>`（ワークフローベースのみ記載したMaiMLサブセット） |
| 作業手順ベース | 作業手順を作成する際に参照・引用するベース（お手本） | `<pnml>`, `<program>`（作業手順ベースのみ記載したMaiMLサブセット） |
| テンプレートベース | テンプレートを作成する際に参照・引用するベース（お手本） | `<program>`（テンプレートベースのみ記載したMaiMLサブセット） |

### 4.3 事前設定が必要なアイテム

| アイテム | 意味 | 対応するMaiML要素 |
|---------|------|-----------------|
| 実験装置 | 管理する実験/計測装置やソフトウェアを表す。シリアル番号別/バージョン別に管理する | `<creator>` |
| 実験装置タイプ | 実験/計測装置・ソフトウェアの一般名またはタイプを表す | `<instrument>` |
| 実験装置ベンダー | 実験/計測装置やソフトウェアのベンダーを表す | `<vendor>` |
| 実験者 | 実験/計測を実施した実験者を表す | `<owner>` / `<eventlog>` |
| MaiML属性セット | MaiMLファイルを出力する際に、`<MaiML>`要素の属性を表す。名前空間を追加する際に変更する | `<maiml>` |
| プロパティセット | すべての実験情報で用いるプロパティの定義を表す。MaiML仕様には記録すべきプロパティの規定はなく各組織で定めて運用する | `<property>` / `<content>` |

## 5. 想定ユーザ・ステークホルダー

### 5.1 ユーザクラスと役割

本システムでは以下の6種類のロールを定義する。システム運用上のロール（provider、system_admin）と業務ロール（data_admin、experiment_admin、experiment_worker、mi_engineer）に大別される。

| ロール（システム内部名） | ユーザクラス | 役割の概要 | 想定スキル |
|------------------------|------------|-----------|-----------|
| provider | プロバイダ | システムプロバイダ。組織の作成・管理、会社マスタの管理を担当。複数組織を横断的に管理する最上位の管理者 | システム管理・運用の知識 |
| system_admin | システム管理者 | 組織内のICTシステム管理者。ユーザ登録・部門設定・ロール管理・セッション管理を担当 | ICTシステム管理の知識 |
| data_admin | データ管理者 | MAIMLを理解済みの全体活動担当者。マスタデータ（Creator/Vendor/Instrument）の管理を担当 | MAIMLの知識が必要 |
| experiment_admin | 実験管理者 | 実験の設計と実行ができる担当者。プロジェクト・ワークフロー（MAIMLファイル）・タスクの作成と管理、フォーマット管理、実験指示事項の入力、実験進捗の確認を担当 | MAIMLの知識 |
| experiment_worker | 実験作業者 | 実験を着実に遂行する担当者。タスクを選択し、実験データ・メモ・ログを記録する | なし（システムが作業手順を提示） |
| mi_engineer | MI技術者 | データ分析・MIを実行する担当者。実験データの検索・分析を担当 | データ分析・MIの知識 |

## 6. システム全体構成

### 6.1 取り扱うデータの種類

本システムで扱うデータの種類は以下の通り。

1. データを相互参照するためのUUIDやID
2. 材料データ（原材料、生成材料）とそれらの特性
3. 材料開発ワークフローデータ
4. 利用する計測器・実験装置での作業指示や制御情報
5. 材料開発時の条件（温度、湿度、機器の設定情報など）
6. 材料開発時のログデータ（開始時刻、終了時刻、作業者IDなど）
7. 原材料や生成材料の計測データ（光学スペクトルデータ等の2次元データを含む）
8. 材料開発時の作業者のメモ、作業時の管理者からの指示事項

> **注）** MI/PI等の解析結果の蓄積機能は本仕様の中では扱わず、将来の検討課題とする。

### 6.2 システム構成

本システムは以下の構成要素で実現される。

#### フロントエンド（Webアプリケーション）

- React 18 + TypeScript + Next.js によるWebアプリケーション
- Webブラウザからアクセスする（端末OS・アプリ不問）
- Ant Design v6 を利用したUIコンポーネント
- ReactFlowを用いた実験ワークフロー（Petri Net形式）のグラフィカル表示・編集

#### バックエンドAPI

- Node.js 18+ + Express.js + TypeScript によるRESTful API
- フロントエンドとファイルストレージ・データベースの橋渡しを担う
- マルチテナント分離（organization_id による組織間のデータ分離）
- JWTベースの認証ミドルウェア、ロールベースアクセス制御（RBAC）

#### ファイルストレージ（データレイク）

| 環境 | ストレージ |
|------|-----------|
| 本番環境（クラウド） | AWS S3 |
| 本番環境（オンプレ） | OpenStack Swift（Dockerコンテナ）  |
| 開発環境 | OpenStack Swift（Dockerコンテナ） |

- MaiML形式（XML）ファイルをオブジェクトストレージに保存する
- マルチテナント分離のため、すべてのファイルパスは `{organization_id}/` プレフィックスを付与する
- ファイルアクセスは署名付きURL（Pre-signed URL）を通じて行う
- プロジェクトごとにバージョン管理（アーカイブ）機能を持つ

#### データベース（データカタログ）

- PostgreSQL 18+ によるリレーショナルデータベース
- プロジェクト・タスク・ユーザ・組織・ロール・ファイルメタデータ等を管理する
- MaiMLファイルから抽出したメタデータを構造化して保存し、効率的な検索を実現する
- セマンティック検索向けのベクトルデータ（pgvector拡張）も管理する
- すべてのテーブルに organization_id カラムを持ち、マルチテナント分離を実現する

#### インフラ構成

```
ブラウザ
  ↓ HTTPS
Nginx（リバースプロキシ）
  ├─ /* ─────────────────────────────────────┐
  │                                          ↓
  │                             ┌──────────────────────────┐
  │                             │ フロントエンド（Next.js）    │
  │                             └──────────────────────────┘
  │
  └─ /api/* ──────────────────────────────────┐
                                              ↓
                                ┌──────────────────────────┐
                                │ バックエンドAPI（Express）  │
                                └──────────────────────────┘
                                  ↓                    ↓
                             PostgreSQL         S3 / Swift
                            （データカタログ）   （ファイルストレージ）
```

> **注）** データマート機能（解析用データセット管理）は将来の検討課題とする。

### 6.3 認証・アクセスコントロール構成

- **JWT（JSON Web Token）+ PINコードメール認証**による独自認証システムを実装する
- ログイン時にPINコードをメール送信し、2段階認証を実現する
- JWTはHTTPOnlyクッキーとして保存し、セッション管理はデータベースと連携して二重管理する
- ロールベースアクセス制御（RBAC）により、ロールに応じた機能アクセス権限を制御する
- マルチテナント分離（organization_id）により組織間のデータアクセスを厳格に制御する
- クライアント証明書（PKCS#12形式）による追加認証にも対応する
- JWTトークンの有効期限は環境変数（`JWT_ACCESS_TOKEN_EXPIRES_IN`、`JWT_REFRESH_TOKEN_EXPIRES_IN`）で一元管理する。ロール別の個別設定は将来の検討項目とする。

## 7. 機能要件

### 7.1 データ入力機能

#### 7.1.1 概要

メインサービスを通じたマニュアル入力（GUI）を提供する。

#### 7.1.2 同時入力の禁止

実験管理者と実験作業者の同時入力は禁止する。具体的なルールは以下の通り。

| 状況 | 操作制限 |
|------|---------|
| タスク実行中（ワークフローがチェックアウト中） | 実験管理者はワークフローを修正できない |
| 実験管理者がワークフロー修正を行う場合 | 実験管理者が明示的にチェックインを行い（実験作業停止・実験作業者チェックアウト後）、実験データが更新されない状態でワークフローの修正や作業手順の修正を実施する |

#### 7.1.3 機能一覧

| # | 対象者 | 機能概要 | 備考 |
|---|--------|---------|------|
| F-INP-001 | 実験管理者 | 実験前に実験ワークフロー・作業手順・実験タスクの設定を行う | 端末⇔メインサービス⇔MaiMLデータレイクでデータ転送。ワークフロー修正登録後に自動的にデータカタログに登録 |
| F-INP-002 | 実験管理者 | 実験タスク実行中にワークフローや作業手順を修正する場合は、明示的なチェックインを行い実験作業者チェックアウト後にのみ修正できる | タスク実行中はチェックアウト（作業中）状態となり修正不可 |
| F-INP-003 | 実験作業者 | 実験者名・作業記録・実験結果・計測結果・実験ログの登録、実験作業中の問題を登録する | 実験機器・計測システムからのデータ取得含む |
| F-INP-004 | 実験管理者 | 実験指示事項の入力（実験作業の制御機能と連携） | 端末⇔メインサービス⇔MaiMLデータレイク間でデータ転送 |
| F-INP-005 | 実験作業者 | 計測・分析結果の登録 | 計測・分析システムからデータ取得 |

### 7.7 セキュリティ機能

#### 7.7.1 アクセス制限

| # | 要件 |
|---|------|
| F-SEC-001 | アクセス制限はJWT + PINコードメール認証による2段階認証とロールベースアクセス制御（RBAC）で実現する |
| F-SEC-002 | ファイルストレージ（S3/Swift）へのアクセスは署名付きURL（Pre-signed URL）を通じて行い、直接アクセスを禁止する |
| F-SEC-003 | すべてのデータ操作に organization_id によるマルチテナント分離を適用し、組織間のデータアクセスを禁止する |
| F-SEC-004 | APIへのアクセスは auth（JWT認証）→ tenantIsolation（テナント分離）→ permissionCheck（権限確認）の順のミドルウェアチェーンで制御する |
| F-SEC-005 | ロール内での個別権限は role_permission テーブルで「書込可（Ⓦ）」・「読取専用（Ⓡ）」の2段階で設定する |
| F-SEC-006 | ユーザクラスによる機能利用権限は6クラスを想定する（5章参照） |

#### 7.7.2 改ざん防止

MaiMLデータの改ざん防止は、MaiML規格に準拠して実装する。

MaiML規格では以下の2つの改ざん防止・検知機能を規定している。

**1. 単独ファイルの改ざん検知**

| 方法 | 詳細 |
|------|------|
| UUIDによる唯一性の判定 | 各MaiMLファイルに付与されたUUIDで唯一性を判定する |
| XML署名による改ざん検知 | XML署名を用いてファイルの改ざんを検知する |

**2. 複数ファイル・チェインによる改ざん負荷**

複数ファイル間で参照ファイルの情報を記録してデータチェインを生成することで、参照先ファイルと参照元ファイルの差異により改ざんを検知できる。さらに改ざんするためにはすべての参照関係でデータを改ざんしなければならないため、改ざん負荷が大きくなり防止しやすい。

| 方法 | 詳細 |
|------|------|
| 過去ファイルのUUID記録 | MaiML中にChain要素のUUIDとして記録。データ改定をした場合にはParent要素にUUIDとして記載 |
| 過去ファイルのハッシュ値記録 | MaiML中にChain要素のハッシュ値として記録。データ改定をした場合にはParent要素にハッシュ値として記載 |

> **注）** MaiML規格で定義されている秘匿方法はあるが、本システム要求の中では扱わない。

## 10. 制約・前提条件・依存関係

### 10.1 制約

#### 業務制約
- システム運用は全社ICT管理部門との整合が必須

#### 法的制約・規制
- 化学物質関連規制（PRTR、化審法）・労働安全衛生法への対応の必要性について別途確認が必要

#### 規制ガイドライン対応
- 対応すべき規制ガイドラインはない（現時点）

### 10.2 前提条件

- 端末はWebブラウザで利用可能であること（Chrome/Edge/Firefox等の最新版を推奨）
- 認証はシステム独自のJWT + PINコードメール認証で実現する（外部IDプロバイダとの連携は将来の検討項目）
- MaiMLデータの入出力はマニュアルで行う（オンライン接続は将来の検討項目）
- ファイルストレージとして AWS S3（クラウド環境）または OpenStack Swift（オンプレミス環境）が利用可能であること
- メール送信サービス（PINコード送信用）が利用可能であること
- コンテナ環境（Docker / Docker Compose）でのデプロイを前提とする

### 10.3 依存関係

#### 別システムとの接続
- 接続する必要のあるシステムの明確化と接続方式：一般的な接続方式に柔軟に対応可能な構造とする
- 接続API・SDK・データ形式（ファイル形式）は別途検討
- 転送速度制約は別途検討

#### 外部データのインポート
- データの真正性確認方法は別途検討
- インポート許可方法は別途検討
- データ検疫方法は別途検討
- データフォーマット・ファイルフォーマットの管理（バージョン管理）は別途検討
  - フォーマット変換方法・利用ツールのバージョン管理・利用制約の管理
  - フォーマット変換時のマッピング表・変換ルール・データ削除またはデータ追加の履歴
- 外部データインポート権限（権限付与者・利用者・期限などの制約）は別途検討

#### 既存データのインポート
- インポート許可方法は別途検討
- データ検疫方法は別途検討
- データフォーマット・ファイルフォーマットの管理（バージョン管理）は別途検討
- 既存データインポート権限（権限付与者・利用者・期限などの制約）は別途検討

| 第3段階 | 既存データのインポート（インポートデータの選定） |
| 第4段階 | データカタログシステム開発とデータレイクからの変換 |
| 第5段階 | データ検索システム |
| 第6段階 | データマートシステムの開発と解析システムへのデータエクスポート |
| 第7段階 | システムモニタリング機能と運用管理監視 |

## 12. 将来拡張予定事項

本仕様には含まれないが、将来の検討課題として以下を想定している。

| # | 項目 | 概要 |
|---|------|------|
| EXT-001 | 実験機器・計測システムとのオンライン接続 | 現在はマニュアル入出力のみ。将来的にはオンライン接続による自動データ取得を実現する |
| EXT-002 | 外部システム・データスペース経由での接続 | 共同研究先や連携機関のシステムとの接続 |
| EXT-003 | 解析結果のデータレイクへの蓄積 | MI/PIツール等での解析結果をデータ管理システムに蓄積・検索する機能 |
| EXT-004 | 共同研究先・連携機関でのデータ管理 | 将来的に全社として多数の部門で活用するだけでなく、共同研究先や連携機関での材料実験データも管理できる仕組み |
| EXT-005 | 接続機器のバージョン管理 | 接続機器のバージョン管理機能 |
| EXT-006 | データ漏洩防止（MaiML規格の秘匿方法） | MaiML規格で定義されている秘匿方法の実装 |
| EXT-007 | タスクのワークフローに従った実験機器・計測システムの自動制御 | 現在は手動操作のみ |
| EXT-008 | 検索クエリの蓄積場所の詳細決定 | MaiMLデータレイクを推奨するが、詳細仕様の中で検討・決定する |
| EXT-009 | 外部IDプロバイダとの連携 | 現在はシステム独自認証（JWT + PINコード）。将来的にはAzure AD / SAML / OAuth2.0等の外部IDプロバイダと連携し、社内アカウント管理システムとのシングルサインオン（SSO）を実現する |
| EXT-010 | データマートシステムの実装 | 解析用データセットの一時管理・利用後自動消去・検索クエリ保存などのデータマート機能を実装する |

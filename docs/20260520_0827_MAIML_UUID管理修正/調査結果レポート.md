# MAIML UUID管理 現状調査結果レポート

**調査日時**: 2026-05-20 08:27  
**調査目的**: MAIMLファイルのUUID管理に関する修正要件の整理

---

## 1. 修正要件（ユーザー指示）

MAIMLファイルはUUIDで要素の唯一性を担保しており、以下のルールに従う必要がある。

- 下位タグが書き換わった場合、そのタグを含む上位タグも書き換わる必要がある
- DocumentタグのUUIDはファイルとしての唯一性を担保する最上位のUUID

**対応が必要な4項目:**
1. MAIML編集開始時にベースとして読み込んだMAIMLのUUIDをParentタグに書き込む
2. Parentタグが書き込まれることで内容が変わるため、DocumentタグのUUIDを編集開始時に再採番する
3. その他のタグについて何かしら内容を変更した際にそれを検知してそのタグのUUIDを書き換える
4. 書き換わったタグを含む上位タグのUUIDを階層的に連鎖して書き換える

## 2. 既存実装の調査結果

### 2.1 Parentタグ挿入機能（実装済み）

**ファイル**: `backend/src/utils/maimlParentInjector.ts`

**呼び出し箇所**:
```typescript
// backend/src/controllers/fileAccessController.ts
import { injectParentTag } from '../utils/maimlParentInjector';

const maimlContent = result.buffer.toString('utf-8');
const injected = injectParentTag(maimlContent, projectUuid, result.buffer);
responseBuffer = Buffer.from(injected, 'utf-8');
```
→ ファイルダウンロード時に自動でParentタグを挿入してフロントエンドに返している

**機能内容**:
- 元ファイルの `<document><uuid>` 値を `<parent><uuid>` として保存
- 元ファイルのSHA-256ハッシュ（Base64）を `<parent><hash method="SHA-256">` として保存
- 既存Parentがある場合はネスト構造で履歴チェーンを保持
- 同一UUIDの重複挿入スキップ（`existingParentUuid === projectUuid` チェック）

**生成されるXML構造:**
```xml
<document>
  <uuid>OLD-UUID-XXXX</uuid>  ← ❌ ここが変わっていない（問題点1）
  <parent>
    <uuid>OLD-UUID-XXXX</uuid>  ← 元UUIDがParentに保存される
    <hash method="SHA-256">base64hash=</hash>
  </parent>
  ...
</document>
```

**問題点**: Parentタグ挿入後に内容が変わっているのに、Document直下の `<uuid>` が再採番されていない

**ファイル**: `backend/src/utils/maimlUuidExtractor.ts`

**使用箇所**: `backend/src/services/maimlWriterService.ts`（承認完了後のdata/eventLog層書き込み時のみ）

**機能**: 既存MAIMLから `data`, `eventLog`, `results`, `material`, `condition`, `result`, `log`, `trace`, `event`, `evnet` 各要素のUUIDマッピングを抽出し、同じ要素には同じUUIDを再利用

**限界**: data/eventLog層のみ対応。place/transition/template等のUUID再利用には未対応

### 2.3 フロントエンドでのMAIML生成状況

#### 単一メソッド保存
**ファイル**: `frontend/src/utils/reactFlowToMaiml.ts`

```typescript
export function generateUUID(): string {
  return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, function(c) {
    const r = Math.random() * 16 | 0;
    const v = c === 'x' ? r : (r & 0x3 | 0x8);
    return v.toString(16);
  });
}

// 保存時に毎回全要素のUUIDを新規生成
const protocolUuid = originalStructure?.protocol?.uuid || generateUUID();
const methodUuid = originalStructure?.method?.uuid || generateUUID();
const pnmlUuid = originalStructure?.pnml?.uuid || generateUUID();
maiml += `<uuid>${generateUUID()}</uuid>\n`;  // place/transition/template等
```

→ `originalStructure` から既存UUIDを再利用している箇所もあるが、place/transition/template/arcは毎回新規生成

#### 複数メソッド保存
**ファイル**: `frontend/src/utils/multiMethodConverter.ts`

```typescript
// こちらも同様に毎回新規生成
xml += `<uuid>${generateUUID()}</uuid>\n`;
```

### 2.4 MAIMLへの変換処理フロー（フロントエンド）

1. ユーザーがエディタで編集（ノード追加/削除/プロパティ編集）
2. 保存ボタン押下
3. `PetriNetEditorInner.handleSaveConfirmAction()` が実行
4. `convertMultipleMethodsToMaiML()` または `convertReactFlowToMaiML()` が呼ばれる
5. 全要素のUUIDを `generateUUID()` で新規生成してMAIML XML文字列を生成
6. バックエンドAPIに送信して保存

**問題点**: ステップ5で変更されていない要素のUUIDも毎回変わってしまう

## 3. 問題点の整理

### 問題A: 編集開始時のDocument UUID再採番なし（要件1・2）

```
現状のフロー:
  元MAIML (document.uuid = "OLD-UUID") → injectParentTag() → フロントエンドへ
  
  フロントエンドが受け取るMAIML:
    <document>
      <uuid>OLD-UUID</uuid>  ← 変わっていない
      <parent><uuid>OLD-UUID</uuid></parent>
    </document>
  
  ✅ 期待される動作:
    <document>
      <uuid>NEW-UUID</uuid>  ← Parentタグ挿入後に再採番される
      <parent><uuid>OLD-UUID</uuid></parent>
    </document>
```

**修正箇所**: `backend/src/utils/maimlParentInjector.ts`  
**修正内容**: `injectParentTag()` 末尾でDocument直下の `<uuid>` を新しいUUIDで置換する

---

### 問題B: 要素変更検知とUUID連鎖更新なし（要件3・4）

```
現状のフロー:
  placeのpropertyを編集 → 保存 → 全UUIDが新規生成（変更箇所もそうでない箇所も）
  
  ✅ 期待される動作:
  placeのpropertyを編集 → 保存
    → 変更されたplace: UUID再生成
    → そのplaceを含むpnml: UUID再生成（連鎖）
    → そのpnmlを含むmethod: UUID再生成（連鎖）
    → そのmethodを含むprotocol: UUID再生成（連鎖）
    → document全体: UUID再生成（連鎖）
    → 変更されていないplace: 既存UUID再利用
```

**主な修正箇所**:
- `frontend/src/utils/reactFlowToMaiml.ts`
- `frontend/src/utils/multiMethodConverter.ts`
- `frontend/src/components/editorv2/PetriNetEditorInner.tsx`（状態管理）

**新規作成が必要なユーティリティ**:
- `frontend/src/utils/maimlUuidMapper.ts` - 元MAIMLからUUIDマッピングを抽出

## 4. 対応タスクの分割

問題Aと問題Bは独立して対応できるため、別タスクとして管理する。

| タスク | 対応内容 | 優先度 | 難易度 |
|--------|----------|--------|--------|
| タスクA | Parentタグ追加 + Document UUID再採番 | 高 | 低（バックエンド1ファイルの修正） |
| タスクB | 下位タグ変更検知 + UUID連鎖再生成 | 中 | 高（フロントエンド広範囲修正） |

→ 各タスクの詳細計画書を別途作成する

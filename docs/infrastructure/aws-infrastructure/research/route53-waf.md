# 調査報告: AWS Route 53 と AWS WAF について

- **作成日**: 2026-04-22
- **対象**: SaaS版 AWS環境（本番環境）
- **関連ファイル**: ARCHITECTURE.md

---

## 1. AWS Route 53 とは？

**AWS が提供する DNS（ドメインネームシステム）サービス**です。

人間が読めるドメイン名（例: `app.your-domain.com`）を、コンピューターが通信に使うIPアドレスや AWS リソースの識別子に変換する「電話帳」のような役割を持ちます。

### Route 53 の役割

```
ユーザーがブラウザに入力
  app.your-domain.com
         ↓ "この名前のアドレスを教えて"
  Route 53（DNS サービス）
         ↓ "ALB のアドレスはこれです"
  ブラウザが ALB に直接接続
```

### 重要: Route 53 はデータの経路ではない

Route 53 は「通過する中継点」ではなく、**接続前に一度だけ行う名前解決**のみを担います。

```
【誤った理解】
ブラウザ → Route 53 → WAF → ALB  ← データが全てを経由するわけではない

【正しい理解】
① DNS 名前解決（接続前の一度だけ）
ブラウザ ─── "app.your-domain.com は？" ──→ Route 53
         ←── "ALB のアドレスはこれです" ───

② 実際の HTTPS 通信（データの流れ）
ブラウザ ─── HTTPS:443 ──────────────────→ ALB（直接接続）
```

名前解決が完了した後は、ブラウザが ALB のアドレスに**直接**接続します。Route 53 はその後の通信には関与しません。

## 2. 今回のシステムに Route 53 は必要か？

**カスタムドメインを取得するかどうかによります。**

### ケースA: カスタムドメインを使わない場合（Route 53 不要）

ALB の DNS 名（`xxx.ap-northeast-1.elb.amazonaws.com`）をそのまま使用します。

| 項目 | 内容 |
|------|------|
| Route 53 | **不要** |
| ACM 証明書 | 自己署名証明書を import（自動更新なし・手動更新が必要） |
| デメリット | ALB を作り直すと URL が変わる。信頼性が低い URL |

### ケースB: カスタムドメインを使う場合（Route 53 必要）

独自ドメイン（例: `app.alchemia.jp`）を取得し、Route 53 で ALB に紐付けます。

| 項目 | 内容 |
|------|------|
| Route 53 | **必要**（Alias レコードで ALB を指定） |
| ACM 証明書 | パブリック証明書を**自動発行・自動更新**（無料） |
| メリット | ALB を作り直しても URL が変わらない。ACM 自動更新が使える |

**本番環境では Route 53 + カスタムドメインを採用**（ARCHITECTURE.md の構成）。

## 3. AWS WAF とは？

**AWS が提供する Web アプリケーションファイアウォール**です。

ALB に紐付けて使用し、インターネットから来る悪意のあるリクエストを自動でブロックします。

### WAF の役割

```
ユーザー
  ↓ HTTPS:443
ALB（WAF が統合済み）
  ├── WAF のルールチェック（ALB 内部で自動実行）
  │     ├── ブロック対象 → 403 を返す
  │     └── 正常 → 通過
  ↓
ECS タスク
```

### WAF でできること

| 機能 | 内容 |
|------|------|
| **IP フィルタリング** | 特定の IP アドレスからのアクセスを許可・拒否 |
| **レートリミット** | 同一 IP から短時間に大量リクエストが来たらブロック（ブルートフォース対策） |
| **マネージドルール** | AWS が提供する既製ルールで SQLインジェクション・XSS 等を自動検知 |
| **地理的制限** | 特定の国からのアクセスをブロック |

---

## 4. 重要: WAF は ALB に「統合」されている

WAF は ALB の「外側にある別の中継サービス」ではなく、**ALB に紐付けて ALB 内部で動作する**サービスです。

```
【誤った理解】
ブラウザ → WAF（独立した中継点） → ALB  ← WAF を別途経由するわけではない

【正しい理解】
ブラウザ → ALB（WAF が統合されており、ALB 内部でフィルタリングを実行）
```

AWS コンソールでの設定は「ALB に WebACL をアタッチ（紐付け）する」という操作で完了します。

### なぜ NLB では WAF を使えないのか？

WAF は HTTP のリクエスト内容（ヘッダー・URLパス・ボディ）を見てフィルタリングします。

| ロードバランサー | HTTP 内容の解釈 | WAF のアタッチ |
|---|---|---|
| **ALB**（レイヤー7） | できる | **可能** |
| **NLB**（レイヤー4） | できない（TCP パケットをそのまま転送） | **不可** |

これが検証環境（NLB）で WAF を使えなかった理由であり、本番環境で ALB に変更することで WAF が利用可能になります。

## 5. 今回のシステムに WAF は必要か？

**必須ではありませんが、本番環境での採用を推奨します。**

### 必要性の判断

| 観点 | 内容 |
|------|------|
| **クライアント証明書認証** | 本システムは mTLS（クライアント証明書）で認証しているため、証明書なしではアプリにログインできない。この点では WAF がなくても一定の保護はある |
| **ブルートフォース攻撃対策** | 証明書を持っていても、パスワードの総当たり攻撃は可能。WAF のレートリミットが有効 |
| **DDoS 攻撃対策** | 大量リクエストでサーバーを過負荷にする攻撃への対策 |
| **ALB との統合** | ALB には WAF を直接アタッチできる（NLB では不可）。これは ALB に変更する主要なメリットの1つ |

### コスト感

- WebACL 基本料: **約 $5/月**
- マネージドルール: 1ルールグループあたり **約 $1～5/月**
- リクエスト料金: **$0.60 / 100万リクエスト**

## 6. まとめ

| サービス | 役割 | データの通過 | 本番環境での採用 |
|---------|------|------------|----------------|
| **Route 53** | DNS 名前解決（ドメイン名 → ALB のアドレス変換） | しない（名前解決のみ） | ✅ カスタムドメイン + ACM 自動更新のため採用 |
| **AWS WAF** | ALB への不正リクエストのフィルタリング | ALB 内部で処理（独立した中継点ではない） | ✅ ブルートフォース対策・DDoS 対策のため採用 |

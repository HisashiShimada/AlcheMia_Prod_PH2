# Requirements Document

## Project Description (Input)
プロジェクト管理画面のプロジェクト一覧取得部分の実装したい。
仕様の部分についてはdocs/design/api/api_project_management.mdの2.1プロジェクト一覧取得を確認してください。

---

## 導入

本ドキュメントは、プロジェクト管理画面におけるプロジェクト一覧取得API（GET /api/v1/projects）のバックエンド実装要件を定義します。マルチテナント環境において、組織ごとに分離されたプロジェクトデータを安全かつ効率的に取得する機能を実現します。

アクセス制御は、**機能レベル（role_permissionテーブル）** と **データレベル（organization_id、プロジェクト所有権、タスク割り当て）** の2層で管理されます。プロジェクト完了ステータス（project_status = 4）のプロジェクトも取得対象ですが、初期表示時は非表示とします。

## Requirements

### 要件1: 認証・認可

**目的:** システム管理者として、認証されたユーザーのみがプロジェクト一覧にアクセスできるようにしたい。これにより、不正アクセスを防止し、データの安全性を確保する。

#### 受入基準

1. When APIリクエストを受信した場合、プロジェクト一覧APIはJWTトークンとセッションの両方を検証しなければならない
2. If Authorizationヘッダーが存在しない場合、プロジェクト一覧APIは401エラー（AUTH_TOKEN_INVALID）を返却しなければならない
3. If JWTトークンの有効期限が切れている場合、プロジェクト一覧APIは401エラー（AUTH_TOKEN_EXPIRED）を返却しなければならない
4. When ユーザーがManager権限を持つ場合、プロジェクト一覧APIは自組織のプロジェクト一覧を返却しなければならない
5. When ユーザーがSystem Admin権限を持つ場合、プロジェクト一覧APIは全組織のプロジェクト一覧を返却できなければならない
6. When ユーザーがWorker権限を持つ場合、プロジェクト一覧APIは割り当てられたプロジェクトのみを返却しなければならない
7. If ユーザーがWorker権限で割り当てられていないプロジェクトにアクセスしようとする場合、プロジェクト一覧APIは403エラー（PERMISSION_INSUFFICIENT）を返却しなければならない

---

### 要件2: マルチテナント分離

**目的:** 実験管理者として、自組織のプロジェクトのみが表示されることを保証したい。これにより、組織間のデータ漏洩を防止する。

#### 受入基準

1. プロジェクト一覧APIは、すべてのデータベースクエリにorganization_idフィルタを含めなければならない
2. When APIリクエストを受信した場合、プロジェクト一覧APIはX-Organization-IdヘッダーからorganizationIdを取得しなければならない
3. If X-Organization-Idヘッダーが存在しない場合、プロジェクト一覧APIは400エラー（VALIDATION_ERROR）を返却しなければならない
4. If X-Organization-IdがUUID形式でない場合、プロジェクト一覧APIは400エラー（VALIDATION_ERROR）を返却しなければならない
5. When データベースクエリを実行する場合、プロジェクト一覧APIはParameterized Queriesを使用しなければならない
6. When System Admin以外のユーザーがリクエストする場合、プロジェクト一覧APIはセッション情報のorganization_idとヘッダーのX-Organization-Idが一致することを確認しなければならない
7. プロジェクト一覧APIは、クロステナントアクセスを防止しなければならない

---

### 要件3: データ取得・フィルタリング

**目的:** 実験管理者として、プロジェクトの状態に応じてフィルタリングされた一覧を取得したい。これにより、必要なプロジェクトのみを効率的に閲覧できる。

#### 受入基準

1. When include_completed=false（デフォルト）の場合、プロジェクト一覧APIはproject_status=4（プロジェクト完了）のプロジェクトを除外しなければならない
2. When include_completed=trueの場合、プロジェクト一覧APIは完了プロジェクトを含めたすべてのプロジェクトを返却しなければならない
3. プロジェクト一覧APIは、projectテーブルから以下のフィールドを取得しなければならない: organizationId, projectId, projectName, description, departmentId, ownerUserId, projectStatus, projectMaimlFlg, checkoutStatus, createAt
4. When project_statusまたはcheckout_statusを取得する場合、プロジェクト一覧APIはcode_masterテーブルから対応する名称を取得しなければならない
5. プロジェクト一覧APIは、取得したデータをキャメルケースに変換してJSON形式で返却しなければならない
6. If データベース接続エラーが発生した場合、プロジェクト一覧APIは500エラー（SYSTEM_DATABASE_ERROR）を返却しなければならない

---

### 要件4: ページネーション

**目的:** 実験管理者として、大量のプロジェクトを効率的に閲覧したい。これにより、パフォーマンスを維持しながら必要な情報にアクセスできる。

#### 受入基準

1. プロジェクト一覧APIは、pageパラメータ（デフォルト: 1）とlimitパラメータ（デフォルト: 20）をサポートしなければならない
2. When pageパラメータが正の整数でない場合、プロジェクト一覧APIは400エラー（VALIDATION_ERROR）を返却しなければならない
3. When limitパラメータが1〜100の範囲外の場合、プロジェクト一覧APIは400エラー（VALIDATION_ERROR）を返却しなければならない
4. プロジェクト一覧APIは、レスポンスにpaginationオブジェクトを含めなければならない（page, limit, totalItems, totalPages, hasNext, hasPrev）
5. When 次のページが存在する場合、プロジェクト一覧APIはhasNext=trueを返却しなければならない
6. When 前のページが存在する場合、プロジェクト一覧APIはhasPrev=trueを返却しなければならない
7. プロジェクト一覧APIは、指定されたページ範囲のデータのみを返却しなければならない

---

### 要件5: ソート

**目的:** 実験管理者として、プロジェクトを任意の順序で表示したい。これにより、最新のプロジェクトや名前順でプロジェクトを確認できる。

#### 受入基準

1. プロジェクト一覧APIは、sort_byパラメータ（デフォルト: create_at）とorderパラメータ（デフォルト: desc）をサポートしなければならない
2. When sort_by=create_atの場合、プロジェクト一覧APIは作成日時順でソートしなければならない
3. When sort_by=project_nameの場合、プロジェクト一覧APIはプロジェクト名順でソートしなければならない
4. When order=descの場合、プロジェクト一覧APIは降順（新しい順・Z→A順）でソートしなければならない
5. When order=ascの場合、プロジェクト一覧APIは昇順（古い順・A→Z順）でソートしなければならない
6. If sort_byが許可されていない値（create_at, project_name以外）の場合、プロジェクト一覧APIは400エラー（VALIDATION_ERROR）を返却しなければならない
7. If orderが許可されていない値（desc, asc以外）の場合、プロジェクト一覧APIは400エラー（VALIDATION_ERROR）を返却しなければならない

---

### 要件6: レスポンス形式

**目的:** フロントエンド開発者として、統一されたレスポンス形式を受け取りたい。これにより、APIレスポンスの処理を標準化できる。

#### 受入基準

1. プロジェクト一覧APIは、成功時に以下の構造のJSONを返却しなければならない: {success: true, data: [...], pagination: {...}, meta: {...}}
2. プロジェクト一覧APIは、dataフィールドにプロジェクト配列を含めなければならない
3. プロジェクト一覧APIは、metaフィールドにtimestamp（ISO 8601形式）とrequestIdを含めなければならない
4. プロジェクト一覧APIは、日付・時刻をISO 8601形式（YYYY-MM-DDTHH:mm:ss.sssZ）で返却しなければならない
5. プロジェクト一覧APIは、成功時にHTTPステータスコード200を返却しなければならない
6. プロジェクト一覧APIは、Content-Typeヘッダーをapplication/jsonに設定しなければならない
7. When プロジェクトが1件も存在しない場合、プロジェクト一覧APIは空の配列を返却しなければならない（エラーにしない）

---

### 要件7: エラーハンドリング

**目的:** システム運用者として、エラーの原因を特定できる詳細な情報を取得したい。これにより、迅速な問題解決が可能になる。

#### 受入基準

1. If バリデーションエラーが発生した場合、プロジェクト一覧APIは400エラーとVALIDATION_ERRORコードを返却しなければならない
2. If 認証エラーが発生した場合、プロジェクト一覧APIは401エラーとAUTH_TOKEN_EXPIREDまたはAUTH_TOKEN_INVALIDコードを返却しなければならない
3. If 権限不足エラーが発生した場合、プロジェクト一覧APIは403エラーとPERMISSION_INSUFFICIENTコードを返却しなければならない
4. If データベースエラーが発生した場合、プロジェクト一覧APIは500エラーとSYSTEM_DATABASE_ERRORコードを返却しなければならない
5. プロジェクト一覧APIは、エラー時に以下の構造のJSONを返却しなければならない: {success: false, error: {code, message, details}, meta: {...}}
6. プロジェクト一覧APIは、エラーメッセージを日本語で返却しなければならない
7. プロジェクト一覧APIは、エラー詳細に機密情報（パスワード、トークン等）を含めてはならない
8. プロジェクト一覧APIは、すべてのエラーをログに記録しなければならない

---

### 要件8: パフォーマンス

**目的:** システム運用者として、応答時間を最適化したい。これにより、ユーザーエクスペリエンスを向上させる。

#### 受入基準

1. プロジェクト一覧APIは、通常時200ms以内でレスポンスを返却しなければならない
2. プロジェクト一覧APIは、最大でも500ms以内でレスポンスを返却しなければならない
3. プロジェクト一覧APIは、データベース接続にコネクションプールを使用しなければならない
4. プロジェクト一覧APIは、必要最小限のカラムのみをSELECTしなければならない
5. プロジェクト一覧APIは、organization_idとproject_statusにインデックスが存在することを前提としなければならない
6. プロジェクト一覧APIは、同時に100リクエスト/秒を処理できなければならない
7. Where キャッシング機能が有効な場合、プロジェクト一覧APIはプロジェクト一覧をTTL 5分でキャッシュしなければならない

---

### 要件9: セキュリティ

**目的:** セキュリティ担当者として、SQLインジェクションやその他の攻撃を防止したい。これにより、システムの安全性を確保する。

#### 受入基準

1. プロジェクト一覧APIは、すべてのDBクエリでParameterized Queriesを使用しなければならない
2. プロジェクト一覧APIは、ユーザー入力値をサニタイゼーションしなければならない
3. プロジェクト一覧APIは、文字列連結でSQLクエリを構築してはならない
4. プロジェクト一覧APIは、authミドルウェアを適用しなければならない
5. プロジェクト一覧APIは、tenantIsolationミドルウェアを適用しなければならない
6. プロジェクト一覧APIは、permissionCheckミドルウェアを適用しなければならない
7. プロジェクト一覧APIは、機密情報をログに出力してはならない
8. プロジェクト一覧APIは、レート制限（100リクエスト/分/ユーザー）を適用しなければならない

---

## テスト要件

### 受入テスト

1. **正常系テスト**
   - 認証済みManagerによるプロジェクト一覧取得が成功すること
   - System Adminによる全組織のプロジェクト取得が成功すること
   - 完了プロジェクトが初期表示で除外されていること
   - include_completed=trueで完了プロジェクトも取得できること
   - create_atの降順でソートされていること
   - ページネーションが正しく動作すること

2. **異常系テスト**
   - 未認証ユーザーによるアクセスで401エラーが返却されること
   - 権限不足ユーザーによるアクセスで403エラーが返却されること
   - 他組織のデータへのアクセスで403エラーが返却されること
   - 不正なorganization_idで400エラーが返却されること
   - 不正なページ番号で400エラーが返却されること
   - limitが範囲外で400エラーが返却されること

3. **パフォーマンステスト**
   - レスポンスタイムが200ms以内であること
   - 100リクエスト/秒の同時処理が可能であること

4. **セキュリティテスト**
   - SQLインジェクション攻撃が防止されていること
   - クロステナントアクセスが防止されていること
   - レート制限が正しく動作すること

---

## 非機能要件

### 可用性
- プロジェクト一覧APIは、99.9%以上の稼働率を維持しなければならない

### 拡張性
- プロジェクト一覧APIは、プロジェクト数が10,000件まで増加しても性能劣化しないこと

### 保守性
- プロジェクト一覧APIは、統一されたエラーハンドリングパターンを使用すること
- プロジェクト一覧APIは、ログ記録を標準化すること

### 互換性
- プロジェクト一覧APIは、HTTP/1.1およびHTTP/2をサポートすること
- プロジェクト一覧APIは、主要なブラウザ（Chrome, Firefox, Safari, Edge）と互換性を持つこと

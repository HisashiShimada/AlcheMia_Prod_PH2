# Requirements Document

## Project Description (Input)
プロジェクト詳細取得API実装

---

## 導入

本ドキュメントは、プロジェクト管理画面におけるプロジェクト詳細取得API（GET /api/v1/projects/:projectId）のバックエンド実装要件を定義します。マルチテナント環境において、特定プロジェクトの包括的な情報（基本情報、S3ファイル一覧、タスク一覧）を安全かつ効率的に取得する機能を実現します。

アクセス制御は、**機能レベル（role_permissionテーブル）** と **データレベル（organization_id、プロジェクト所有権、タスク割り当て）** の2層で管理されます。並列データ取得により200ms以内のレスポンスタイムを目標とします。

## Requirements

### 要件1: 認証・認可

**目的:** システム管理者として、認証されたユーザーのみがプロジェクト詳細にアクセスできるようにしたい。これにより、不正アクセスを防止し、データの安全性を確保する。

#### 受入基準

1. When APIリクエストを受信した場合、プロジェクト詳細APIはJWTトークンとセッションの両方を検証しなければならない
2. If Authorizationヘッダーが存在しない場合、プロジェクト詳細APIは401エラー（AUTH_TOKEN_INVALID）を返却しなければならない
3. If JWTトークンの有効期限が切れている場合、プロジェクト詳細APIは401エラー（AUTH_TOKEN_EXPIRED）を返却しなければならない
4. When ユーザーがManager権限を持つ場合、プロジェクト詳細APIは自組織のプロジェクト詳細を返却しなければならない
5. When ユーザーがSystem Admin権限を持つ場合、プロジェクト詳細APIは全組織のプロジェクト詳細を返却できなければならない
6. When ユーザーがWorker権限を持つ場合、プロジェクト詳細APIは割り当てられたプロジェクトのみの詳細を返却しなければならない
7. If ユーザーがWorker権限で割り当てられていないプロジェクトにアクセスしようとする場合、プロジェクト詳細APIは403エラー（PERMISSION_INSUFFICIENT）を返却しなければならない

---

### 要件2: マルチテナント分離

**目的:** 実験管理者として、自組織のプロジェクトのみが表示されることを保証したい。これにより、組織間のデータ漏洩を防止する。

#### 受入基準

1. プロジェクト詳細APIは、すべてのデータベースクエリにorganization_idフィルタを含めなければならない
2. When APIリクエストを受信した場合、プロジェクト詳細APIはX-Organization-IdヘッダーからorganizationIdを取得しなければならない
3. If X-Organization-Idヘッダーが存在しない場合、プロジェクト詳細APIは400エラー（VALIDATION_ERROR）を返却しなければならない
4. If X-Organization-IdがUUID形式でない場合、プロジェクト詳細APIは400エラー（VALIDATION_ERROR）を返却しなければならない
5. When データベースクエリを実行する場合、プロジェクト詳細APIはParameterized Queriesを使用しなければならない
6. When System Admin以外のユーザーがリクエストする場合、プロジェクト詳細APIはセッション情報のorganization_idとヘッダーのX-Organization-Idが一致することを確認しなければならない
7. プロジェクト詳細APIは、クロステナントアクセスを防止しなければならない

---

### 要件3: プロジェクト基本情報の取得

**目的:** 実験管理者として、プロジェクトの基本情報を包括的に取得したい。これにより、プロジェクトの現在の状態を即座に把握できる。

#### 受入基準

1. When projectIdパラメータを受信した場合、プロジェクト詳細APIはUUID形式であることを検証しなければならない
2. If projectIdがUUID形式でない場合、プロジェクト詳細APIは400エラー（VALIDATION_INVALID_UUID）を返却しなければならない
3. プロジェクト詳細APIは、projectテーブルから以下のフィールドを取得しなければならない: organizationId, projectId, projectName, description, departmentId, ownerUserId, projectStatus, checkoutStatus, createAt
4. When プロジェクト情報を取得する場合、プロジェクト詳細APIはorganization_userテーブルと結合して所有者名（ownerUserName）を取得しなければならない
5. When project_statusまたはcheckout_statusを取得する場合、プロジェクト詳細APIはcode_masterテーブルから対応する名称を取得しなければならない
6. If 指定されたprojectIdが存在しない場合、プロジェクト詳細APIは404エラー（RESOURCE_NOT_FOUND）を返却しなければならない
7. プロジェクト詳細APIは、取得したデータをキャメルケースに変換してJSON形式で返却しなければならない

---

### 要件4: S3ファイル一覧の取得

**目的:** 実験管理者として、プロジェクトに関連するすべてのファイル（MAIMLファイル、アーカイブファイル）を確認したい。これにより、プロジェクトの履歴と現在の状態を把握できる。

#### 受入基準

1. When S3ファイル一覧を取得する場合、プロジェクト詳細APIは`org_{organization_prefix}/projects/{project_name}/`配下のすべてのファイルをリストしなければならない
2. プロジェクト詳細APIは、`archive/`サブフォルダ内のファイルも含めなければならない
3. When 各ファイル情報を返却する場合、プロジェクト詳細APIはfileName, filePath, fileSize, lastModifiedを含めなければならない
4. When アーカイブファイルを返却する場合、プロジェクト詳細APIはファイル名からバージョン番号（version）を抽出しなければならない
5. When ファイル情報を返却する場合、プロジェクト詳細APIは各ファイルの署名付きURL（signedUrl）を生成しなければならない
6. When 署名付きURLを生成する場合、プロジェクト詳細APIは有効期限を1時間（3600秒）に設定しなければならない
7. If S3フォルダが空である場合、プロジェクト詳細APIは空のファイル配列を返却しなければならない（エラーにしない）
8. If S3アクセスエラーが発生した場合、プロジェクト詳細APIは警告をログに記録し、空のファイル配列を返却しなければならない（500エラーにしない）

---

### 要件5: タスク一覧の取得

**目的:** 実験管理者として、プロジェクトに関連するすべてのタスクの進捗状況を確認したい。これにより、プロジェクト全体の進行状況を把握できる。

#### 受入基準

1. When タスク一覧を取得する場合、プロジェクト詳細APIはproject_task_detailテーブルにレコードが存在するか確認しなければならない
2. If タスクが存在しない場合、プロジェクト詳細APIは空のタスク配列を返却しなければならない（タスク詳細クエリをスキップする）
3. When タスクが存在する場合、プロジェクト詳細APIはorganization_idとproject_idでフィルタリングしてタスク詳細を取得しなければならない
4. When タスク一覧を返却する場合、プロジェクト詳細APIはタスクをtask_no順にソートしなければならない
5. When 各タスク情報を返却する場合、プロジェクト詳細APIはmethodId, taskNo, taskStatus, taskStatusName, workerUserId, workerUserName, reviewerUserId, reviewerUserNameを含めなければならない
6. When タスクステータス名称を返却する場合、プロジェクト詳細APIはcode_masterテーブルから対応する名称を取得しなければならない
7. When タスク情報を取得する場合、プロジェクト詳細APIはorganization_userテーブルとJOINしてユーザー名を取得しなければならない

---

### 要件6: サマリー情報の生成

**目的:** 実験管理者として、プロジェクトの概要を数値で把握したい。これにより、プロジェクトの規模と進捗を即座に理解できる。

#### 受入基準

1. When レスポンスを生成する場合、プロジェクト詳細APIは総ファイル数（totalFiles）を集計しなければならない
2. When レスポンスを生成する場合、プロジェクト詳細APIは総タスク数（totalTasks）を集計しなければならない
3. When レスポンスを生成する場合、プロジェクト詳細APIは完了タスク数（completedTasks: task_status = 3）を集計しなければならない
4. When レスポンスを生成する場合、プロジェクト詳細APIは実行中タスク数（runningTasks: task_status = 1）を集計しなければならない
5. When レスポンスを生成する場合、プロジェクト詳細APIは実行待ちタスク数（waitingTasks: task_status = 0）を集計しなければならない
6. If タスクが未作成である場合、プロジェクト詳細APIはすべてのタスク関連カウントを0に設定しなければならない
7. プロジェクト詳細APIは、サマリー情報をメモリ内で計算しなければならない（追加のDBクエリを実行しない）

---

### 要件7: レスポンス形式

**目的:** フロントエンド開発者として、統一されたレスポンス形式を受け取りたい。これにより、APIレスポンスの処理を標準化できる。

#### 受入基準

1. プロジェクト詳細APIは、成功時に以下の構造のJSONを返却しなければならない: {success: true, data: {project, files, tasks, summary}, meta: {...}}
2. プロジェクト詳細APIは、dataフィールドにproject（オブジェクト）、files（配列）、tasks（配列）、summary（オブジェクト）を含めなければならない
3. プロジェクト詳細APIは、metaフィールドにtimestamp（ISO 8601形式）とrequestIdを含めなければならない
4. プロジェクト詳細APIは、日付・時刻をISO 8601形式（YYYY-MM-DDTHH:mm:ss.sssZ）で返却しなければならない
5. プロジェクト詳細APIは、成功時にHTTPステータスコード200を返却しなければならない
6. プロジェクト詳細APIは、Content-Typeヘッダーをapplication/jsonに設定しなければならない
7. プロジェクト詳細APIは、すべてのフィールド名をキャメルケース形式に変換しなければならない

---

### 要件8: エラーハンドリング

**目的:** システム運用者として、エラーの原因を特定できる詳細な情報を取得したい。これにより、迅速な問題解決が可能になる。

#### 受入基準

1. If projectIdがUUID形式でない場合、プロジェクト詳細APIは400エラー（VALIDATION_INVALID_UUID）を返却しなければならない
2. If 指定されたprojectIdが存在しない場合、プロジェクト詳細APIは404エラー（RESOURCE_NOT_FOUND）を返却しなければならない
3. If 認証エラーが発生した場合、プロジェクト詳細APIは401エラー（AUTH_TOKEN_EXPIREDまたはAUTH_TOKEN_INVALID）を返却しなければならない
4. If 権限不足エラーが発生した場合、プロジェクト詳細APIは403エラー（PERMISSION_INSUFFICIENT）を返却しなければならない
5. If データベースエラーが発生した場合、プロジェクト詳細APIは500エラー（SYSTEM_DATABASE_ERROR）を返却しなければならない
6. プロジェクト詳細APIは、エラー時に以下の構造のJSONを返却しなければならない: {success: false, error: {code, message, details}, meta: {...}}
7. プロジェクト詳細APIは、エラーメッセージを日本語で返却しなければならない
8. プロジェクト詳細APIは、エラー詳細に機密情報（パスワード、トークン等）を含めてはならない
9. プロジェクト詳細APIは、すべてのエラーをログに記録しなければならない

---

### 要件9: パフォーマンス

**目的:** システム運用者として、応答時間を最適化したい。これにより、ユーザーエクスペリエンスを向上させる。

#### 受入基準

1. プロジェクト詳細APIは、通常時200ms以内でレスポンスを返却しなければならない
2. プロジェクト詳細APIは、最大でも500ms以内でレスポンスを返却しなければならない
3. When プロジェクト基本情報、S3ファイル一覧、タスク存在チェックを実行する場合、プロジェクト詳細APIはPromise.allで並列実行しなければならない
4. When タスクが存在する場合のみ、プロジェクト詳細APIはタスク詳細クエリを実行しなければならない（条件付き最適化）
5. プロジェクト詳細APIは、データベース接続にコネクションプールを使用しなければならない
6. プロジェクト詳細APIは、必要最小限のカラムのみをSELECTしなければならない
7. Where キャッシング機能が有効な場合、プロジェクト詳細APIはプロジェクト基本情報をTTL 3分でキャッシュしなければならない

---

### 要件10: セキュリティ

**目的:** セキュリティ担当者として、SQLインジェクションやその他の攻撃を防止したい。これにより、システムの安全性を確保する。

#### 受入基準

1. プロジェクト詳細APIは、すべてのDBクエリでParameterized Queriesを使用しなければならない
2. プロジェクト詳細APIは、ユーザー入力値をサニタイゼーションしなければならない
3. プロジェクト詳細APIは、文字列連結でSQLクエリを構築してはならない
4. プロジェクト詳細APIは、authミドルウェアを適用しなければならない
5. プロジェクト詳細APIは、tenantIsolationミドルウェアを適用しなければならない
6. プロジェクト詳細APIは、permissionCheckミドルウェアを適用しなければならない
7. プロジェクト詳細APIは、機密情報をログに出力してはならない
8. プロジェクト詳細APIは、レート制限（100リクエスト/分/ユーザー）を適用しなければならない
9. When S3署名付きURLを生成する場合、プロジェクト詳細APIは有効期限を1時間に制限しなければならない

## テスト要件

### 受入テスト

1. **正常系テスト**
   - 認証済みManagerによるプロジェクト詳細取得が成功すること
   - System Adminによる全組織のプロジェクト詳細取得が成功すること
   - プロジェクト基本情報、ファイル一覧、タスク一覧、サマリーが正しく返却されること
   - タスクが未作成のプロジェクトでも正常にレスポンスが返却されること
   - S3ファイル一覧に現在のMAIMLファイルとアーカイブファイルが含まれること
   - 署名付きURLが生成され、有効期限が1時間に設定されていること

2. **異常系テスト**
   - 未認証ユーザーによるアクセスで401エラーが返却されること
   - 権限不足ユーザーによるアクセスで403エラーが返却されること
   - 他組織のプロジェクトへのアクセスで403エラーが返却されること
   - 存在しないprojectIdで404エラーが返却されること
   - 不正なUUID形式のprojectIdで400エラーが返却されること
   - 不正なorganization_idで400エラーが返却されること

3. **パフォーマンステスト**
   - レスポンスタイムが200ms以内であること
   - 並列データ取得により50-70%の時間短縮が実現されていること
   - タスク存在チェック後、条件付きでタスク詳細取得が実行されること

4. **セキュリティテスト**
   - SQLインジェクション攻撃が防止されていること
   - クロステナントアクセスが防止されていること
   - レート制限が正しく動作すること
   - S3署名付きURLが1時間で期限切れになること

---

## 非機能要件

### 可用性
- プロジェクト詳細APIは、99.9%以上の稼働率を維持しなければならない

### 拡張性
- プロジェクト詳細APIは、ファイル数が1,000件まで増加しても性能劣化しないこと
- プロジェクト詳細APIは、タスク数が100件まで増加しても性能劣化しないこと

### 保守性
- プロジェクト詳細APIは、統一されたエラーハンドリングパターンを使用すること
- プロジェクト詳細APIは、ログ記録を標準化すること
- プロジェクト詳細APIは、既存のプロジェクト一覧APIと同じコーディングスタイルを維持すること

### 互換性
- プロジェクト詳細APIは、HTTP/1.1およびHTTP/2をサポートすること
- プロジェクト詳細APIは、主要なブラウザ（Chrome, Firefox, Safari, Edge）と互換性を持つこと

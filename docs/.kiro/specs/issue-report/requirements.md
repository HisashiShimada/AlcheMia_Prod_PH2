# Requirements Document

## Project Description (Input)
実験作業者画面の問題報告を行うバックエンドの機能を実装する。

仕様の部分については
'docs\design\api\api_issue_management.md' (see below for file content) 
の1. 問題報告APIを確認してください。

## Introduction
本要件定義書は、実験作業者が実験中に遭遇する問題を報告するためのバックエンド機能の要件を定義します。問題管理システムは、プロジェクト、タスク、トランジション単位で問題を記録し、迅速な問題対応の基盤を提供します。

## Requirements

### Requirement 1: 問題報告機能
**Objective:** 実験作業者として、実験中に発生した問題を記録できるようにすることで、問題の可視化と迅速な対応を実現する

#### Acceptance Criteria
1. When 実験作業者が問題報告を送信した場合、問題管理システムは問題をデータベースに登録し、一意のIDを発行すること
2. When 問題報告時に対象種別がプロジェクトの場合、問題管理システムは指定されたプロジェクトに問題を紐付けること
3. When 問題報告時に対象種別がタスクの場合、問題管理システムは指定されたメソッドID、タスク連番のタスクに問題を紐付けること
4. When 問題報告時に対象種別がトランジションの場合、問題管理システムはトランジションを問題に紐付けること
5. When 問題が登録される場合、問題管理システムは報告者のユーザーID、報告日時を自動的に記録すること
6. When 問題が登録される場合、問題管理システムはステータスを「未解決」として初期化すること
7. The 問題管理システムは問題タイトルを1-200文字の範囲で受け付けること
8. The 問題管理システムは問題詳細を1-2000文字の範囲で受け付けること
9. The 問題管理システムは問題種別として以下を受け付けること: material_shortage（材料不足）、equipment_failure（機器故障）、procedure_unclear（手順不明）、safety_concern（安全懸念）、quality_issue（品質問題）、time_constraint（時間制約）、other（その他）

### Requirement 2: セキュリティとマルチテナント分離
**Objective:** システム管理者として、セキュアで分離されたデータアクセスを保証することで、組織間のデータ漏洩を防ぐ

#### Acceptance Criteria
1. The 問題管理システムはすべてのAPIエンドポイントでJWT認証を必須とすること
2. The 問題管理システムはすべてのAPIエンドポイントでテナント分離を適用すること
3. The 問題管理システムはすべてのデータベースクエリでorganization_idフィルタを必須とすること
4. When 問題を登録する場合、問題管理システムは現在のユーザーの組織IDを自動的に設定すること
5. When データを取得する場合、問題管理システムは現在のユーザーの組織に属するデータのみを返すこと
6. If 他組織のデータへのアクセスが試みられた場合、問題管理システムは404エラーを返すこと（存在情報の漏洩防止）
7. The 問題管理システムはすべてのSQLクエリでParameterized Queriesを使用すること
8. The 問題管理システムはユーザー入力をサニタイズしてXSS攻撃を防ぐこと

### Requirement 3: データ検証とエラーハンドリング
**Objective:** システムとして、不正なデータを拒否し明確なエラーメッセージを提供することで、データ整合性とユーザビリティを確保する

#### Acceptance Criteria
1. If プロジェクトIDがUUID形式でない場合、問題管理システムは400エラーを返すこと
2. If 必須パラメータが欠落している場合、問題管理システムは400エラーと欠落フィールド情報を返すこと
3. If 文字列長が制限を超える場合、問題管理システムは400エラーと制限値情報を返すこと
4. If 問題種別が許可された値でない場合、問題管理システムは400エラーと許可値リストを返すこと
5. If targetTypeが「task」または「transition」でtaskNoが欠落している場合、問題管理システムは400エラーを返すこと
6. If targetTypeが「transition」でtransitionIdが欠落している場合、問題管理システムは400エラーを返すこと
7. If 指定されたプロジェクトIDが存在しない場合、問題管理システムは404エラーを返すこと
8. If 指定されたメソッドIDが存在しない場合、問題管理システムは404エラーを返すこと
9. If 指定されたタスク番号が存在しない場合、問題管理システムは404エラーを返すこと
10. When エラーが発生した場合、問題管理システムは統一されたエラーレスポンス形式（success、error、meta）を返すこと
11. When エラーが発生した場合、問題管理システムはエラーログを記録すること（Winston構造化ログ）

### Requirement 4: 権限管理
**Objective:** システムとして、ロールに応じた適切なアクセス制御を実施することで、権限の不正利用を防ぐ

#### Acceptance Criteria
1. The 問題管理システムは問題報告APIをWorker以上のロールに許可すること
2. If 権限が不足している場合、問題管理システムは403エラーを返すこと

### Requirement 5: パフォーマンスとスケーラビリティ
**Objective:** システムとして、効率的なデータアクセスと高速なレスポンスを提供することで、快適なユーザー体験を実現する

#### Acceptance Criteria
1. The 問題管理システムはissuesテーブルに (organization_id, project_id, status) の複合インデックスを持つこと
2. The 問題管理システムはissuesテーブルに (organization_id, created_at) のインデックスを持つこと
3. When 複数テーブルを結合する場合、問題管理システムは適切なJOIN戦略を使用すること

### Requirement 6: APIレスポンス形式
**Objective:** システムとして、統一されたレスポンス形式を提供することで、フロントエンド開発の一貫性を確保する

#### Acceptance Criteria
1. When APIが成功した場合、問題管理システムは success: true を含むJSONレスポンスを返すこと
2. When APIが成功した場合、問題管理システムは data フィールドに登録された問題情報を含めること
3. When APIが失敗した場合、問題管理システムは success: false を含むJSONレスポンスを返すこと
4. When APIが失敗した場合、問題管理システムは error フィールドに code、message、details を含めること
5. The 問題管理システムはすべてのレスポンスに meta フィールド（timestamp、requestId）を含めること
6. The 問題管理システムは成功時のHTTPステータスコードとして201（Created）を返すこと
7. The 問題管理システムはエラー時のHTTPステータスコードとして、バリデーションエラーは400、認証エラーは401、権限エラーは403、リソース不存在は404を返すこと

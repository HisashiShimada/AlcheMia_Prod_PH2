# 要件定義書: トランジションステータス更新

## プロジェクト概要（Input）

実験作業者画面のトランジションステータス更新を行うバックエンドの機能を実装する。

仕様の詳細については以下のドキュメントを参照：
`docs/design/api/api_experiment_data.md` の「2. トランジションステータス更新API」

---

## 要件定義（Requirements）

### 要件1: トランジションステータス更新

**目的:** 実験作業者として、トランジションのステータスを手動で更新したい。その結果、実験の進捗状況を正確に記録できる。

#### 受入基準

1. When 有効なプロジェクトID、メソッドID、トランジションIDを指定してステータス更新APIを呼び出す場合、the トランジションステータス更新APIは指定されたトランジションのステータスを更新すること
2. When ステータス更新リクエストを受信する場合、the トランジションステータス更新APIはタスク連番、ステータス、進捗率、コメントを受け付けること
3. The トランジションステータス更新APIは認証済みユーザーのみがアクセス可能であること
4. The トランジションステータス更新APIは`worker`、`manager`、`admin`ロールのユーザーのみが実行可能であること
5. When ステータス更新が成功した場合、the トランジションステータス更新APIは更新後のトランジション情報を返却すること

### 要件2: ステータス値の管理

**目的:** 実験管理者として、標準化されたステータス値で実験進捗を管理したい。その結果、一貫性のある進捗追跡ができる。

#### 受入基準

1. The トランジションステータス更新APIは以下のステータス値のみを受け付けること: `initial`, `preparing`, `ready`, `running`, `paused`, `completed`, `error`
2. If 許可されていないステータス値が指定された場合、then the トランジションステータス更新APIは400エラー（バリデーションエラー）を返却すること
3. The トランジションステータス更新APIはステータス値の大文字小文字を区別すること
4. When ステータスが更新される場合、the トランジションステータス更新APIは更新日時と更新者情報を記録すること

### 要件3: 進捗率の自動制御

**目的:** データ管理者として、ステータスと進捗率の整合性を保証したい。その結果、誤ったデータ登録を防止できる。

#### 受入基準

1. When ステータスが`completed`に設定される場合、the トランジションステータス更新APIは進捗率を自動的に100に設定すること
2. When 進捗率が指定されている場合、the トランジションステータス更新APIは0から100の範囲内であることを検証すること
3. If 進捗率が0未満または100を超える場合、then the トランジションステータス更新APIは400エラーを返却すること
4. When 進捗率が指定されていない場合、the トランジションステータス更新APIは現在の値を維持すること
5. The トランジションステータス更新APIは進捗率を整数値として扱うこと

### 要件4: コメント機能

**目的:** 実験作業者として、ステータス更新時にコメントを記録したい。その結果、変更理由や補足情報を残すことができる。

#### 受入基準

1. The トランジションステータス更新APIはオプショナルでコメントを受け付けること
2. When コメントが指定されている場合、the トランジションステータス更新APIは2000文字以内であることを検証すること
3. If コメントが2000文字を超える場合、then the トランジションステータス更新APIは400エラーを返却すること
4. The トランジションステータス更新APIはコメントをそのまま保存すること（サニタイゼーション後）

### 要件5: プロジェクトステータス検証

**目的:** システム管理者として、編集可能なプロジェクトのみステータス更新できるようにしたい。その結果、完了済みやアーカイブ済みプロジェクトの変更を防止できる。

#### 受入基準

1. The トランジションステータス更新APIはステータス更新前にプロジェクトステータスを確認すること
2. While プロジェクトステータスが`draft`、`active`、`waiting_approval`のいずれかである場合、the トランジションステータス更新APIはステータス更新を許可すること
3. If プロジェクトステータスが`archived`または`completed`の場合、then the トランジションステータス更新APIは403エラー（権限不足）を返却すること
4. The トランジションステータス更新APIはプロジェクトステータス確認時にorganization_idフィルタを適用すること

### 要件6: トランジション存在確認

**目的:** データ管理者として、存在するトランジションのみ更新できるようにしたい。その結果、データ整合性を保証できる。

#### 受入基準

1. The トランジションステータス更新APIはステータス更新前にトランジションの存在を確認すること
2. The トランジションステータス更新APIはトランジションが指定されたプロジェクト、メソッド、タスク連番に属することを検証すること
3. If 指定されたトランジションが存在しない場合、then the トランジションステータス更新APIは404エラー（リソースが見つからない）を返却すること
4. The トランジションステータス更新APIはトランジション確認時にorganization_idフィルタを適用すること

### 要件7: タスク進捗率の再計算

**目的:** 実験管理者として、トランジション更新時にタスク全体の進捗率を自動更新したい。その結果、タスクレベルの進捗を常に最新に保てる。

#### 受入基準

1. When トランジションステータスが更新される場合、the トランジションステータス更新APIはタスク内の全トランジションの進捗率から平均を計算すること
2. The トランジションステータス更新APIは計算されたタスク進捗率でproject_taskテーブルを更新すること
3. The トランジションステータス更新APIはタスク進捗率の計算時に同一タスクに属するトランジションのみを対象とすること
4. The トランジションステータス更新APIはタスク進捗率を小数第1位まで計算すること

### 要件8: マルチテナント分離

**目的:** システム管理者として、組織間のデータ分離を確保したい。その結果、セキュリティとプライバシーを保護できる。

#### 受入基準

1. The トランジションステータス更新APIはすべてのデータベースクエリにorganization_idフィルタを適用すること
2. The トランジションステータス更新APIは認証済みユーザーの所属組織のトランジションのみを更新可能とすること
3. If ユーザーが他組織のプロジェクトIDを指定した場合、then the トランジションステータス更新APIは404エラー（リソースが見つからない）を返却すること
4. The トランジションステータス更新APIはレスポンスに他組織の情報を含まないこと

### 要件9: 認証と認可

**目的:** セキュリティ管理者として、適切な権限を持つユーザーのみがAPIにアクセスできるようにしたい。その結果、不正アクセスを防止できる。

#### 受入基準

1. If 認証トークンが提供されていない場合、then the トランジションステータス更新APIは401エラー（認証エラー）を返却すること
2. If 認証トークンが無効または期限切れの場合、then the トランジションステータス更新APIは401エラーを返却すること
3. If ユーザーが必要な権限（worker、manager、admin）を持っていない場合、then the トランジションステータス更新APIは403エラー（権限不足）を返却すること
4. The トランジションステータス更新APIはAuthorizationヘッダーからJWTトークンを取得して検証すること

### 要件10: バリデーション

**目的:** 開発者として、不正なリクエストを適切に処理したい。その結果、システムの安定性とユーザー体験を向上できる。

#### 受入基準

1. If プロジェクトID（projectId）がUUID形式でない場合、then the トランジションステータス更新APIは400エラー（バリデーションエラー）を返却すること
2. If タスク連番（taskNo）が1未満の整数の場合、then the トランジションステータス更新APIは400エラーを返却すること
3. If ステータスが未指定の場合、then the トランジションステータス更新APIは400エラーを返却すること
4. If メソッドIDまたはトランジションIDが空文字列の場合、then the トランジションステータス更新APIは400エラーを返却すること
5. The トランジションステータス更新APIはすべてのバリデーションエラーに対して詳細なエラー情報を返却すること

### 要件11: エラーハンドリング

**目的:** 開発者として、エラー時に適切な情報を提供したい。その結果、問題の診断と解決を容易にできる。

#### 受入基準

1. If データベース接続エラーが発生した場合、then the トランジションステータス更新APIは500エラー（システムエラー）を返却すること
2. If トランザクション中にエラーが発生した場合、then the トランジションステータス更新APIはすべての変更をロールバックすること
3. The トランジションステータス更新APIはすべてのエラーレスポンスにerror code、message、detailsを含むこと
4. The トランジションステータス更新APIはすべてのレスポンスにmeta情報（timestamp、requestId）を含むこと
5. The トランジションステータス更新APIはエラーメッセージに機密情報を含まないこと

### 要件12: レスポンス形式

**目的:** フロントエンド開発者として、統一されたレスポンス形式で情報を受け取りたい。その結果、一貫性のあるクライアント実装ができる。

#### 受入基準

1. The トランジションステータス更新APIは成功時にsuccessフィールドをtrueに設定して返却すること
2. The トランジションステータス更新APIは成功時にdataフィールドに更新後のトランジション情報を含めて返却すること
3. The トランジションステータス更新APIはエラー時にsuccessフィールドをfalseに設定して返却すること
4. The トランジションステータス更新APIはエラー時にerrorフィールドにエラー情報を含めて返却すること
5. The トランジションステータス更新APIはすべてのレスポンスにmetaフィールド（timestamp、requestId）を含めること
6. The トランジションステータス更新APIは日時フィールドをISO 8601形式（YYYY-MM-DDTHH:mm:ss.sssZ）で返却すること

### 要件13: トランザクション管理

**目的:** データ管理者として、データの整合性を保証したい。その結果、部分的な更新によるデータ不整合を防止できる。

#### 受入基準

1. The トランジションステータス更新APIはトランジションステータス更新とタスク進捗率更新を1トランザクションで実行すること
2. If いずれかの更新が失敗した場合、then the トランジションステータス更新APIはすべての変更をロールバックすること
3. The トランジションステータス更新APIはトランザクション中に適切なロックを取得すること
4. The トランジションステータス更新APIはトランザクション完了後に明示的にコミットすること

### 要件14: パフォーマンス

**目的:** システム管理者として、APIが適切なパフォーマンスで動作することを確保したい。その結果、ユーザー体験を向上できる。

#### 受入基準

1. The トランジションステータス更新APIは通常のリクエストに対して1秒以内にレスポンスを返却すること
2. The トランジションステータス更新APIは効率的なデータベースクエリを使用してN+1問題を回避すること
3. The トランジションステータス更新APIはtransition_dataテーブルに適切なインデックスが設定されていることを前提とすること
4. The トランジションステータス更新APIは不要なデータ取得を避け、必要な情報のみをクエリすること

### 要件15: データ整合性

**目的:** データ管理者として、返却されるデータの整合性を保証したい。その結果、信頼性の高い情報を提供できる。

#### 受入基準

1. The トランジションステータス更新APIは更新者情報（updated_by）を現在のユーザーIDで記録すること
2. The トランジションステータス更新APIは更新日時（updated_at）を現在のシステム時刻で記録すること
3. When 複数のトランジションが同時に更新される場合、the トランジションステータス更新APIは正しい順序で処理すること
4. The トランジションステータス更新APIはタイムスタンプをUTC形式で記録すること

### 要件16: 監査ログ

**目的:** セキュリティ管理者として、すべてのステータス変更を追跡したい。その結果、監査とトラブルシューティングができる。

#### 受入基準

1. When トランジションステータスが更新される場合、the トランジションステータス更新APIは変更履歴をログに記録すること
2. The トランジションステータス更新APIはログに以下の情報を含めること: ユーザーID、組織ID、プロジェクトID、トランジションID、変更前ステータス、変更後ステータス、タイムスタンプ
3. The トランジションステータス更新APIはログを構造化形式（JSON）で出力すること
4. The トランジションステータス更新APIは重要な操作に対してINFOレベルのログを出力すること

### 要件17: イベントログ記録

**目的:** データ管理者として、すべてのトランジションステータス変更をデータベースに永続化したい。その結果、監査証跡と履歴分析ができる。

#### 受入基準

1. When トランジションステータスが更新される場合、the トランジションステータス更新APIはmaiml_event_logテーブルに変更履歴を記録すること
2. The トランジションステータス更新APIは組織ID、プロジェクトIDをリクエストデータから取得してイベントログに記録すること
3. The トランジションステータス更新APIはシーケンス番号をorganization_idとproject_idの組み合わせごとに自動採番すること
4. The トランジションステータス更新APIはAPIリクエストデータをJSON形式でlogカラムに格納すること
5. The トランジションステータス更新APIはイベントログにevent_type（'transition_status_update'）、method_id、task_no、transition_id、status、progress_rate、comment、updated_by、timestampを含めること
6. The トランジションステータス更新APIはトランジションステータス更新とイベントログ記録を1トランザクションで実行すること
7. If イベントログ記録が失敗した場合、then the トランジションステータス更新APIはトランジションステータス更新もロールバックすること

## 非機能要件

### セキュリティ
- すべてのデータベースクエリにorganization_idフィルタを適用
- Parameterized Queriesを使用してSQLインジェクションを防止
- 認証トークンの検証を実装
- ロールベースアクセス制御（RBAC）を実装
- 入力データのサニタイゼーション（XSS対策）

### 可用性
- データベース接続エラー時の適切なエラーハンドリング
- トランザクション失敗時のロールバック保証
- エラーログの記録とモニタリング

### 保守性
- 統一されたエラーハンドリングパターンの使用
- 適切なログ出力（情報、警告、エラー）
- コードコメントとドキュメンテーション
- 明確なエラーメッセージ

### パフォーマンス
- データベースインデックスの最適化
- 効率的なクエリ設計（N+1問題の回避）
- 適切なトランザクション管理
- 不要なデータ取得の回避

## 受入条件

このAPIが完成したと判断するための条件：

1. ✅ すべての受入基準がテストで検証されている
2. ✅ マルチテナント分離が正しく実装されている
3. ✅ 認証と認可が適切に機能している
4. ✅ プロジェクトステータス検証が正しく動作している
5. ✅ トランザクション管理が正しく実装されている
6. ✅ エラーハンドリングがすべてのケースで適切に動作している
7. ✅ レスポンス形式が統一された形式に準拠している
8. ✅ パフォーマンステストで基準を満たしている
9. ✅ セキュリティチェックリストがすべてクリアされている
10. ✅ 監査ログが適切に記録されている

## 実装時の技術的考慮事項

### データベーステーブル
- **transition_data**: ステータス、進捗率、コメントを保存
- **maiml_event_log**: イベントログ（変更履歴）を保存
  - organization_id: 組織ID
  - project_id: プロジェクトID
  - sequence_no: シーケンス番号（自動採番、organization_id + project_id単位で連番）
  - log: JSONB形式のログデータ（event_type、method_id、task_no、transition_id、status、progress_rate、comment、updated_by、timestamp）
  - created_at: 作成日時
- **projects**: プロジェクトステータス確認用
- **project_task**: タスク存在確認、進捗率更新用

### インデックス要件
- `transition_data (organization_id, project_id, method_id, task_no, transition_id)` - 複合主キー
- `transition_data (organization_id, project_id, updated_at)` - 検索・ソート用

### トランザクション設計
1. プロジェクトステータス確認
2. タスク・トランジション存在確認
3. トランジションステータス更新
4. イベントログ記録（maiml_event_logテーブル）
   - シーケンス番号の自動採番
   - APIデータのJSON形式での格納
5. タスク進捗率再計算・更新
6. コミット（エラー時はロールバック）

## 1. プロジェクト概要

### 背景

mmdpfプロジェクト（マルチモーダルデータプラットフォーム）では、プロジェクト管理機能の一部として、MAIMLファイルのチェックイン/チェックアウト機能が必要とされています。複数のユーザーが協調してプロジェクトファイルを編集する際、排他制御によりファイルの整合性を保つ必要があります。

### 目的

- プロジェクトファイル（MAIML）のチェックイン/チェックアウト状態を管理するRESTful APIを提供する
- ユーザーによる排他的なファイル編集を可能にし、同時編集による競合を防止する
- プロジェクト管理画面からのシームレスな状態切り替えをサポートする

### スコープ

**対象範囲**:
- プロジェクトファイルのチェックアウト（編集権限の取得）
- プロジェクトファイルのチェックイン（編集完了と権限解放）
- チェックアウト状態の強制解除（管理者権限）
- 現在のチェックアウト状態の照会

**対象外**:
- ファイルバージョン管理機能（既存機能で対応）
- ファイル内容の編集機能（既存エディタで対応）
- ロールバック・マージ機能

## 2. 機能要件

### FR-1: チェックアウト機能

#### FR-1.1: チェックアウト実行

**要件**: システムは、ユーザーがプロジェクトファイルをチェックアウトできるようにしなければならない。

**受け入れ基準**:
- **AC-1.1.1**: `POST /api/v1/projects/{projectId}/checkout` にリクエストを送信した場合、システムは当該プロジェクトのcheckout_statusを1（チェックアウト中）に変更しなければならない
- **AC-1.1.2**: チェックアウトが成功した場合、システムはprojectテーブルのcheckout_statusカラム（NUMERIC(2,0)型）を更新しなければならない
- **AC-1.1.3**: 認証されたユーザーのみがチェックアウトを実行できる場合、システムは未認証リクエストに対して401エラーを返却しなければならない
- **AC-1.1.4**: ユーザーが所属組織のプロジェクトをチェックアウトしようとした場合、システムはマルチテナント分離を適用してorganization_idを検証しなければならない
- **AC-1.1.5**: プロジェクトのステータスが0（プロジェクト計画中）である場合、システムは400エラーを返却しなければならない
- **AC-1.1.6**: project_instructionテーブルに当該プロジェクトのレコードが存在しない場合、システムは400エラーを返却しなければならない

#### FR-1.2: チェックアウト競合検出

**要件**: システムは、既にチェックアウトされているプロジェクトへの重複チェックアウトを防止しなければならない。

**受け入れ基準**:
- **AC-1.2.1**: プロジェクトが既にチェックアウトされている状態で別のユーザーがチェックアウトしようとした場合、システムは409エラーを返却しなければならない
- **AC-1.2.2**: 409エラーレスポンスに現在のチェックアウト保持者の情報（ユーザー名、チェックアウト日時）を含める場合、システムは個人情報保護を考慮して必要最小限の情報のみを返却しなければならない
- **AC-1.2.3**: 同一ユーザーが既にチェックアウト済みのプロジェクトを再度チェックアウトしようとした場合、システムは冪等性を保ち200 OKを返却しなければならない

### FR-2: チェックイン機能

#### FR-2.1: チェックイン実行

**要件**: システムは、チェックアウトしたユーザーがプロジェクトファイルをチェックインできるようにしなければならない。

**受け入れ基準**:
- **AC-2.1.1**: `POST /api/v1/projects/{projectId}/checkin` にリクエストを送信した場合、システムは当該プロジェクトのcheckout_statusを0（チェックイン中）に変更しなければならない
- **AC-2.1.2**: チェックインが成功した場合、システムはprojectテーブルのcheckout_statusカラム（NUMERIC(2,0)型）を更新しなければならない
- **AC-2.1.3**: チェックアウトしていないユーザーがチェックインしようとした場合、システムは403エラーを返却しなければならない
- **AC-2.1.4**: 既にチェックインされているプロジェクトをチェックインしようとした場合、システムは冪等性を保ち200 OKを返却しなければならない
- **AC-2.1.5**: project_task_detailテーブルにtask_statusが1（実行中）のレコードが存在する場合、システムは400エラーを返却しなければならない

### FR-3: チェックアウト状態照会

#### FR-3.1: 状態取得

**要件**: システムは、プロジェクトの現在のチェックアウト状態を照会できるようにしなければならない。

**受け入れ基準**:
- **AC-3.1.1**: `GET /api/v1/projects/{projectId}/checkout-status` にリクエストを送信した場合、システムは現在のチェックアウト状態を返却しなければならない
- **AC-3.1.2**: レスポンスにチェックアウト状態（checked_out: boolean）、チェックアウト保持者のユーザーID、チェックアウト日時を含める場合、システムはこれらの情報を含めなければならない
- **AC-3.1.3**: プロジェクトがチェックインされている場合、システムはchecked_out: falseを返却し、ユーザー情報フィールドはnullとしなければならない

## 3. 非機能要件

### NFR-1: パフォーマンス

**要件**: システムは、チェックイン/チェックアウト操作を高速に処理しなければならない。

**受け入れ基準**:
- **AC-NFR-1.1**: チェックアウト/チェックイン操作のレスポンスタイムが通常時2秒以内である場合、システムはこの目標を達成しなければならない
- **AC-NFR-1.2**: 同時に10件のチェックアウト/チェックイン操作を処理する場合、システムはデータベースロックにより順次処理を保証しなければならない

### NFR-2: セキュリティ

**要件**: システムは、認証・認可・マルチテナント分離に関するセキュリティ要件を満たさなければならない。

**受け入れ基準**:
- **AC-NFR-2.1**: すべてのAPIエンドポイントにアクセスする場合、システムはJWT認証を要求しなければならない
- **AC-NFR-2.2**: すべてのデータベースクエリを実行する場合、システムはorganization_idフィルタを適用してマルチテナント分離を保証しなければならない
- **AC-NFR-2.3**: 監査ログを記録する場合、システムは実行者のユーザーID、組織ID、IPアドレス、タイムスタンプを含めなければならない

### NFR-3: 可用性

**要件**: システムは、高可用性を維持しなければならない。

**受け入れ基準**:
- **AC-NFR-3.1**: データベース接続が失敗した場合、システムは適切なエラーメッセージ（500 Internal Server Error）を返却し、詳細をログに記録しなければならない
- **AC-NFR-3.2**: APIエンドポイントがタイムアウトした場合、システムは504 Gateway Timeoutを返却しなければならない

### NFR-4: 保守性

**要件**: システムは、保守性とコード品質の基準を満たさなければならない。

**受け入れ基準**:
- **AC-NFR-4.1**: APIエンドポイントを実装する場合、システムはOpenAPI 3.0仕様に準拠したドキュメントを生成しなければならない
- **AC-NFR-4.2**: エラーレスポンスを返却する場合、システムは統一されたエラーフォーマット（api.md準拠）を使用しなければならない

## 4. 制約事項

### 技術的制約
- **TC-1**: バックエンドはNode.js 18+ + Express.js + TypeScriptで実装すること
- **TC-2**: データベースはPostgreSQL 18+を使用すること
- **TC-3**: 認証はJWT + Session Hybrid方式に従うこと

### ビジネス制約
- **BC-1**: チェックアウトの最大保持期間は設定しない（ユーザーが明示的にチェックインするまで保持）
- **BC-2**: 同一ユーザーは同時に複数プロジェクトをチェックアウト可能
- **BC-3**: プロジェクトステータスが0（計画中）の場合はチェックアウト不可
- **BC-4**: project_instructionレコードが存在しない場合はチェックアウト不可
- **BC-5**: task_statusが1（実行中）のタスクが存在する場合はチェックイン不可

### セキュリティ制約
- **SC-1**: すべてのAPIリクエストはミドルウェアチェーン（auth → tenantIsolation → permissionCheck）を通過すること
- **SC-2**: すべてのDBクエリはParameterized Queryを使用すること
- **SC-3**: クロステナントアクセスは厳禁（System Admin除く）

## 5. 前提条件

### システム前提
- **SP-1**: プロジェクト管理APIが既に実装されており、projectsテーブルが存在する
- **SP-2**: 認証・認可システムが正常に動作している
- **SP-3**: マルチテナント分離機能が実装されている

### データベーススキーマ前提
- **DP-1**: projectテーブルにはcheckout_status（NUMERIC(2,0)）カラムが既に存在する（0: チェックイン中、1: チェックアウト中）
- **DP-2**: projectテーブルには複合主キー（organization_id, project_id）、owner_user_id、create_at、project_statusカラムが既に存在する
- **DP-3**: projectテーブルのproject_statusカラムは、0（プロジェクト計画中）、1（実験準備中）、2（実験実施中）、3（実験完了）などのステータスを持つ
- **DP-4**: project_instructionテーブルが存在し、プロジェクトIDとの関連を持つ
- **DP-5**: project_task_detailテーブルが存在し、task_statusカラム（0: 未実行、1: 実行中、2: 完了）を持つ

### ユーザー前提
- **UP-1**: すべてのユーザーは認証済みでJWTトークンを保持している
- **UP-2**: ユーザーは自組織のプロジェクトに対してのみ操作可能

## 6. API仕様概要

### エンドポイント一覧

| メソッド | パス | 説明 | 権限 |
|---------|------|------|------|
| POST | `/api/v1/projects/{projectId}/checkout` | プロジェクトをチェックアウト | 認証ユーザー |
| POST | `/api/v1/projects/{projectId}/checkin` | プロジェクトをチェックイン | チェックアウト実行者 |
| GET | `/api/v1/projects/{projectId}/checkout-status` | チェックアウト状態取得 | 認証ユーザー |

### 共通レスポンス形式

#### 成功レスポンス
```json
{
  "success": true,
  "data": {
    "projectId": "uuid",
    "isCheckedOut": true,
    "checkedOutBy": "uuid",
    "checkedOutAt": "2026-01-16T10:00:00Z"
  },
  "meta": {
    "timestamp": "2026-01-16T10:00:00Z",
    "requestId": "req_abc123"
  }
}
```

## 7. テスト要件

### 単体テスト
- **UT-1**: チェックアウト成功パターン
- **UT-2**: チェックアウト競合パターン（409エラー）
- **UT-3**: プロジェクトステータスが0の場合のチェックアウト失敗（400エラー）
- **UT-4**: project_instructionレコードが存在しない場合のチェックアウト失敗（400エラー）
- **UT-5**: チェックイン成功パターン
- **UT-6**: 実行中タスクが存在する場合のチェックイン失敗（400エラー）
- **UT-7**: 権限不足パターン（403エラー）
- **UT-8**: マルチテナント分離検証

### 統合テスト
- **IT-1**: チェックアウト → 編集 → チェックインの完全フロー
- **IT-2**: 複数ユーザーによる同時チェックアウト試行
- **IT-3**: 実行中タスクがある状態でのチェックイン失敗確認

### セキュリティテスト
- **ST-1**: 未認証ユーザーのアクセス拒否
- **ST-2**: 他組織のプロジェクトへのアクセス拒否
- **ST-3**: SQLインジェクション対策検証

# 二段階ALB構成の検討結果

- **作成日**: 2026-04-28
- **対象**: 本番環境 AWS システム構成
- **参照図**: `docs/design/infrastructure/production-architecture.drawio` / `production-architecture-simple.drawio`

---

## 1. 背景・検討目的

現行の本番環境アーキテクチャでは、パブリックサブネットに配置した ALB（Application Load Balancer）が  
フロントエンド（port:3000）とバックエンド（port:3001）の両 ECS サービスに直接振り分けている。

**提案内容:**  
「サブネットの接点を1つにするために、以下の二段階 ALB 構成はどうか？」という検討依頼。

```
[現行]
インターネット → IGW → パブリック ALB → (/* or /api/*) → プライベートサブネット ECS

[提案]
インターネット → IGW → パブリック ALB → プライベート ALB → frontend ECS (port:3000)
                                          └────────────────→ backend ECS  (port:3001)
```

---

## 2. 現行アーキテクチャ（パブリックALB直接振り分け）

### 構成概要

```
[ユーザー]
  │ HTTPS:443（クライアント証明書 .p12）
  ▼
[Route 53] → ALB DNS名を返す
  │
  ▼
[Internet Gateway]
  │
  ▼
┌─────────────────────────────────┐
│ パブリックサブネット（1a/1c）     │
│  ALB (HTTPS:443)                │
│  ├─ mTLS 検証                   │
│  ├─ WAF アタッチ                 │
│  ├─ ACM サーバー証明書           │
│  └─ X-Amzn-Mtls-Clientcert-Subject ヘッダー付与 │
└─────────┬────────────────────────┘
          │ /* → port:3000
          │ /api/* → port:3001
          ▼
┌─────────────────────────────────┐
│ プライベートサブネット（1a/1c）   │
│  frontend ECS (Next.js)         │
│  backend ECS (Node.js)          │
└─────────────────────────────────┘
```

### セキュリティグループ構成

| SG名 | インバウンド |
|------|------------|
| alchemia-alb-sg | TCP:443 ← 0.0.0.0/0 |
| alchemia-frontend-sg | TCP:3000 ← alb-sg のみ |
| alchemia-backend-sg | TCP:3001 ← alb-sg のみ |

---

## 3. 提案アーキテクチャ（二段階ALB構成）

### 構成概要

```
[ユーザー]
  │ HTTPS:443
  ▼
[Internet Gateway]
  │
  ▼
┌─────────────────────────────────┐
│ パブリックサブネット（1a/1c）     │
│  External ALB (HTTPS:443)       │
│  ├─ mTLS 検証                   │
│  ├─ WAF アタッチ                 │
│  └─ /* → Internal ALB に転送    │
└─────────┬────────────────────────┘
          │ HTTP/HTTPS（全リクエストを転送）
          ▼
┌─────────────────────────────────┐
│ アプリプライベートサブネット（1a/1c）│
│  Internal ALB (HTTP or HTTPS)   │
│  ├─ /* → frontend ECS (3000)    │
│  └─ /api/* → backend ECS (3001) │
│                                 │
│  frontend ECS (Next.js)         │
│  backend ECS (Node.js)          │
└─────────────────────────────────┘
```

---

## 4. メリット

### 4-1. 将来的な拡張性

内部 ALB を追加することで、新たなサービス（例: 管理API用マイクロサービス）を追加した際に  
外部 ALB の設定を変更せずに内部 ALB のルーティングを変更するだけで対応できる。

### 4-2. ネットワーク境界の明確化

- 外部 ALB：インターネット境界（認証・WAF・mTLS）
- 内部 ALB：アプリケーション振り分け（パスベースルーティング）

という責務分離が明確になる。

### 4-3. 段階的なトラフィック制御

内部 ALB のみを更新することで、フロントエンド/バックエンドへのルーティングルールを  
外部 ALB（mTLS・WAF 設定）に影響なく変更できる。

---

## 5. デメリット・リスク

### 5-1. コスト増加

ALB は1台あたり月額 $16〜$20 程度（LCU 使用量に応じて変動）の固定コストがかかる。  
内部 ALB を追加することで **月額 $16〜$20 程度のコスト増加**となる。  
（Multi-AZ 構成でも ALB 自体のコストは1台単位で課金）

### 5-2. レイテンシ増加

外部 ALB → 内部 ALB → ECS と2段階のロードバランサーを経由するため、  
わずかながらレイテンシが増加する（数ミリ秒程度）。

### 5-3. 構成の複雑化

- 管理対象の ALB が2台になり、ルーティングルールの管理コストが増加する
- トラブルシューティング時の確認箇所が増える
- CloudFormation / CDK / Terraform 等の IaC テンプレートが複雑になる

### 5-4. ⚠️ 最大リスク：mTLS ヘッダーの消失

**これが最も重大なリスク。**

#### 問題の詳細

mTLS 認証において、外部 ALB はクライアント証明書を検証後、以下のヘッダーをバックエンドに付与する：

```
X-Amzn-Mtls-Clientcert-Subject: CN=<org-uuid>,O=MMDPF,...
```

このヘッダーから `CN`（UUID）を取り出すことで、バックエンドが `organization_id` を特定している。

#### 二段階 ALB 構成での懸念

外部 ALB が付与した `X-Amzn-Mtls-Clientcert-Subject` ヘッダーが、  
内部 ALB を通過する際に **除去または上書きされる可能性がある**。

- ALB は `X-Amzn-*` プレフィックスのヘッダーを予約済みシステムヘッダーとして扱う
- ロードバランサー一般の設計として、自身が生成するシステムヘッダーと同名のものを  
  受け取った場合、セキュリティ上の理由から上書きまたは除去する動作が一般的である
- 内部 ALB は mTLS 検証を行っていないため、`X-Amzn-Mtls-Clientcert-Subject` を  
  自身では付与しない。その結果、外部 ALB が付与した値が失われる可能性がある

#### 影響

もしヘッダーが消失した場合、バックエンドが `organization_id` を取得できなくなり、  
**マルチテナント分離が機能しなくなる**（全リクエストがエラーになる）。

#### 確認方法

実際の挙動は以下で確認可能：

```bash
# 内部ALB経由後のバックエンドコンテナで受け取ったヘッダーを確認
curl -H "X-Amzn-Mtls-Clientcert-Subject: CN=test-uuid,O=TEST" \
  http://<内部ALBのDNS>/api/echo-headers
```

#### 公式ドキュメント参照先

- **ALB mTLS ヘッダー仕様:**  
  https://docs.aws.amazon.com/elasticloadbalancing/latest/application/mutual-authentication.html

- **ALB HTTP ヘッダー全般:**  
  https://docs.aws.amazon.com/elasticloadbalancing/latest/application/x-forwarded-headers.html

> ⚠️ **注意**: 「内部ALBがヘッダーを除去する」という挙動は AWS 公式ドキュメントに明示的に  
> 記載されているわけではなく、ALB の一般的な設計原則に基づく推論を含む。  
> 採用前に必ず実際の動作検証を行うこと。

## 6. 現行構成との比較まとめ

| 観点 | 現行（単一ALB） | 提案（二段階ALB） |
|------|--------------|-----------------|
| **コスト** | ✅ ALB1台分 | ❌ ALB2台分（月+$16〜$20） |
| **レイテンシ** | ✅ 少ない | ⚠️ わずかに増加 |
| **構成の複雑さ** | ✅ シンプル | ❌ 複雑 |
| **mTLS ヘッダー** | ✅ 確実に到達 | ❌ 消失リスクあり（要検証） |
| **責務分離** | ⚠️ 単一ALBで全処理 | ✅ 外部/内部で分離 |
| **将来的な拡張性** | ⚠️ ALBルール追加で対応 | ✅ 内部ALB変更のみで対応 |
| **障害点** | ✅ 1箇所 | ❌ 2箇所（SPOF が増える） |
| **運用コスト** | ✅ 低 | ❌ やや高 |

---

## 7. 結論：現行構成（単一ALB）を維持

### 理由

1. **mTLS ヘッダー消失リスクが致命的**  
   本システムのマルチテナント認証の根幹である `X-Amzn-Mtls-Clientcert-Subject` ヘッダーが  
   内部 ALB 通過時に消失する可能性があり、動作保証のためには詳細な検証が必要。

2. **単一ALBで振り分けルールの変更は容易**  
   ALB のリスナールール（`/api/*` → backend-tg、`/*` → frontend-tg）は後から変更可能であり、  
   サービス追加時の拡張も単一 ALB のルール追加で対応できる。

3. **不要なコスト・複雑性の増加を避ける**  
   現時点でサブネット接点を減らす設計的メリットより、コスト・運用複雑性・リスクのデメリットが大きい。

### 現行構成の有効性

現行構成でも以下のセキュリティは十分に確保されている：

- ECS タスクはプライベートサブネットに配置（直接インターネットアクセス不可）
- SG により ALB からの通信のみを許可（frontend: TCP:3000、backend: TCP:3001）
- mTLS により正規クライアント証明書を持つユーザーのみが ALB を通過できる
- WAF により SQLi/XSS/IP フィルタリングを実施

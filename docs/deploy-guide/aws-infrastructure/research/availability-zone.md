# REPORT12: AZ（アベイラビリティゾーン）とは何か

- **作成日**: 2026-04-24
- **対象**: 検証環境 AWSシステム構成図（staging-architecture.drawio / ARCHITECTURE.md）の解説

---

## 1. AZ（アベイラビリティゾーン）とは

**AZ = Availability Zone（アベイラビリティゾーン）** の略称です。

AZとは、**AWSリージョン内にある物理的に独立したデータセンター群**のことです。  
構成図では以下の2つのAZが使われています。

| AZ名 | 意味 |
|------|------|
| `ap-northeast-1a` | 東京リージョン（ap-northeast-1）内の "1a" データセンター |
| `ap-northeast-1c` | 東京リージョン（ap-northeast-1）内の "1c" データセンター |

各AZは物理的に**異なる建物・異なる電源・異なるネットワーク**を持っており、片方が障害を起こしても、もう片方は影響を受けないように設計されています。

---

## 2. なぜ2つのAZが用意されているのか

**障害時の可用性（冗長性）を確保するため**です。

もし1つのAZしかなかった場合、そのデータセンターで障害（停電・火災・ネットワーク障害など）が発生すると、**サービス全体が止まってしまいます**。

2つのAZに分散することで、以下のような恩恵があります。

```
【1つのAZだけの場合（検証環境の問題点）】
  AZ-1a がダウン → サービス全停止 💀

【2つのAZに分散した場合（本番環境の理想）】
  AZ-1a がダウン → AZ-1c が継続稼働 ✅
```

### 構成図での具体的な使われ方

| AZ | 配置されているリソース |
|----|----------------------|
| `ap-northeast-1a` | パブリックサブネット（NLB/ALBノード）、プライベートサブネット（Auroraプライマリ、Redisノード、踏み台EC2） |
| `ap-northeast-1c` | パブリックサブネット（NLB/ALBノード）、プライベートサブネット（Auroraレプリカ用枠、Redisレプリカ用枠） |

`ARCHITECTURE.md` の「検証環境との差分サマリー」でも、**検証環境（シングルノード）→ 本番環境（MultiAZ）** という対応方針が記載されています。

```
Aurora 構成: シングルノード / db.t3.medium → MultiAZ / db.r6g.large
Redis 構成:  シングルノード / cache.t3.small → MultiAZ / AutoFailover
```

## 3. AZの複数化とスケーラビリティの関係

### 可用性 vs スケーラビリティの違い

| 概念 | 意味 | 目的 |
|------|------|------|
| **可用性（Availability）** | 障害が起きてもサービスが止まらない | 「落ちない」こと |
| **スケーラビリティ（Scalability）** | 負荷が増えても処理能力を増やせる | 「捌ける」こと |

### AZの複数化は主に「可用性」のため

AZを2つにしても、**処理能力の合計が保証されるわけではありません**。

```
【2つのAZ / タスク1個ずつ】
  AZ-1a: タスク1個（100リクエスト/秒）
  AZ-1c: タスク1個（100リクエスト/秒）
  合計: 200リクエスト/秒 に見えるが...

  AZ-1a が障害 → AZ-1c の100リクエスト/秒だけで継続
  ※ 200が保証されるわけではない（冗長性の考え方）
```

### スケーラビリティは「Auto Scaling」で実現

本来のスケーラビリティは、**ECS の Auto Scaling** によって実現します。

```
【負荷が増えた場合の Auto Scaling の動き】

通常時:
  AZ-1a: タスク1個
  AZ-1c: タスク1個

負荷増大 → Auto Scaling が検知 → タスクを自動追加:
  AZ-1a: タスク2個
  AZ-1c: タスク2個（AZをまたいで均等に増える）
  合計: 4倍の処理能力
```

構成図では `desiredCount ≥ 2` と記載されており、**複数タスクを複数AZに分散**させることで、可用性とスケーラビリティの両方を得る設計になっています。

### AZの複数化がスケーラビリティに間接的に貢献する部分

```
複数AZ
  ↓
Auto Scaling でタスクを追加するとき、
複数AZにまたがってタスクを配置できる
  ↓
1つのAZのリソース上限（CPU・メモリ）に
縛られずにスケールアップできる
```

ただしこれは「スケールしやすい土台を作る」という意味であり、**AZを増やしただけではスケーラビリティは確保されません**。

---

## 4. まとめ

| 目的 | 実現する仕組み |
|------|--------------|
| **可用性** | 複数AZ への分散配置（Multi-AZ） |
| **スケーラビリティ** | ECS Auto Scaling（タスク数の自動増減） |
| **両方の組み合わせ** | 複数AZ ＋ Auto Scaling → 「落ちない＆捌ける」システム |

今回の本番環境の設計は、`desiredCount ≥ 2` ＋ Multi-AZ の組み合わせで、可用性とスケーラビリティの土台を両立させた構成になっています。

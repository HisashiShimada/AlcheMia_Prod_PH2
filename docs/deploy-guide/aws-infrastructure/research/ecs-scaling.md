# ECSスケーリング調査レポート

- **作成日**: 2026-04-23
- **対象**: REPORT.md「5. ECSサービスの冗長性・自動スケール未設定」に関する調査
- **調査形式**: Q&A形式

---

## Q1. `desiredCount を2以上に変更` とは、タスクが2つ作成されるということか？

**回答: はい、その通りです。**

ECSにおける「タスク」とは、タスク定義（コンテナの設定）をもとに起動される **コンテナの実行単位** です。

`desiredCount=2` にすると、**同一のタスク定義から2つのタスク（コンテナ）が独立して起動・維持** されます。

```
desiredCount=1（現状）:
  ECSサービス → タスク①（バックエンドコンテナ）

desiredCount=2（対応後）:
  ECSサービス → タスク①（バックエンドコンテナ）
               → タスク②（バックエンドコンテナ）← 追加
```

**メリット**:
- タスク①が何らかの理由でクラッシュしても、タスク②が引き続きリクエストを処理できる（冗長性）
- Fargateの場合、ECSが自動的に異なるAZ（アベイラビリティゾーン）に分散配置を試みるため、AZ障害にも耐性が生まれる

## Q2. `Auto Scaling の設定` は負荷状況に応じてCPUやメモリが増やされるということか？

**回答: 「CPUやメモリのスペック（サイズ）を増やす」のではなく、「タスク（コンテナ）の数を増減させる」という仕組みです。**

これを **水平スケーリング（スケールアウト/スケールイン）** と呼びます。

```
通常時（負荷が低い）:
  タスク数: 2個（min-capacity=2）

高負荷時（CPU使用率 > 80% など）:
  タスク数: 5個に自動増加（スケールアウト）

負荷が下がったら:
  タスク数: 2個に自動減少（スケールイン）
```

REPORT.mdに記載のコマンドの意味:
```bash
--min-capacity 2   # タスク数の最小値（常に2つ以上維持）
--max-capacity 10  # タスク数の最大値（最大10まで自動増加）
```

Auto Scalingのポリシーには通常 **CPU使用率** や **メモリ使用率** のしきい値を設定し、それを超えたときにタスク数を増やします。

> **補足**: 個々のタスクに割り当てるCPU・メモリのサイズ自体を動的に変更することは「垂直スケーリング（スケールアップ）」と呼ばれますが、**ECS Auto Scaling は水平スケーリング（タスク数の増減）** が基本です。タスク単体のスペック変更はタスク定義の更新が必要で、Auto Scalingでは行われません。

## Q3. 垂直スケーリングを行うためには、どういった設定が必要か？

**回答: ECS（特にFargate）での垂直スケーリングは、「タスク定義」を更新して新しいリビジョンをデプロイする手順になります。Auto Scalingのように「自動で動的に変更」することはできず、手動またはCI/CDパイプラインで対応するのが一般的です。**

### 手順

#### 1. タスク定義で CPU・メモリを変更する

タスク定義（例: `ecs-task-definition-alchemia-backend.json`）の `cpu` と `memory` の値を変更します。

```json
// 変更前（例）
{
  "cpu": "512",
  "memory": "1024"
}

// 変更後（例: 2倍に増強）
{
  "cpu": "1024",
  "memory": "2048"
}
```

**Fargateで指定できる主な組み合わせ（CPU単位: 1vCPU=1024）:**

| CPU | メモリ範囲 |
|-----|----------|
| 256 (.25 vCPU) | 512MB〜2GB |
| 512 (.5 vCPU) | 1GB〜4GB |
| 1024 (1 vCPU) | 2GB〜8GB |
| 2048 (2 vCPU) | 4GB〜16GB |
| 4096 (4 vCPU) | 8GB〜30GB |

#### 2. 新しいタスク定義リビジョンを登録する

```bash
aws ecs register-task-definition \
  --cli-input-json file://ecs-task-definition-alchemia-backend.json
```

#### 3. ECSサービスを新しいタスク定義リビジョンで更新する

```bash
aws ecs update-service \
  --cluster alchemia-staging \
  --service alchemia-backend-service \
  --task-definition alchemia-backend-task:新リビジョン番号
```

これにより、既存タスクが新スペックのタスクに入れ替わります（ローリングアップデート）。

### 水平スケーリング vs 垂直スケーリングの使い分け

| | 水平スケーリング（Auto Scaling） | 垂直スケーリング（タスク定義更新） |
|---|---|---|
| 方法 | タスク数を増減 | CPU/メモリのサイズを変更 |
| 自動化 | ✅ 自動で動的に対応可能 | ❌ 手動またはCI/CDが必要 |
| 用途 | リクエスト数の増減に対応 | アプリの処理能力自体が不足している場合 |
| ダウンタイム | なし（ローリング） | なし（ローリング） |
| コスト | 需要に応じて変動 | 常に高いスペックのコストが発生 |

### 実運用上の推奨アプローチ

ECSでは一般的に **水平スケーリングを主体** として設計し、垂直スケーリングは以下のタイミングで対応するのが一般的です：

- **初期チューニング**: サービス開始後に実際のCPU/メモリ使用量を計測し、適切なサイズを決定
- **恒常的な不足**: 水平スケールで対応しきれないメモリ集約型の処理（例: 大容量ファイル処理）がある場合
- **コスト最適化**: タスク数を増やすより1タスクのスペックを上げた方がコスト効率が良い場合

## Q4. nginx+frontendが同居しているタスクで水平スケーリングを行うと、frontendの負荷が上がった場合に無駄にnginxも増えてコストがかかる？

**回答: はい、その通りです。**

### 現状の構成

nginx と frontend が **同一タスク内に同居** しています。

```
alchemia-nginx-service（ECSタスク）
  ├── nginxコンテナ  ← リバースプロキシ・SSL終端
  └── frontendコンテナ ← Next.jsアプリ
```

この構成でスケールアウトすると：

```
タスク① : nginx + frontend
タスク② : nginx + frontend  ← nginxも一緒に増える
タスク③ : nginx + frontend
```

**frontendだけに負荷がかかっている場合でも、nginxも同数増えてしまう**ため、その分コストが無駄になります。

### なぜこの構成になっているか

本プロジェクトの場合、nginxは単なるリバースプロキシではなく **クライアント証明書認証（mTLS）** を担っており、frontendコンテナと密接に連携する必要があります。また、Next.jsはサーバーサイドレンダリング（SSR）のため、nginxと同じタスクに置くことで低レイテンシな内部通信ができるという実装上の理由もあります。

### 本番環境での改善オプション

#### オプションA: nginx と frontend を別サービスに分離（推奨）

```
alchemia-nginx-service（ECSタスク）
  └── nginxコンテナのみ  ← 通常は2タスク固定で十分

alchemia-frontend-service（ECSタスク）← 新設
  └── frontendコンテナのみ ← 負荷に応じてAuto Scaling
```

- nginxはL4ロードバランサー（NLB）やALBが担うため、タスク数を増やす必要がほとんどない
- frontendの負荷に合わせてfrontendだけをスケールできる
- **ただし**: クライアント証明書認証のロジックをnginxに持たせたまま分離すると、内部通信の設計変更が必要

#### オプションB: nginxをALB（Application Load Balancer）に置き換え

AWSのALBはmTLS（相互TLS）にも対応しているため、nginxの役割をALB自体に移管できます。

```
インターネット → ALB（SSL終端・クライアント証明書検証）
                 ↓
           alchemia-frontend-service（ECSタスク）
           alchemia-backend-service（ECSタスク）
```

- nginxコンテナが不要になり、frontendとbackendを独立してスケール可能
- コスト・運用の複雑さが下がる可能性がある
- **ただし**: 現在のnginxが行っているルーティングロジックをALBのルールに移植する必要がある

#### オプションC: 現状維持（検証環境・小規模運用では許容範囲）

nginxのリソース消費（CPU・メモリ）は非常に軽量なため、frontendと同居してもコスト増は軽微です。本番初期の運用規模であれば、**現状構成のまま `desiredCount=2` + Auto Scaling** で運用を始め、トラフィックが増えてから分離を検討するという判断も現実的です。

| オプション | メリット | デメリット |
|-----------|---------|-----------|
| A: nginx/frontend分離 | スケールを独立制御できる | 設計変更が必要 |
| B: ALBに移行 | nginx不要・完全分離 | 移行コスト大 |
| C: 現状維持 | 対応不要 | 無駄なnginxが増える（ただし軽微） |

**推奨**: 本番初期であれば **オプションC（現状構成）で運用開始 → 負荷状況を見てオプションAへ移行** が現実的な進め方です。

## Q5. nginx+frontendが同居しているタスクで垂直スケーリングを行うと、nginxも増強されてしまう？

**回答: はい、その通りです。** 垂直スケーリングでも水平スケーリングと同じ問題が発生します。

### なぜそうなるのか

ECSのタスク定義では、**タスク全体**に対してCPUとメモリを割り当てます。タスク内の個々のコンテナにも上限は設定できますが、タスク全体のリソースが増えれば当然nginxも含めてコストが増加します。

```
タスク定義: cpu=1024, memory=2048
  ├── nginxコンテナ  (containerCpu=256, containerMemory=512)
  └── frontendコンテナ (containerCpu=768, containerMemory=1536)

↓ 垂直スケーリング（タスク定義を更新）

タスク定義: cpu=2048, memory=4096  ← タスク全体が増強
  ├── nginxコンテナ  (containerCpu=256, containerMemory=512)  ← 上限は同じでも...
  └── frontendコンテナ (containerCpu=1792, containerMemory=3584) ← frontendに多く割り当て可
```

コンテナレベルの割り当てを調整することで「frontendに多く振る」ことはできますが、**タスク全体のコストはnginx分も含めて増加**します。

### 水平・垂直スケーリング どちらも同じ問題を抱えている

| スケーリング方法 | nginxへの影響 |
|---------------|-------------|
| 水平（タスク数を増やす） | nginxコンテナが台数分増える |
| 垂直（CPU/メモリを増やす） | nginxコンテナも一緒に増強されるコストがかかる |

**どちらの方法でも、nginx+frontendが同居している限り、frontendだけを独立してスケールすることは構造的にできません。**

## Q6. コンテナレベルのCPU・メモリは `ecs-task-definition-alchemia-nginx.json` で設定できるか？

**回答: はい、設定できます。** ただし現在の `ecs-task-definition-alchemia-nginx.json` では、コンテナレベルのCPU・メモリは未設定です。

### 現状の設定確認

```json
// タスクレベル（現状）
"cpu": "512",      ← タスク全体: 0.5 vCPU
"memory": "1024",  ← タスク全体: 1GB

// containerDefinitions 内（mmdpf-frontend, mmdpf-nginx）
// → cpu / memory フィールドなし（未設定）
```

現状はタスク全体のリソースだけ決まっており、**2つのコンテナが1024MBのメモリと512CPUユニットを共有**している状態です。

### コンテナレベルで設定できるフィールド

各コンテナの定義に以下を追加できます：

```json
{
  "name": "mmdpf-frontend",
  "cpu": 384,               ← コンテナに割り当てるCPUユニット（タスク合計512の中から）
  "memory": 768,            ← メモリハードリミット（この上限を超えるとコンテナが強制終了）
  "memoryReservation": 512, ← メモリソフトリミット（予約量。超えても即強制終了しない）
  ...
},
{
  "name": "mmdpf-nginx",
  "cpu": 128,               ← nginxは軽量なので少なく割り当て
  "memory": 256,
  "memoryReservation": 128,
  ...
}
```

| フィールド | 意味 | Fargateでの扱い |
|-----------|------|----------------|
| `cpu` | CPUユニット数 | 任意設定。タスク合計を超えてはいけない |
| `memory` | メモリハードリミット | 超えるとコンテナが強制終了（OOM Kill） |
| `memoryReservation` | メモリソフトリミット | 予約量として確保。超えても即終了しない |

### 注意事項

- **Fargateの場合**: コンテナの `memory` の合計がタスクの `memory` を超えてはいけません
- コンテナレベルのCPUは相対的な**優先度**として機能します（厳密な上限ではなく、余裕があれば超えて使える）
- **設定しなくても動作はします**（未設定の場合はタスクのリソースをコンテナ間で競争して使用）

### 現状の構成への適用例

```json
// タスクレベル（変更なし）
"cpu": "512",
"memory": "1024",

// frontendコンテナ（Next.js は比較的重い）
"name": "mmdpf-frontend",
"cpu": 384,
"memoryReservation": 768,

// nginxコンテナ（軽量）
"name": "mmdpf-nginx",
"cpu": 128,
"memoryReservation": 256,
```

このように設定することで、**nginxに過度にリソースが使われないよう制限**しつつ、frontendに多くのリソースを優先配分できます。ただし、コスト（Fargate課金）はタスク全体のCPU・メモリで決まるため、**nginxとfrontendを同居させている限りコスト削減にはなりません**。

## Q7. Auto ScalingをONにした場合、desiredCountは2にしておく必要があるか？

**回答: 厳密には「必須」ではありませんが、`desiredCount` と `min-capacity` を揃えておくのがベストプラクティスです。**

### desiredCount と min-capacity の関係

| 設定項目 | 役割 |
|---------|------|
| `desiredCount` | ECSサービス起動時・通常時に維持したいタスク数 |
| `--min-capacity` | Auto Scalingが維持する**最小**タスク数（下限） |
| `--max-capacity` | Auto Scalingが増やせる**最大**タスク数（上限） |

### desiredCount=1 のまま Auto Scaling をONにした場合

```
起動時: desiredCount=1 → タスク1個でスタート
      ↓
Auto Scaling が min-capacity=2 を検知
      ↓
即座にタスクを2個に増やす（スケールアウト）
```

動作はしますが、「起動直後に余計なスケールアウトが走る」という無駄が生じます。

### 推奨設定

```bash
# desiredCount と min-capacity を揃える（推奨）
desiredCount = 2
--min-capacity 2
--max-capacity 10
```

こうすることで、起動時から2タスクが維持され、Auto Scalingが安定した状態でコントロールできます。

## Q8. desiredCountにいくつを設定すべきかは、事前の検証が必要か？

**回答: `desiredCount=2`（冗長性確保）自体は検証なしで決定できますが、`max-capacity` やスケールアウトのしきい値は実稼働後のモニタリングを経て調整するのが現実的です。**

### 考え方の整理

| 設定値 | 意味 | 検証の要否 |
|--------|------|-----------|
| `desiredCount = 2` | 冗長性の確保（AZ障害対応） | **事前に決定可能**（冗長化が目的なら2で固定） |
| `min-capacity = 2` | Auto Scaling の下限 | 上に同じ |
| `max-capacity = 10` | スケールアウトの上限 | **実際の負荷計測後に調整推奨** |
| スケールアウトのしきい値（CPU>70%等） | いつタスクを増やすか | **実稼働後にチューニング推奨** |

### 実務的な進め方

```
① 本番初期: desiredCount=2, min=2, max=10, CPU>70% でスケールアウト設定
          ↓（まず安定稼働させる）
② CloudWatch でタスクの CPU・メモリ使用率を1〜2週間計測
          ↓
③ 計測結果に応じて以下を調整:
   - max-capacity: 実際のピーク時タスク数 + 余裕分
   - スケールアウトしきい値: 60%〜80%の範囲で実態に合わせて調整
   - タスクの垂直スペック（cpu/memory）: 常時使用率が高ければ見直し
```

## Q9. Auto Scalingでタスクを増やす条件は何か？

**回答: ECS Auto Scalingのスケールアウト条件は、CloudWatchのアラームをベースに設定します。**

### スケーリングポリシーの種類

#### ターゲット追跡スケーリング（最もシンプル・推奨）

「CPU使用率を○%に保つように、タスク数を自動調整する」という設定です。

```bash
aws application-autoscaling put-scaling-policy \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration '{
    "TargetValue": 70.0,
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ECSServiceAverageCPUUtilization"
    },
    "ScaleOutCooldown": 60,    ← スケールアウト後の待機時間（秒）
    "ScaleInCooldown": 300     ← スケールイン後の待機時間（秒）
  }'
```

| 設定できるメトリクス | 説明 |
|---|---|
| `ECSServiceAverageCPUUtilization` | タスク全体の平均CPU使用率 |
| `ECSServiceAverageMemoryUtilization` | タスク全体の平均メモリ使用率 |
| `ALBRequestCountPerTarget` | ALB経由のターゲット1つあたりリクエスト数 |

#### ステップスケーリング（しきい値を細かく設定したい場合）

「CPU>60% になったら1タスク追加、CPU>80% になったら2タスク追加」のように、段階的に増減数を変えたい場合に使います。

### 実際の動作フロー（ターゲット追跡の例）

```
通常時（CPU 40%）:
  タスク数: 2個（min-capacity=2）

↓ アクセス増加

CPU使用率が70%を超え始める:
  Auto Scaling が「タスクを追加すれば平均70%に下げられる」と判断
  → タスクを3個に増加（スケールアウト）

↓ さらにアクセス増加

CPU使用率がまだ高い:
  → タスクを4個、5個…と増加（最大 max-capacity=10 まで）

↓ アクセス減少

CPU使用率が下がる:
  → ScaleInCooldown（300秒）待機後、タスクを減らす（スケールイン）
  ※ ただし min-capacity=2 を下回ることはない
```

### クールダウンについて

| 設定 | 意味 | 推奨値 |
|------|------|--------|
| `ScaleOutCooldown` | スケールアウト後、次のスケールアウトまでの待機時間 | 60秒（短め） |
| `ScaleInCooldown` | スケールイン後、次のスケールインまでの待機時間 | 300秒（長め） |

スケールインは慎重に行うべき（急に減らすとリクエストが捌けなくなる）ため、クールダウンを長めに設定するのが一般的です。

### mmdpfプロジェクトへの推奨設定（初期値）

```
ポリシー種別: ターゲット追跡スケーリング
メトリクス:  ECSServiceAverageCPUUtilization（CPU使用率）
ターゲット値: 70%
min-capacity: 2
max-capacity: 10
ScaleOutCooldown: 60秒
ScaleInCooldown: 300秒
```

## Q10. タスクが停止した場合、Auto Scalingはタスクを増やしてくれるか？

**回答: いいえ。タスクの自動復旧は Auto Scaling ではなく、ECS サービス自体の機能です。**

### 役割の違い

| 機能 | 担当 | 役割 |
|------|------|------|
| **タスクの自動復旧**（クラッシュ・停止からの回復） | **ECS サービス** | desiredCount を維持する |
| **タスクのスケーリング**（負荷に応じた増減） | **Auto Scaling** | CPU/メモリ等のメトリクスに応じてタスク数を変える |

### ECS サービスによる自動復旧の仕組み

ECS サービスは常に **desiredCount（目標タスク数）** を維持しようとします。

```
desiredCount=2 の状態でタスク①がクラッシュ:

  タスク①（停止）
  タスク②（稼働中）
       ↓
  ECSサービスが検知:「現在のタスク数=1、目標=2」
       ↓
  自動的に新しいタスク①'を起動（Auto Scalingとは無関係）
       ↓
  タスク①'（新規起動）
  タスク②（稼働中）← 元に戻る
```

**これは Auto Scaling が ON かどうかに関係なく、ECS サービスが常に行う動作です。**

### まとめ: 機能の使い分け

| ケース | 対応する機能 |
|--------|------------|
| タスクがクラッシュ・停止した → 元の数に戻す | **ECS サービス**（Auto Scaling 不要） |
| 負荷が高くてタスクを増やしたい | **Auto Scaling** |
| 負荷が下がってタスクを減らしたい | **Auto Scaling** |
| min-capacity を下回らないよう保証する | **Auto Scaling** |

`desiredCount=2` に設定しておくだけで、**Auto Scaling が無くてもタスク停止からの自動復旧は機能します**。Auto Scaling は「負荷に応じた増減」のために追加で設定するものです。

---

## まとめ

| 項目 | 内容 |
|------|------|
| `desiredCount=2` | 同じコンテナが2つ起動・維持される（冗長化） |
| Auto Scaling | 負荷に応じてタスク**数**が自動増減される（CPUやメモリのサイズは変わらない） |
| 垂直スケーリング | タスク定義を更新してデプロイすることで実現（自動化不可） |
| nginx+frontend同居の問題 | 水平・垂直どちらのスケーリングでも nginxも一緒にスケールされる。根本解決はサービス分離 |
| コンテナレベルのリソース設定 | `cpu` / `memory` / `memoryReservation` で個別コンテナへの割り当てを制御可能（コスト削減には寄与しない） |
| desiredCount と min-capacity | 揃えておくのがベストプラクティス（例: 両方 2 に設定） |
| Auto Scalingのトリガー | CloudWatch メトリクス（CPU使用率等）のしきい値を超えたときにスケールアウト |
| タスク停止からの復旧 | Auto Scaling ではなく **ECS サービス**が担当（desiredCount を維持しようとする） |

## 1. 目的と適用範囲

### 1.1 目的

本書は、Alchemia に実装する実験品質管理機能のうち、実験管理者が MaiML プロジェクト全体の品質を最終評価し記録する工程について、基本設計を定義するものである。具体的な対象機能は、MaiMLプロジェクト全体評価、階層別サマリー算出、および全体評価結果の MaiML への記録の三機能である。

### 1.2 適用範囲

本書は、下位評価（メソッド別・タスク別・トランジション別）が既に登録済みであることを前提として、それらを判断材料に集約し、実験管理者が全体評価を決定してエビデンスとして記録するまでを対象とする。作業者による一次品質記録の入力機能、実験計画作成機能、テンプレート機能は本書の対象外とし、必要に応じて関連機能として参照するに留める。

### 1.3 前提条件

品質評価軸は、本プロジェクトで確立済みの確からしさ評価と環境評価の二軸を維持する。下位評価は良好・要確認・不良の三段階のデジタル評価と、文章によるアナログ評価（感情評価）で登録済みである。評価の粒度は、MaiML 全体を必須、メソッド別・トランジション別を任意とする。

## 3. 全体方針と特許との位置づけ

### 3.1 設計方針

本設計は、本プロジェクト固有の評価軸（確からしさ・環境）の内容には手を加えず、評価を行う階層構造・集計・確定・記録のフレームを整備することを方針とする。これにより、独自の評価軸を維持したまま、将来的に特許の枠組みへ写像・拡張できる余地を確保する。

### 3.2 特許（特願2026-013606）との位置づけ

特許は、工程（トランジション）単位・タスク単位・メソッド単位・実験全体という階層で品質を評価・集計する構成を規定している。本設計の三階層集計（MaiML全体・メソッド別・トランジション別）は、この特許の階層評価構造と一対一に対応づけられる。評価軸の内容（本設計は確からしさ・環境、特許は時間品質・精度品質）は各階層のセルの中身として保持されるため、将来この中身を特許の時間乖離率・精度達成度へ写像する際にも、階層集計ロジックと画面構造をそのまま流用できる。数値スコア写像の既定値（良好100・要確認50・不良0）は、特許の精度達成度（100点・50点・0点）と一致させており、写像時の接続点として意図的に設計している。

## 5. 画面設計

### 5.1 プロジェクト全体評価画面

既存アプリのタブ体裁に「全体評価」タブとして組み込む。画面は上から下へ、判断材料の提示から意思決定へと導線を構成する。

| 領域 | 内容 | 備考 |
|---|---|---|
| 階層別サマリー | メソッド別・タスク別・トランジション別の良好／要確認／不良の度数分布を集計バーで俯瞰表示。 | 第6章のロジックで算出 |
| 要注意項目 | 良好以外の評価をコメント付きで抽出し、判断材料として前面に提示。 | 不良・要確認を重大度順に表示 |
| 全体評価の決定 | デジタル評価（良好／要確認／不良＋任意の数値スコア）とアナログ評価（文章）を入力し登録。 | MaiML全体は必須スコープ |

全体評価の評価値は下位評価と同一の三段階スケールを用いる。これにより全体評価が既存の評価一覧に同一データ構造の1行として自然に追記でき、評価単位が「プロジェクト全体」であるだけで他の階層評価と統一的に扱える。

### 5.2 集約ルール設定画面

テナント（組織）共通の集約ルールを設定する管理画面。設定変更が階層別サマリーの算出結果へ与える影響を、登録済みデータに対するプレビューで即時確認できる。

| 設定項目 | 選択肢 | 効果 |
|---|---|---|
| 評価値→スコア写像 | 良好／要確認／不良の各数値 | 階層スコアの算出基礎 |
| 対象ロールアップ | ワーストケース／多数決／平均 | 多基準対象の代表値決定（第1段） |
| 階層代表ステータス | 最悪値採用／多数決 | 階層の代表ステータス決定（第2段） |
| 階層スコア | 平均／最小値 | 階層スコアの代表方式 |
| 未評価の扱い | 別カウント／分母除外／良好扱い | 未評価対象の集計上の扱い |
| トランジション階層 | 合算／分離表示 | トランジション（メソッド別／タスク別）の階層粒度 |

## 6. 処理設計（階層別サマリー算出ロジック）

### 6.1 評価値の写像

三値の評価値に対して、集約のために二系統の尺度を定義する。順序尺度（重大度）は良好→0・要確認→1・不良→2 とし、値が大きいほど品質が低いことを表す。数値尺度（品質スコア）は集約ルールの写像に従う（既定：良好100・要確認50・不良0）。

| 評価値 | 重大度（順序尺度） | 品質スコア（既定） |
|---|---|---|
| 良好 | 0 | 100 |
| 要確認 | 1 | 50 |
| 不良 | 2 | 0 |

### 6.2 二段集約

サマリーは、対象単位ロールアップ（第1段）と階層集計（第2段）の二段で算出する。二段構成とするのは、一つの対象が複数の不確かさ基準で評価される場合に、レコードを直接数えると多基準の対象が過大に重み付けされるためである。

**第1段：対象単位ロールアップ**

同一対象に複数基準のレコードがある場合、その代表評価値を集約ルールの対象ロールアップ規則で決定する。既定のワーストケースでは、各基準の重大度の最大値を採用する（一つでも不良基準があれば当該対象は不良）。これは、一基準でも品質基準を満たさない対象を要注意とみなす、見逃しコストと過検出コストの非対称性を反映した保守的集約である。

**第2段：階層集計**

対象単位に丸めた代表評価値を階層別にグルーピングし、良好・要確認・不良の度数分布と対象数 N を算出する。階層代表ステータスは、最悪値採用の場合はその階層に存在する最悪の値とし、不良が1件でもあれば階層は不良表示となる。多数決の場合は最頻値を採り、同数タイは重大側へ寄せる。階層スコアは、平均採用なら対象スコアの平均、最小値採用なら最小値（最悪対象）を用いる。

トランジション（メソッド別）とトランジション（タスク別）は、集約ルールのトランジション階層設定が合算の場合は 1 階層（トランジション別）に、分離の場合は 2 階層に集計する。未評価対象は、集約ルールの未評価の扱いに従う（既定の別カウントでは、良好・要確認・不良と別に未評価数を保持し N には含める）。

**算出式**

各階層 L について、対象集合を T\_L、対象 t の代表評価値を r(t)、カテゴリ c の度数を n\_c(L) = |{ t ∈ T\_L : r(t) = c }|、対象数を N(L) = |T\_L| とする。

- 階層代表ステータス（最悪値採用）：status(L) = argmax\_{t∈T\_L} severity(r(t))
- 階層スコア（平均）：score(L) = (1/N) Σ q(r(t))
- 階層スコア（最小値）：score(L) = min\_{t∈T\_L} q(r(t))

ここで severity は重大度、q は品質スコア写像を表す。

### 6.3 算出例（添付データ7件）

全対象が単一基準のためロールアップは登録値と一致し、既定ルール（ワーストケース・最悪値採用・平均・合算）を適用した集計結果を以下に示す。

| 階層 | N | 良好 | 要確認 | 不良 | 代表ステータス | 平均スコア |
|---|---|---|---|---|---|---|
| メソッド別 | 2 | 1 | 1 | 0 | 要確認 | 75.0 |
| タスク別 | 2 | 1 | 0 | 1 | 不良 | 50.0 |
| トランジション別 | 3 | 2 | 1 | 0 | 要確認 | 83.3 |

トランジション別の3件は、トランジション（メソッド別）のT001と、トランジション（タスク別）のT002・T003を合算した結果である。集計バーは度数分布を N で正規化した比率で描画する。

## 7. データ設計

データ構造は JSON Schema（draft 2020-12）で定義する。集約ルールと評価レコードの主要項目を以下に示す。詳細な定義は別添スキーマファイル（`aggregation-rule.schema.json`、`evaluation-record.schema.json`）を正とする。

### 7.1 集約ルール（テナント共通）

| 項目 | 型 | 説明 |
|---|---|---|
| ruleId / version | uuid / integer | ルール系列と版。(ruleId, version) で一意。 |
| tenantId | string | テナント識別子。ルールはこの単位で共通。 |
| status | enum | ACTIVE / DEPRECATED。ACTIVE は同時に1版のみ。 |
| scoreMapping | object | 良好／要確認／不良の数値スコア写像。 |
| targetRollup | enum | WORST_CASE / MAJORITY / AVERAGE。 |
| levelStatusRule | enum | WORST_CASE / MAJORITY。 |
| levelScoreRule | enum | MEAN / MIN。 |
| missingHandling | enum | SEPARATE_COUNT / EXCLUDE_DENOMINATOR / TREAT_AS_GOOD。 |
| transitionHierarchy | enum | MERGE / SPLIT。 |

### 7.2 評価レコード（MaiML記録）

| 項目 | 型 | 説明 |
|---|---|---|
| evaluationId | uuid | 評価レコード識別子。 |
| maimlProjectId | string | MaiML全体（プロジェクト）識別子。 |
| evaluationScope | const | MAIML_PROJECT（全体評価が必須スコープ）。 |
| evaluatedBy / evaluatedAt | string / date-time | 実験管理者と登録日時（断面の基準時刻）。 |
| appliedRule | object | 適用したテナント共通ルールの参照と凍結パラメータ。 |
| overall | object | MaiML全体評価。digital（三値＋任意スコア）と analog（文章）。 |
| levelEvaluations | array | 任意：メソッド別・トランジション別の管理者個別評価。 |
| aggregationSnapshot | object | 集計結果の断面。再計算しない。 |

`aggregationSnapshot` は三層で構成する。`levels` が階層別サマリーの計算結果、`sourceEvaluations` が集計入力となった全下位評価の凍結値、`attentionItems` が良好以外を抽出した判断材料の部分集合である。入力・規則・出力を同一レコード内に揃えることで、第三者が独立に再計算して一致を検証できる、証拠として完結した断面となる。

## 8. 集約ルール管理方針

集約ルールはテナント（組織）全体で共通とし、プロジェクトやテンプレート単位の上書きは持たない。テナント内では status=ACTIVE の版を同時に1つだけ有効とし、新版を有効化すると旧版は DEPRECATED へ遷移する。評価登録時には、その時点で ACTIVE な版が参照され、評価レコードの `appliedRule` にパラメータごと凍結される。テナント共通で一元管理しつつ、過去エビデンスの再現性を各レコード側で自己完結的に保証する設計である。

---

## 9. エビデンス記録方針

集計結果は評価登録時点の断面としてのみ MaiML に記録し、参照のたびに再計算しない。断面は、集計入力（凍結された下位評価）・適用規則（凍結された `appliedRule`）・算出結果（`levels`）を同一レコード内に保持し、再現可能な証拠として完結させる。集約ルールが後日変更されても、当該評価が当時のどの版・どの写像・どの規則で算出されたかをレコード単独で証明できる。これは、断面のみ残すという要件を、単なる結果保存ではなく再現可能な証拠保存として解釈した設計である。

## 10. 制約・トレードオフ・今後の検討事項

| 論点 | 内容 | 対応方針 |
|---|---|---|
| 集約規則の選択 | 最悪値採用／平均は見逃しリスクと過検出のトレードオフを持つ。 | 設定画面のプレビューで数値影響を可視化し組織方針で決定。 |
| 多基準ロールアップ | 単一基準データでは効果が出ず、多基準対象で初めて差が生じる。 | 多基準対象を含む検証データをテストケースとして別途用意。 |
| 未評価の扱い | 除外は完成度が不可視、良好扱いは過大評価となる。 | 既定は別カウントとし、未評価件数を可視化。 |
| 階層粒度と横断分析 | 断面はルール適用後の粒度で凍結され、テナント版により粒度が異なり得る。 | 横断分析要件の具体化時に正規化ビュー併設を検討。 |
| 階層間の評価不一致 | 下位に不良が残る状態での全体評価の扱い。 | 要確認（条件付き相当）で記録し、改善事項を次回へ引継ぎ。 |

## 11. 特許との対応

本設計の主要要素と特許（特願2026-013606）の対応を以下に示す。評価軸の内容は独自だが、階層構造・集計・記録のフレームが整合する。

| 本設計の要素 | 特許の対応要素 |
|---|---|
| 三階層集計（全体・メソッド・トランジション） | 工程／タスク／メソッド／実験全体の階層評価 |

| 全体評価結果のMaiML記録 | 実験計画・実験結果・評価結果を関係づけた実験データ記憶（請求項9） |
